title: Требования к DNS установки
---

Перед установкой notify у домена отправителя должны быть опубликованы три записи: DKIM, SPF и
DMARC. notify проверяет их при старте и не становится готовым, пока все три проверки не пройдут.
Если запись нарушена, старт заканчивается отказом с именем проверки и причиной. В работе notify
повторяет проверки по расписанию: нарушение отражается в метрике и журнале, но отправку не
останавливает. Страница описывает форму записей, тексты отказа, объект ключа DKIM и порядок
смены ключа DKIM.

Готовых записей для копирования здесь нет — только их форма. Значения зависят от домена и ключа
вашей установки.

## Домен отправителя

Все три проверки идут по **домену `From`** — домену адреса отправителя установки. Адрес задаёт
ключ values `global.kacho.identity.smtp.fromAddress` (в процессе — `KACHO_NOTIFY_SMTP_FROM_ADDRESS`).
Ниже этот домен обозначен `<домен From>`.

Имена запросов notify строит абсолютными (с завершающей точкой), поэтому домены поиска пода
на результат не влияют. Резолвер — резолвер пода; отдельной настройки адреса резолвера у notify
нет.

## Три проверки

| Проверка (`check`) | Имя запроса TXT | Проверка пройдена, когда |
|---|---|---|
| `dkim` | `<селектор>._domainkey.<домен From>.` | запись ровно одна, и её открытый ключ RSA совпадает с ключом, выведенным из закрытого ключа объекта DKIM |
| `spf` | `<домен From>.` | запись `v=spf1` ровно одна, и её последний механизм — `-all` или `~all` |
| `dmarc` | `_dmarc.<домен From>.` | запись `v=DMARC1` ровно одна, и её политика — `p=quarantine` или `p=reject` |

`<селектор>` — селектор из объекта ключа DKIM ([ниже](#объект-ключа-dkim)).

Форма записей:

| Имя | Тип | Значение (форма) |
|---|---|---|
| `<селектор>._domainkey.<домен From>` | TXT | `v=DKIM1; k=rsa; p=<открытый ключ в base64>` |
| `<домен From>` | TXT | `v=spf1 <механизмы ваших ретрансляторов> -all` (или `~all`) |
| `_dmarc.<домен From>` | TXT | `v=DMARC1; p=quarantine` (или `p=reject`) и прочие теги вашей политики |

Открытый ключ в записи DKIM принимается в форме SubjectPublicKeyInfo или PKCS#1. Запись,
разбитая на несколько строк TXT, склеивается резолвером и читается как одна.

### Организационный домен не используется

Политику DMARC notify ищет **только** по имени `_dmarc.<домен From>.`. Запись DMARC
вышестоящего (организационного) домена с тегом `sp=` не учитывается. Если домен `From` —
поддомен, опубликуйте запись DMARC на самом поддомене. Иначе старт откажет с причиной
`dmarc_missing`, даже если получатели применили бы политику организационного домена.

## Причины нарушения

Каждая проверка разбирает запись по закрытой таблице. Строки читаются сверху вниз, срабатывает
первая подходящая. Исход «пройдена» даёт только последняя строка таблицы; любое иное
содержимое — нарушение. Причина попадает в текст отказа и в журнал без содержимого записи.

### `dkim`

| Содержимое записи | Причина |
|---|---|
| записи нет | `dkim_missing` |
| записей под селектором больше одной | `dkim_multiple` |
| тег повторён или не разбирается; `v=` стоит не первым или не равен `DKIM1` | `dkim_malformed` |
| `k=` задан и не равен `rsa` | `dkim_key_type` |
| `h=` задан и не содержит `sha256` | `dkim_hash` |
| тега `p=` нет | `dkim_malformed` |
| `p=` пуст (ключ отозван) | `dkim_revoked` |
| `p=` не base64 либо не разбирается как открытый ключ | `dkim_malformed` |
| ключ в записи не RSA | `dkim_key_type` |
| ключ в записи не совпадает с ключом объекта DKIM | `dkim_key_mismatch` |
| ключи совпадают | пройдена |

### `spf`

| Содержимое TXT домена `From` | Причина |
|---|---|
| нет записи, которая начинается с `v=spf1`, а за ним пробел или конец записи (`v=spf10` — не SPF) | `spf_missing` |
| таких записей больше одной | `spf_multiple` |
| терм не разбирается как механизм или модификатор `имя=значение` | `spf_malformed` |
| механизма `all` нет, есть `redirect=` | `spf_redirect` |
| механизма `all` нет | `spf_no_all` |
| после `all` стоит ещё механизм (модификаторы после него допустимы) | `spf_all_not_last` |
| `all` с квалификатором `+`, `?` или без квалификатора | `spf_all_permissive` |
| `-all` или `~all` | пройдена |

### `dmarc`

| Содержимое TXT `_dmarc.<домен From>` | Причина |
|---|---|
| нет записи, первый тег которой — ровно `v=DMARC1` | `dmarc_missing` |
| таких записей больше одной | `dmarc_multiple` |
| тег повторён или не разбирается как `имя=значение` | `dmarc_malformed` |
| тега `p=` нет | `dmarc_policy_invalid` |
| `p=none` | `dmarc_policy_none` |
| `p=` с другим значением, кроме `quarantine` и `reject` | `dmarc_policy_invalid` |
| `p=quarantine` или `p=reject` | пройдена |

Регистр значений `rsa`, `all`, `none`, `quarantine` и `reject` не учитывается.

## Старт: ожидание и тексты отказа

Проверки идут после подъёма диагностической поверхности. Пока они не прошли, `/healthz`
отвечает, а `/readyz` сообщает «не готов». Отказ с именем проверки поэтому наступает раньше,
чем перезапуск пода по проверке живости.

Одна попытка — три проверки параллельно; на каждый запрос отводится 5 с. Если нарушения нет,
но какая-то проверка не получила ответа (тайм-аут, SERVFAIL), следующая попытка начинается
через 1 с. Попытки идут до срока `KACHO_NOTIFY_DNS_BOOT_DEADLINE`. «Записи нет» — это ответ,
а не временный отказ: такая проверка нарушена сразу.

При отказе процесс завершается с ненулевым кодом и пишет в журнал запись `отказ старта` с полем
`err`. Его текст:

| Ситуация | Текст `err` |
|---|---|
| запись нарушена | `страж DNS установки: проверка <check> нарушена: <причина>` |
| за срок старта нет ответа | `страж DNS установки: исчерпан срок старта <срок>, ответа нет по проверке <check>[, <check>…]` |

Пример формы: `страж DNS установки: проверка dmarc нарушена: dmarc_policy_none`. Срок
печатается в форме длительности, например `2m0s`.

## Перепроверка в работе

Раз в `KACHO_NOTIFY_DNS_RECHECK_INTERVAL` notify повторяет проверки одной попыткой. Итог
каждой проверки отражает метрика реплики:

| Метрика | Значение |
|---|---|
| `notify_mail_dns_posture{check="dkim"\|"spf"\|"dmarc"}` | `1` — проверка исправна, `0` — нарушена |

Если перепроверка нашла нарушение, метрика этой проверки падает в `0`, а в журнал пишется
строка WARN `перепроверка DNS установки: проверка <check> нарушена` с полями `check` и `reason`.
Отправка при этом **не останавливается**: остановка отрезала бы письма с кодами второго
фактора. Если ответа не было, значение метрики не меняется. Если нарушение возникло, когда
процесс уже работает, учтите: следующий старт с этим нарушением закончится отказом.

## Ручки

| Ручка (ключ values чарта) | Переменная | Границы (включительно) | Поставляемое значение |
|---|---|---|---|
| `dns.bootDeadline` | `KACHO_NOTIFY_DNS_BOOT_DEADLINE` | 10 с … 10 мин | `2m` |
| `dns.recheckInterval` | `KACHO_NOTIFY_DNS_RECHECK_INTERVAL` | 1 мин … 24 ч | `1h` |

Незаданная ручка — отказ старта с текстом `ручка не задана; умолчания у неё нет`. Значение вне
границы — отказ с текстом `значение <значение> вне границы [<нижняя>..<верхняя>]`. В обоих
случаях строка отказа начинается с имени ручки и переменной, например
`notify.dns.bootDeadline (KACHO_NOTIFY_DNS_BOOT_DEADLINE): …`.

Ручки, отключающей проверки, нет.

## Объект ключа DKIM

Закрытый ключ и селектор DKIM лежат в отдельном объекте Secret — не в секрете почты. В боевой
посадке объект создаёт оператор; чарт notify объекта не создаёт, а монтирует его томом в
каталог `/etc/kacho/notify/dkim`. Объект называет узел values:

| Ключ values | Что задаёт |
|---|---|
| `global.kacho.identity.smtp.dkim.secretName` | имя объекта |
| `global.kacho.identity.smtp.dkim.privateKeyKey` | ключ объекта с закрытым ключом |
| `global.kacho.identity.smtp.dkim.selectorKey` | ключ объекта с селектором |

Если notify рендерится, а поле узла пусто, рендер чарта отказывает с полным именем ключа.

Требования к содержимому:

- **закрытый ключ** — RSA не короче 2048 бит, PEM (`RSA PRIVATE KEY` или `PRIVATE KEY`);
- **селектор** — имя DNS из одной или нескольких меток через точку, например `mail` или
  `2026.mail`. Каждая метка — латинские буквы, цифры и дефис, без дефиса по краям, не длиннее
  63 символов; всё имя — не длиннее 253 символов. Значение — ровно имя, **без перевода строки
  в конце**: с ним селектор вне формы имени DNS.

Отказ загрузки называет ручку, имя ключа объекта и причину; содержимого ключа в тексте и в
журнале нет:

```text
notify отказывается стартовать:
  notify.dkim.keyFile (KACHO_NOTIFY_DKIM_KEY_FILE): ключ DKIM `<ключ объекта>`: <причина>
```

| Часть | Причины |
|---|---|
| ключ DKIM (`notify.dkim.keyFile`) | `не читается` · `нет в объекте` · `не RSA` · `короче 2048 бит` |
| селектор DKIM (`notify.dkim.selectorFile`) | `нет в объекте` · `пуст` · `вне формы имени DNS` |

## Смена ключа DKIM

Ключ меняется **новым селектором**. Запись прежнего селектора остаётся опубликованной, пока
notify на него опирается.

1. Выпустите новую пару RSA (не короче 2048 бит) и выберите новый селектор.
2. Опубликуйте TXT-запись нового селектора `<новый селектор>._domainkey.<домен From>` с
   открытым ключом новой пары. Дождитесь, пока запись начнёт отдаваться резолвером кластера.
3. Замените в объекте ключа DKIM закрытый ключ и селектор **одной правкой** объекта.
4. Дождитесь перехода. Обновлённый объект доходит до пода без перезапуска, а notify читает
   пару заново на каждой перепроверке, то есть не позже `KACHO_NOTIFY_DNS_RECHECK_INTERVAL`
   после обновления тома. Новая пара проходит те же проверки загрузки и проверку `dkim` по
   своей записи. Если обе прошли, notify переходит на новую пару; в журнале — строка
   `подпись перешла на селектор <новый селектор>`, метрика `dkim` = `1`. Каждая реплика
   переходит сама, поэтому смотрите журнал и метрику каждой.
5. Когда переход отметили все реплики, снимите запись прежнего селектора.

### Если записи нового селектора нет

Если в объекте уже новая пара, а её запись не опубликована (или не совпадает с ключом),
работающий процесс **остаётся на прежней паре**. Метрика `dkim` падает в `0`, в журнал
пишется одна строка WARN:

```text
пара DKIM в объекте сменилась и не прошла проверку dkim: <причина>; подпись остаётся на селекторе <прежний селектор>; перезапуск в этом состоянии остановит отправку: старт откажет по проверке dkim
```

**Перезапуск в этом состоянии остановит отправку.** При старте notify читает только ту пару,
что лежит в объекте, то есть новую, и проверка `dkim` по её записи не проходит — старт
отказывает (`dkim_missing`, если записи нет). Чтобы выйти из этого состояния, опубликуйте
запись нового селектора либо верните в объект прежнюю пару.

Если новая пара не прошла проверки загрузки (например, ключ короче 2048 бит), поведение то же:
процесс остаётся на прежней паре, метрика `dkim` = `0`, и в строке WARN вместо причины
проверки стоит текст отказа загрузки. Если том в момент чтения не читается, процесс остаётся
на прежней паре и пишет строку WARN `том DKIM: поколение не читается; подпись остаётся на
прежней паре`.
