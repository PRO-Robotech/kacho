# Развёртывание

kacho-compute — gRPC-сервис на Go с хранилищем PostgreSQL. Эта страница описывает, как поднять
сервис: локальный dev-стенд, отдельный запуск и порядок применения миграций. Полный список
параметров — [Конфигурация](/install/configuration).

## Компоненты

Для работы kacho-compute нужны:

| Компонент | Роль |
|---|---|
| PostgreSQL 16 | Хранилище схемы `kacho_compute` |
| kacho-iam | authz-Check, `ProjectService.Get`, регистрация owner-tuple |
| kacho-geo | валидация `zoneId` (`ZoneService.Get`) |
| kacho-vpc | валидация NIC-spec (при работе с сетевыми интерфейсами) |
| api-gateway | REST-проекция и маршрутизация операций (для tenant-клиентов) |

Peer-валидацию можно отключить в изолированных сценариях (`KACHO_COMPUTE_SKIP_PEER_VALIDATION=true`)
— тогда existence-check project/zone/vpc становится no-op (для unit/newman без поднятых peer'ов).

## Локальный dev-стенд

Самый быстрый путь — общий стенд платформы (каталог `deploy` того же
репозитория, kind + helm + Postgres). Соседнего репозитория стенда рядом с
деревом нет: команды запускаются **от корня репозитория**.

<CodeBlock language="bash">
  {dedent`
    make -C deploy dev-up                       # поднять стенд (все сервисы + Postgres)
    make -C deploy reload-svc SVC=compute       # пересобрать/перезапустить только compute
    make -C deploy logs-svc SVC=compute         # логи сервиса
    make -C deploy psql SVC=compute             # psql к базе kacho_compute
  `}
</CodeBlock>

После `make dev-up` пробросьте api-gateway на локальный порт (например `localhost:18080`) —
все REST-примеры документации используют этот адрес.

## Порты

| Порт | Listener | Назначение |
|---|---|---|
| `:9090` (env `KACHO_COMPUTE_GRPC_PORT`) | public gRPC | Tenant-API (Instance / MachineType) |
| `:9091` (env `KACHO_COMPUTE_INTERNAL_PORT`) | internal gRPC | `InternalMachineTypeService`, `InternalMachineTypeService` (mTLS) |
| metrics (env `KACHO_COMPUTE_METRICS_ADDR`) | HTTP | Prometheus-метрики, health-пробы |

## Миграции

Схема версионируется goose (встроена в бинарь через embed.FS). При старте сервиса миграции
применяются к базе `kacho_compute`; `0001_initial.sql` — squashed baseline. Применённые
миграции **не редактируются** — только новые, поэтому в истории рядом стоят и создание
таблицы, и её удаление: `0001` заводил в том числе таблицы блочного хранения и оси
размещения с их посевом, а `0011`, `0013`, `0021`, `0022` их сняли, когда владельцами стали
kacho-geo и kacho-storage. Каждое удаление проходит через манифест
(`internal/migrations/dropguard.json`), который называет таблицу, причину и ожидаемое число
строк: удаление, не совпавшее с заявленным, не проходит.

:::caution Проверяйте наличие объектов, а не только версию
При renumbering/hard-cut схемы `goose_db_version` может числить миграцию применённой, хотя
объекта в базе нет. После нетривиальных изменений схемы сверяйте **фактическое наличие**
таблиц/колонок (`to_regclass`), а не только `max(version_id)`.
:::

## Сборка образа документации

Документация (этот сайт) собирается отдельным multi-stage образом и отдаётся nginx:

<CodeBlock language="bash">
  {dedent`
    cd docs
    docker build -t kacho-compute-docs:dev .   # npm build → nginx (порт 8080)
  `}
</CodeBlock>

Helm-чарт документации — в `docs/deploy/` (`compute-docs`).

## Проверка работоспособности

После старта проверьте доступность через api-gateway (аутентифицированно — unauth-запрос
отсечёт authz до backend):

<CodeBlock language="bash">
  {dedent`
    curl -s http://localhost:18080/compute/v1/machineTypes -H 'Authorization: Bearer <JWT>'
  `}
</CodeBlock>

Ответ со списком типов машин подтверждает, что сервис поднят, база доступна и authz-цепочка
работает.

## Откат выкатки

Неудачная выкатка откатывается в **три шага, и порядок в них несущий**. Схему
возвращают ДО образа: down-миграция лежит в том образе, который её принёс, и
вернув образ первым, вы останетесь без файла, которым откатывать.

Отдельно про то, чего `helm rollback` не делает сам: миграции едут
initContainer'ом и прогоняются `up` **на каждом старте пода**, поэтому возврат
образа перекатывает под и снова накатывает схему до головы своей цепочки.
Возврат образа сам по себе схему не возвращает.

### Шаг 1. Решить, нужен ли откат СХЕМЫ

| что несла выкатка | нужен ли откат схемы |
|---|---|
| только образ, миграций нет | нет — сразу шаг 3 |
| миграции аддитивные (новая таблица, новая колонка) | как правило нет: прежний код их не читает, и это самый дешёвый путь |
| миграция несовместима с прежним кодом (переименование, сужение типа, снятие колонки) | да — шаг 2 |
| миграция снесла таблицу или колонку | схему вернуть можно, **данные — нет**; см. рамку ниже |

### Шаг 2. Откатить схему — образом, который эту миграцию несёт

```bash
# ДО helm rollback, пока в поде ещё НОВЫЙ образ: у него есть down-файл.
kubectl -n <namespace> exec deploy/<деплой kacho-compute> -- \
  /usr/local/bin/kacho-migrator status
kubectl -n <namespace> exec deploy/<деплой kacho-compute> -- \
  /usr/local/bin/kacho-migrator down --target <версия, до которой откатываем>
```

### Шаг 3. Вернуть образ

```bash
helm history <релиз>
helm rollback <релиз> <ревизия>
```

:::danger `down` возвращает форму, а не данные
Down-миграция воссоздаёт схему **пустой**. Строки, которые снёс `DROP`, она не
возвращает: «восстановимо» про снос означает «восстановима схема». Единственный
путь назад для снесённых строк — резервная копия базы.

Продукт защищает это на своей стороне: накат считает живые строки в каждой
таблице, которую уронит ещё не применённая миграция, и **отказывает**, пока снос
не одобрен явно — переменной `KACHO_MIGRATOR_DROP_APPROVED` с именем конкретного
сноса. Отказ на выкатке стоит одной выкатки; восстановление из копии — сильно
дороже, и узнаёте вы о нужде в нём уже после.
:::

### Чем проверить, что откат состоялся

Проверять надо **три** вещи, и «под Ready» само по себе ни одной из них не
доказывает:

| что | чем |
|---|---|
| ревизия релиза вернулась | `helm history <релиз>` — последняя запись со статусом `deployed` |
| под работает нужным образом | `kubectl -n <namespace> get pod -l app=<деплой kacho-compute> -o jsonpath='{..image}'` |
| схема на ожидаемой версии | `kacho-migrator status` — головная применённая версия |
| зависимости сервиса живы | `readinessProbe` спрашивает `/readyz`, поэтому `kubectl get pods` показывает готовность **по зависимостям**, а не по открытому сокету: под в `0/1` — это отказ зависимости, а не «ещё поднимается» |
