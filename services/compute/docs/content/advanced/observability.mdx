# Наблюдаемость

kacho-compute инструментирован для эксплуатации в кластере: метрики, health-пробы,
структурированные логи и наблюдаемость асинхронных операций. Эта страница — обзор того, что
доступно оператору.

## Метрики

Сервис экспонирует метрики в формате Prometheus на cluster-internal diagnostic-листенере
(`KACHO_COMPUTE_METRICS_ADDR`, по умолчанию `:9095`). Реестр **собственный**, не глобальный
по умолчанию, поэтому набор семейств известен точно — вот он целиком, с префиксом
`kacho_compute_`:

| Семейство | Что показывает |
|---|---|
| `build_info` | версия и сборка процесса |
| `dependency_up` | доступность каждой зависимости (та же оценка, что у health-проб) |
| `lro_workers_active` | сколько воркеров операций занято прямо сейчас |
| `operations_terminal_write_retries_total` · `operations_terminal_write_failures_total` | повторы и отказы при записи терминального состояния операции |
| `operations_orphans_recovered_total` | сколько осиротевших операций разрешено |
| `operations_reconcile_runs_total` · `operations_reconcile_errors_total` | проходы и ошибки реконсайлера операций |
| `outbox_backlog_depth` · `outbox_oldest_pending_age_seconds` | глубина очереди и возраст самой старой недоставленной строки |
| `outbox_poisoned_current` · `outbox_poisoned_total` | отравленные строки: сколько сейчас и сколько было |
| `outbox_backlog_depth_by_direction` · `outbox_oldest_pending_age_seconds_by_direction` · `outbox_delivered_by_direction` | то же в разрезе направления доставки |

:::note Чего в этом наборе НЕТ
Метрик по gRPC-методам (RPS, латентность, распределение кодов), по пулу соединений и по
числу активных потоков подписки сервис **не публикует**. Прежняя редакция этой страницы их
перечисляла; ни одно такое семейство в реестре не заведено. Латентность и коды смотрите на
краю либо в логах.

Потолок одновременных потоков подписки при этом ЕСТЬ и он отказывает явно
(`RESOURCE_EXHAUSTED`), а не копит очередь, — но сколько потоков занято сейчас,
снаружи не видно. Это остаток, а не решение.
:::

## Health / readiness

Health-пробы (`internal/observability/health`) отражают доступность зависимостей — та же
оценка, что публикует `dependency_up`. Отдельно работает boot-gate
`KACHO_COMPUTE_REQUIRE_IAM`: пока связанный с kaname дренер регистраций не поднялся,
сервис отвечает **NotReady** и **отказывает мутирующему Create**. Это не падение процесса
при старте: сервис жив, читает и не притворяется готовым — тогда как отказ старта лишил бы
оператора и диагностики.

## Логи

Логи структурированные (slog); в проде текст ошибок БД наружу **не** выводится в API (клиент
получает фиксированный `INTERNAL "internal database error"`), но в логах сохраняется контекст
для диагностики. Не логируйте секреты.

## Наблюдаемость операций

Асинхронные операции наблюдаемы через API: `ListOperations` по ресурсу показывает историю LRO,
а `OperationService.Get` — текущее состояние. Для диагностики «зависших» Create/Start/AttachDisk
это первичный инструмент — до анализа метрик и логов.

:::note «Задеплоено» ≠ «работает»
Rollout, Running-поды и применённые миграции — не доказательство работоспособности. Ряд классов
проблем (потеря principal в worker'е, расхождение миграций, недоступность peer-канала) видны
только на живом стеке через end-to-end проверку (запрос через api-gateway аутентифицированно).
Проверяйте реальным запросом, а не только статусом подов.
:::

## Диагностика частых ситуаций

| Симптом | Куда смотреть |
|---|---|
| Мутация падает `UNAVAILABLE` | Доступность peer-сервиса (iam/vpc/geo) на request-path |
| Ресурс не виден в `List` сразу после Create | Пропагация authz-tuple (~секунды) — поллинг, не мгновенный assert |
| Операция «зависла» `done: false` | `ListOperations` ресурса; логи worker'а; состояние drainer outbox |
| `INTERNAL "internal database error"` | Логи (текст SQL там); наличие объектов схемы (`to_regclass`) |
