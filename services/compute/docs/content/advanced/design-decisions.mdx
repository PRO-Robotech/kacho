# Особенности дизайна Kachō Compute

Kachō Compute спроектирован под задачу в чистой форме — это собственный продукт со своими
конвенциями. Ниже — осознанные дизайн-решения и объяснение «почему так»: они помогают понять
поведение API там, где оно может показаться неочевидным.

## Решения и обоснования

| Решение | Почему так |
|---|---|
| **Control-plane без data plane** | Сервис управляет намерением и состоянием (API, валидация, жизненный цикл, authz). Реального гипервизора нет: статус переходит детерминированной state-машиной, содержимое тома не материализуется, «загрузка» образа мгновенна, вывод serial-порта синтетический. Это позволяет сосредоточить контракт на управлении, отделив его от исполнения. |
| **Все мутации — асинхронные (`Operation`)** | Единый устойчивый контракт: клиент не блокируется, повторный опрос идемпотентен, запись об операции переживает рестарт. Синхронный возврат ресурса из мутации намеренно исключён. |
| **Instance создаётся без авто-NIC** | Жизненный цикл инстанса и сетевая привязка разделены: `Create` не провижинит сетевые интерфейсы, они подключаются отдельным действием `AttachNetworkInterface`. Это делает управление сетью инстанса явным и независимым, а сам NIC — first-class ресурсом домена kacho-vpc. |
| **Блочное хранение — во внешнем домене** | Volume / Image / Snapshot / DiskType принадлежат kacho-storage. Compute их не дублирует: том создаётся у владельца и присоединяется сюда по `volumeId`, а сама связь хранится у storage. Один владелец на тип ресурса — иначе два сервиса отвечают за одну сущность и расходятся. |
| **Attach инициирует compute, а проверяет storage** | Запрос на присоединение несёт самоописывающийся набор (инстанс, его зона, проект), поэтому storage проверяет свою строку одним атомарным сравнением-и-записью и **никогда не зовёт compute обратно**. Так ребро остаётся однонаправленным, и цикла между сервисами не возникает по построению. |
| **Размер — только через каталог типов машин** | Вместо свободной пары «платформа + ресурсы» инстанс ссылается на запись каталога (`machineTypeId`), а действующие ресурсы выводит сервер. Свободные числа позволяли собрать конфигурацию, которую платформа не обслуживает; каталог делает набор размеров закрытым и наблюдаемым. |
| **MachineType — read-only на публичном API** | Каталог типов машин задаёт администратор платформы; tenant только читает. Управление каталогом — admin-функция на internal-порту (`InternalMachineTypeService`), не на публичной поверхности. |
| **Geography (Region/Zone) — во внешнем домене** | Зоны и регионы — топологический leaf-домен kacho-geo. Compute не владеет ими, а валидирует `zoneId` вызовом `ZoneService.Get`. Это убирает дублирование топологии между сервисами. |
| **Зона инстанса и зона его подсети совпадают** | Подсеть каждого интерфейса обязана быть в зоне инстанса, и проверяется это **на пути запроса**, а не в отложенном запуске. Исключение — региональная (anycast) подсеть: зоны она не несёт, поэтому из зональной проверки исключена по построению, а региональная когерентность остаётся. |
| **Идентификаторы — дефисной формы, неизменяемые** | `ins-…` и `mt-…`: id присваивается на Create и живёт с ресурсом до конца — операции смены id не существует. В URL и ссылки попадает только он, а `name` остаётся косметическим и меняется свободно. Иначе переименование ломало бы ссылки и гранты. Операции сохраняют legacy-форму `epd`, по которой api-gateway их маршрутизирует. |
| **Placement скрыт из публичного Instance** | Привязка инстанса к физическому хосту/host-группе — инфра-чувствительные данные (разведка для lateral movement). Они исключены из публичной проекции `Instance` и доступны, при необходимости, только на internal-проекции. |

## Имя ресурса — одна форма на всю платформу

Имена ресурсов Compute подчиняются **общей** форме платформы — DNS label по RFC 1123,
`^[a-z0-9]([-a-z0-9]{0,61}[a-z0-9])?$`: строчные латинские буквы, цифры и дефис, первый и
последний знак — буква или цифра, длина 1..63. Подчёркивание не допускается; цифра первым
знаком допускается.

Здесь стояло, что форма Compute «осознанно строже, чем permissive-имена в некоторых других
доменах». Утверждение о РАЗЛИЧИИ доменов пережило своё основание: до #715 валидаторов имени
было четыре, и они расходились по регистру, подчёркиванию и пустой строке; с тех пор
валидатор в дереве один (`pkg/validate/nameform`), а форма продублирована ограничением
таблицы в пяти схемах. Соглашение об именовании принимается один раз и переносится между
доменами без поправок.

Форма взята внешним стандартом намеренно: имя, годное как DNS label, годится сегментом
адреса, меткой в средствах наблюдения и именем в конфигурации развёртывания — без
экранирования и без второго правила «а здесь можно иначе».

## Снятое с контракта — снято, а не оставлено «на будущее»

Поле запроса, на которое сервис не смотрит, здесь не держат. Легаси-вход создания инстанса
(пара «платформа + ресурсы», inline-спека загрузочного диска, свободная сортировка списка)
**удалён из контракта**, а его номера и имена зарезервированы, чтобы не быть переиспользованными
под другим смыслом.

Причина в том, что «принять и не применить» хуже отказа: вызывающий получает успех и считает
свой параметр учтённым. Именно так вела себя inline-спека диска — обработчик читал только
идентификатор тома и молча отбрасывал остальное. Отказ виден сразу, а несделанное — только по
последствиям.

:::note Тексты ошибок — часть контракта
Формулировки ошибок (`"Instance is not running"`, `"Instance is not running or stopped"`,
`"machine type %s not found"`, `"machine type %s is retired and cannot be used on Create"`)
стабильны и являются частью контракта — клиенты вправе на них полагаться. Меняются только
осознанно, через тикет.
:::
