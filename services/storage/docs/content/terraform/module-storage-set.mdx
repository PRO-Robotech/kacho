# Модуль `storage-set`

Модуль описывает набор блочного хранения целиком: тома, снимки с них и образы из этих
снимков или томов. Это типовая единица — по отдельности их заводят редко, потому что
снимок без тома снять не с чего, а образ без источника край не создаёт вовсе.

## Использование

```hcl
module "app_storage" {
  source = "github.com/PRO-Robotech/kacho//terraform/modules/storage-set"

  project_id = var.project_id
  region_id  = "ru-central1"
  labels     = { origin = "terraform" }

  volumes = {
    "app-data-a" = {
      zone_id      = "ru-central1-a"
      disk_type_id = "network-ssd"
      size_bytes   = 21474836480
    }
    "app-data-b" = {
      zone_id      = "ru-central1-b"
      disk_type_id = "network-ssd"
      size_bytes   = 21474836480
      labels       = { tier = "hot" }
    }
  }

  snapshots = {
    "app-data-daily" = { source_volume_key = "app-data-a" }
  }

  images = {
    "app-golden" = { source_snapshot_key = "app-data-daily" }
  }
}
```

Модуль требует OpenTofu/Terraform **1.9 и выше**: его проверки входа ссылаются на другую
переменную (ключ снимка обязан быть ключом карты томов), а межпеременные проверки
появились именно там.

## Что модуль решает за вас

### Внутри набора ссылаются КЛЮЧОМ, за его пределы — идентификатором

Снимок называет свой том ключом карты `volumes`, образ называет снимок или том ключом их
карт. Причина проста: идентификатор присваивает край при создании, поэтому у ресурса,
которого ещё нет, его нет и у вызывающего. Ключ модуль разрешает в идентификатор сам —
и тем строит граф зависимостей.

Внешний источник (`source_snapshot_id`, `source_image_id` у тома) — наоборот,
идентификатор: такой ресурс уже существует.

### Том из снимка ЭТОГО ЖЕ набора заводится вторым экземпляром модуля

Ссылка тома на снимок замкнула бы граф блоков — снимок уже ссылается на том, — и
конфигурация была бы отвергнута циклом ещё до обращения к краю. Поэтому у тома нет поля
«снимок этого набора»; идентификатор отдан выходом `snapshot_ids`, и второй экземпляр
модуля принимает его как `source_snapshot_id`.

### Регион задаётся один раз, зона — у каждого тома

Регион — общий: образ здесь региональная проекция томов того же набора, и расхождение
регионов между двумя образами одного набора не задумано. Зона, наоборот, задаётся у
каждого тома: разнесение томов по зонам — это и есть смысл зональной посадки, и набор
одного проекта законно живёт в нескольких зонах одного региона.

### Порядок сноса держится ССЫЛКАМИ, и больше ничем

Образы → снимки → тома. Обоснование у этого порядка **обратное ожидаемому**: край его
не держит. Ссылки снимка на том и образа на снимок или том объявлены `ON DELETE SET NULL`,
поэтому неверный порядок ничем не отвергается — край молча обнуляет источник, и
происхождение теряется без единого сообщения.

:::warning Не полагайтесь на «неверный порядок даст ошибку»
Ни один из трёх ресурсов набора не защищён от сноса своим потомком. Порядок выражен
графом ссылок и держится только им — поэтому в модуле снимок ссылается на `.id` тома, а
не на переменную с тем же значением.
:::

## Переменные

| Имя | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `project_id` | `string` | — | Проект-владелец всех ресурсов набора. |
| `region_id` | `string` | — | Регион **образов** набора. |
| `labels` | `map(string)` | `{}` | Метки на все ресурсы; метка ресурса сильнее общей. |
| `volumes` | `map(object)` | `{}` | Тома; ключ — имя тома в проекте. |
| `snapshots` | `map(object)` | `{}` | Снимки; ключ — имя снимка, `source_volume_key` — ключ карты `volumes`. |
| `images` | `map(object)` | `{}` | Образы; ключ — имя образа, источник — ровно один из `source_snapshot_key` и `source_volume_key`. |

### Запись тома

| Поле | Обязательно | Назначение |
|---|---|---|
| `zone_id` | да | Зона тома. Неизменяема: смена пересоздаёт том, а с ним пропадают данные. |
| `size_bytes` | да | Размер в БАЙТАХ, строго больше нуля. |
| `disk_type_id` | да | Позиция справочника типов дисков. |
| `block_size` | нет | Размер блока; не задан — край подставляет `4096`. |
| `source_snapshot_id` · `source_image_id` | нет | ВНЕШНИЙ источник, взаимоисключающи. |
| `description` · `labels` | нет | Описание и метки тома. |

`size_bytes` и `disk_type_id` обязательны **у каждого тома, включая том из снимка и том из
образа**: край не выводит их из источника и отвергает создание синхронно. У тома из образа
размер обязан быть вдобавок не меньше `minDiskBytes` этого образа — величину знает только
край, поэтому модуль её не сверяет и не подставляет.

Умолчания у размера нет намеренно: том нельзя уменьшить, поэтому подставленное за
вызывающего значение исправляется только пересозданием, то есть потерей данных.

## Проверки входа

Все они срабатывают на `plan`, до обращения к краю, и называют **виновные ключи**:

- у тома заданы оба источника сразу;
- у тома не задан `size_bytes` — в том числе у тома с источником;
- у тома не задан `disk_type_id`;
- `size_bytes` не положителен;
- снимок ссылается на ключ, которого нет в `volumes` (отказ перечисляет известные ключи);
- у образа задано не ровно одно из `source_snapshot_key` и `source_volume_key`;
- образ ссылается на ключ, которого нет в `snapshots` или в `volumes`.

Обязательность выражена **проверками**, а не обязательными атрибутами типа объекта, и это
не стилистика: пропуск обязательного атрибута край HCL сообщает ошибкой, которая ни к
какой переменной не приписана, поэтому отрицательной пробы на неё не написать вовсе.

## Когерентность размещения модуль НЕ проверяет — и не может

Правило, которое обязан соблюсти вызывающий: зона каждого тома, из которого — прямо или
через снимок — делается образ, обязана принадлежать региону `region_id`.

Проверить это на стороне Terraform нечем: соответствие зон регионам знает только край
(справочник geo), а выводить регион разбором имени зоны запрещено — имена зон и регионов
произвольны, между ними нет гарантированного отношения, и такая проверка молча проходила
бы всегда, выглядя исполненной.

:::note Отказ при несогласованном размещении образа выглядит как «не найдено»
Край проверяет когерентность источника **внутри самой записи**, то есть уже в асинхронной
операции, и отвечает `Snapshot S not found` либо `Volume V not found` — тем же текстом,
что и на источник из чужого проекта. Различимый ответ выдавал бы существование чужих
ресурсов. У тома иначе: там причина называется прямо (`Volume and Image must be in the
same region`, `Volume and Snapshot must be in the same zone`), потому что источник своего
проекта вызывающему уже виден и скрывать нечего.
:::

Внешнего источника у образа нет намеренно: образ из чужого тома завёл бы в набор источник
в неизвестном регионе, и общий `region_id` перестал бы быть единственной опорой правила.
Такой образ заводится ресурсом рядом с модулем, где его регион виден вызывающему целиком.

## Выходы

| Имя | Что это |
|---|---|
| `volume_ids` · `snapshot_ids` · `image_ids` | Идентификаторы по ключам входных карт. |
| `volumes` | Том целиком: идентификатор, **зона** и состояние. |
| `snapshots` | Снимок целиком: идентификатор, разрешённый идентификатор тома-источника и состояние. |
| `images` | Образ целиком: идентификатор, **регион** и состояние. |

Зона у тома и регион у образа выведены рядом с идентификатором намеренно: это те самые
входы правила когерентности, которые вызывающему придётся сверять самому, а держать их в
голове после `apply` не на чем.

`snapshot_ids` выведены не только для отчётности — это тот идентификатор, который второй
экземпляр модуля получит как `source_snapshot_id` тома.

:::tip Смотрите на `status`
Снимок существует раньше, чем становится пригоден как источник, и `status` — единственное
место, где эта разница видна без обращения к краю.
:::

## Чем проверяется сам модуль

У модуля есть пробы: `tests/wiring.tftest.hcl`, гоняются командой `tofu test` из каталога
модуля. Провайдер в них подменён (`mock_provider`), то есть край не участвует — падение
означает ошибку в модуле, а не состояние стенда.

Проб **16**, из них **10** отрицательных. Они закрепляют две вещи: **связывание** (снимок
ссылается на том по идентификатору, ключ образа резолвится в нужный источник, регион общий
у всех образов, зона своя у каждого тома, метки ресурса накладываются поверх общих,
внешний источник доезжает до ресурса) и **отвержение** негодного входа — все семь условий
из раздела выше. Второе не менее важно первого: без отрицаний положительные пробы зеленели
бы и на модуле, принимающем что угодно.

Конвейер требует пробы от КАЖДОГО модуля и падает на модуле без них.
