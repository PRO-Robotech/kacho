# Модель данных

Сервис владеет схемой `kacho_storage` в собственной базе. Общих баз между сервисами нет:
каждый владеет своей, и целостность через границу выражается вызовом владельца, а не
внешним ключом.

## Таблицы

| Таблица | Роль |
|---|---|
| `disk_types` | Классы диска — продуктовая политика. Идентификатор — slug, назначает администратор при регистрации |
| `storage_backends` | Реестр бэкендов: чем исполняется хранение и в каких зонах |
| `disk_type_bindings` | Неизменяемые ревизии политики для пары «класс, зона» |
| `volumes` | Тома. Зональные |
| `snapshots` | Снимки томов. Несут собственную зону, переживают исходный том |
| `images` | Образы. Региональные (anycast) |
| `volume_attachments` | Привязки тома к машине — источник истины |
| `operations` | Долгие операции (общая таблица платформы) |
| `fga_register_outbox` | Очередь регистрации владельца ресурса в модели прав |

## Политика фиксируется ссылкой на неизменяемую строку

Класс диска изменяем: администратор правит имя, зоны, границы. Ресурс при этом ссылается
не на класс, а на **ревизию привязки** — строку, которая не меняется никогда.

| Что | Где живёт | Меняется |
|---|---|---|
| Продуктовая политика (ярус, состояние обращения, границы) | `disk_types` | да, правкой справочника |
| Чем и на каких условиях класс исполняется в зоне | `disk_type_bindings` | **нет**: новая ревизия, прежняя вытесняется |
| Чем именно исполняется хранение и где | `storage_backends` | да, но бэкенд с ревизиями не удаляется |

**Отсутствие обновления и есть механизм.** Том хранит `binding_id`, и правка справочника
физически не может задним числом изменить его свойства: цель ссылки неизменяема by
construction, поэтому джойн к ней не может «уехать». Ссылка на неизменяемую строку
равносильна копии политики, но нормализована.

«Ровно одна действующая ревизия на пару (класс, зона)» держится **частичным уникальным
индексом** `(disk_type_id, zone_id) WHERE status = 'ACTIVE'`, а не проверкой «прочитал →
записал»: две конкурентные регистрации иначе обе прошли бы чтение и обе записали.

Способности бэкенда живут на ревизии, а не на классе: умеет ли он снимки, зависит ли клон
от родителя, есть ли корзина и с каким сроком — это свойства исполнителя, а не продуктовой
политики. Публичный класс **выводит** способности пересечением по своим действующим
ревизиям, консервативно: класс предлагается в нескольких зонах, а зоны могут обслуживаться
разными бэкендами.

## Желаемое и наблюдаемое — две колонки, а не одна

У тома, снимка и образа состояние разложено на две величины:

| Колонка | Что означает |
|---|---|
| `state` | **Желаемое**: что мы заказали (`CREATING` · `READY` · `DELETING` · `ERROR`) |
| `observed_state` | **Наблюдённое**: что сверщик увидел у бэкенда (`ABSENT` · `READY` · `ERROR` · `UNKNOWN`) |
| `observed_at` | Когда смотрел. Пусто — не смотрел ни разу |
| `status_reason` | Чем закончилась последняя попытка; закрытый словарь наших полос |
| `binding_id` | Ревизия политики, под которой ресурс **лежит сейчас** |
| `desired_binding_id` | Ревизия, на которую его переводят. Назначена и отлична от `binding_id` — идёт переезд |

Свести их в одну колонку значило бы сделать расхождение **невидимым by construction**.
Пока величины две, дрейф между нашей строкой и хранилищем находим — и находит его частичный
индекс расхождения `WHERE state <> observed_state`, который и есть рабочий список сверщика.
Это не очередь: очередь пришлось бы поддерживать в согласии с реальностью, а индекс
выводится из неё.

Потребление (`used_bytes`) хранится **обнуляемой** колонкой: `NULL` означает «бэкенд не
сообщил», и это не ноль. Ноль на этом месте был бы утверждением «том пуст» — правдоподобной
ложью, по которой считают стоимость.

## Ссылки внутри базы и через границу

Различие принципиальное, и оно видно прямо в схеме.

**Внутри базы** — настоящие внешние ключи с явным поведением на удаление:

| Ссылка | Поведение | Почему так |
|---|---|---|
| `volumes.disk_type_id → disk_types` | `RESTRICT` | Класс, которым пользуются тома, удалить нельзя |
| `volumes.binding_id → disk_type_bindings` | `RESTRICT` | Ревизия живёт, пока на неё ссылаются |
| `disk_type_bindings.disk_type_id → disk_types` | `RESTRICT` | Класс с ревизиями не удаляется |
| `disk_type_bindings.backend_id → storage_backends` | `RESTRICT` | Бэкенд с привязками не удаляется — вывод из обращения это `DRAINING` |
| `volume_attachments.volume_id → volumes` | `RESTRICT` | Привязанный том не удаляется |
| `volumes.source_snapshot_id → snapshots` | `SET NULL` | Происхождение, а не живая зависимость |
| `volumes.source_image_id → images` | `SET NULL` | Удаление образа стирает родословную, но не данные тома |
| `snapshots.source_volume_id → volumes` | `SET NULL` | Снимок переживает том, с которого снят |
| `images.source_snapshot_id → snapshots` | `SET NULL` | Происхождение |
| `images.source_volume_id → volumes` | `SET NULL` | Происхождение |

Разница между `RESTRICT` и `SET NULL` здесь смысловая: `RESTRICT` стоит там, где ссылка
означает **использование** (удалять нельзя, пока пользуются), `SET NULL` — там, где она
означает **происхождение** (источник можно удалить, данные остаются, теряется только
запись о родословной).

**Через границу сервиса** — TEXT без внешнего ключа: `project_id` (kaname), `zone_id`
и `region_id` (kacho-geo), `instance_id` (kacho-compute). Существование проверяется
вызовом владельца на пути запроса; исчезнувшую ссылку сервис переживает мягко.

:::info Взаимная ссылка томов и снимков
`volumes.source_snapshot_id → snapshots` и `snapshots.source_volume_id → volumes`
ссылаются друг на друга. В миграции это развязано порядком: сначала создаются обе таблицы
**без** этих двух ключей, затем оба добавляются `ALTER TABLE`. Это единственный корректный
порядок для взаимной ссылки без отложенной проверки — на момент добавления каждая таблица
уже существует.
:::

## Статус выводится, а не хранится

Значений `AVAILABLE`, `IN_USE` и `MIGRATING` в колонке `state` **нет** — все три
выводятся, и у каждого свой производитель:

| Строка в базе | Что видит клиент |
|---|---|
| `desired_binding_id` назначен и отличается от `binding_id` | `MIGRATING` |
| `state='READY'`, привязки нет | `AVAILABLE` |
| `state='READY'`, привязка есть | `IN_USE` |
| `state='CREATING' \| 'DELETING' \| 'ERROR'` | как есть |

Хранить «привязан ли том» отдельной колонкой значило бы завести второй источник истины о
том же факте. Два источника расходятся — вопрос лишь когда. Здесь их один.

По той же причине у переезда на другой класс **нет** собственного значения `state`: он
выводится из расхождения ревизий — желаемая назначена, действующая ещё прежняя. Отсюда
требование к схеме: расхождение ревизий обязано попадать в рабочий список сверщика, и
частичный индекс расхождения ловит **обе** оси — и `state <> observed_state`, и
`desired_binding_id IS DISTINCT FROM binding_id`. Ловил бы он только первую — переезд
остался бы невидим, том навис бы между классами, а сверщик исправно рапортовал бы, что
расхождений нет.

Сколько привязок допускает том, решает **способность его ревизии** (`cap_multi_attach`), а
не форма первичного ключа: ключ таблицы привязок составной — `(volume_id, instance_id)`, а
предикат «свободен либо уже наш» читается прямо во вставке. Прежде запрет второй привязки
держал сам ключ, и множественная привязка была бы невозможна by construction, каким бы
способным ни оказался бэкенд.

## Проверки значений

Правила полей выражены `CHECK`-констрейнтами, то есть держатся независимо от того, каким
путём пришла запись:

- имя — `^[a-z0-9]([-a-z0-9]{0,61}[a-z0-9])?$` (DNS label по RFC 1123; цифра первым
  знаком допустима). Пустого имени в таблице не бывает: пустой вход создания сервис
  заменяет именем, производным от `id`, до вставки;
- описание — не длиннее 256;
- метки — не более 64 пар, ключ по своему шаблону, значение до 63 байт (проверяется
  функцией схемы);
- размер тома `> 0`;
- ярус класса — из закрытого словаря; состояние обращения — из закрытого перечня;
- границы размера класса неотрицательны, упорядочены и кратны шагу;
- желаемое и наблюдаемое состояния — каждое из своего закрытого перечня;
- причина состояния — из закрытого словаря наших полос;
- род и полоса действия бэкенда — из закрытых перечней; координата и ссылка на учётные
  данные непусты;
- формат образа — из закрытого перечня;
- у образа источник — снимок **либо** том, но не оба.

## Миграции

Схема ведётся goose-миграциями в `internal/migrations`. Опорные:

| Миграция | Что вносит |
|---|---|
| `0001_initial` | Схема и служебное |
| `0002_operations` | Таблица долгих операций |
| `0003_storage_domain` | Тома, снимки, привязки, каталог классов |
| `0006_fga_register_outbox` | Очередь регистрации владельца |
| `0007_image_and_volume_source_image` | Образы и происхождение тома от образа |
| `0008`–`0010` | Индексы и обслуживание очереди регистрации |
| `0011_drop_storage_outbox` | Снятие неиспользуемой очереди |
| `0013_tenant_cursor_indexes` | Индексы под курсорную выдачу страниц |
| `0014_snapshot_zone_anchor` | Собственный якорь размещения снимка |
| `0015_storage_backends_and_bindings` | Реестр бэкендов и неизменяемые ревизии привязки |
| `0016_disk_type_policy` | Снятие посева каталога, состояние обращения, границы, словарь яруса |
| `0017_resource_binding_and_observed` | Ссылка на ревизию, имя объекта у бэкенда, наблюдаемые колонки |
| `0018_volume_attachments_multi` | Составной первичный ключ привязок |
| `0019_snapshot_image_backend_namespace` | Собственное пространство арендатора у снимка и образа — координата хранится у того, кому принадлежит, а не добирается через источник |
| `0020_volume_migration_drift` | Расхождение ревизий попадает в рабочий список сверщика: без этого переезд на другой класс остался бы невидим |
| `0021_copy_provenance` | Происхождение копии снимка и образа — «скопирован с» выразить прежними колонками было нечем |
| `0022_backend_object_uniq_excludes_unassigned` | Предикат уникальности имени объекта у бэкенда исключает **неприсвоенное** имя |

Применённая миграция не редактируется — изменение вносится новой. Поэтому и снятие посева,
и смена первичного ключа пришли **новыми** миграциями, а не правкой прежних.

:::note `0022` — форма проверки без содержания, и цена была не косметическая
`0017` объявил уникальность имени объекта у бэкенда предикатом «имя задано», но колонки
объявлены непустыми со значением по умолчанию — пустой строкой. Предикат оказался
**тождественно истинным**, поэтому пустая строка (законное состояние «имя ещё не
присвоено») становилась уникальной на всю таблицу: **второй** ресурс без присвоенного
имени падал уникальностью.

Развёртывание без префикса установки не смогло бы завести больше одного тома. Проверка
при этом выглядела исполненной — она просто не различала того, ради чего писалась.
:::

:::note Снятие посева — условное, и это не осторожность, а необходимость
Миграция `0016` удаляет заранее заготовленные позиции каталога **только те, на которые не
ссылается ни один том**: `AND NOT EXISTS (… volumes …)`. Безусловный `DELETE` упёрся бы во
внешний ключ `RESTRICT` и уронил бы старт сервиса на любой установке, где такой том успел
появиться.

Там же приводится к закрытому словарю прежний ярус: он был свободной строкой, и значения
переводятся нормализующим `UPDATE` в **той же** миграции, до наложения `CHECK`. Иначе
ограничение не наложилось бы на существующие строки.
:::

## Каталог классов диска

Каталог **не наполняется миграцией**. Класс регистрирует администратор через внутренний
листенер по факту услуги: пока класс не заведён и не привязан к бэкенду в конкретной зоне,
том на нём не создаётся.

Пустой каталог — законное состояние свежей установки, а не признак неполной поставки.
Поле `zone_ids` ограничивает доступность класса зонами; пустой список означает, что
ограничения нет, но действующая ревизия привязки на зону тома нужна в любом случае.
