# Модель данных

Сервис владеет схемой `kacho_storage` в собственной базе. Общих баз между сервисами нет:
каждый владеет своей, и целостность через границу выражается вызовом владельца, а не
внешним ключом.

## Таблицы

| Таблица | Роль |
|---|---|
| `disk_types` | Каталог типов диска. Идентификатор — читаемый slug, назначает администратор |
| `volumes` | Тома. Зональные |
| `snapshots` | Снимки томов. Переживают исходный том |
| `images` | Образы. Региональные (anycast) |
| `volume_attachments` | Привязки тома к машине — источник истины |
| `operations` | Долгие операции (общая таблица платформы) |
| `fga_register_outbox` | Очередь регистрации владельца ресурса в модели прав |

## Ссылки внутри базы и через границу

Различие принципиальное, и оно видно прямо в схеме.

**Внутри базы** — настоящие внешние ключи с явным поведением на удаление:

| Ссылка | Поведение | Почему так |
|---|---|---|
| `volumes.disk_type_id → disk_types` | `RESTRICT` | Тип, которым пользуются тома, удалить нельзя |
| `volume_attachments.volume_id → volumes` | `RESTRICT` | Привязанный том не удаляется |
| `volumes.source_snapshot_id → snapshots` | `SET NULL` | Происхождение, а не живая зависимость |
| `volumes.source_image_id → images` | `SET NULL` | Удаление образа стирает родословную, но не данные тома |
| `snapshots.source_volume_id → volumes` | `SET NULL` | Снимок переживает том, с которого снят |
| `images.source_snapshot_id → snapshots` | `SET NULL` | Происхождение |
| `images.source_volume_id → volumes` | `SET NULL` | Происхождение |

Разница между `RESTRICT` и `SET NULL` здесь смысловая: `RESTRICT` стоит там, где ссылка
означает **использование** (удалять нельзя, пока пользуются), `SET NULL` — там, где она
означает **происхождение** (источник можно удалить, данные остаются, теряется только
запись о родословной).

**Через границу сервиса** — TEXT без внешнего ключа: `project_id` (kacho-iam), `zone_id`
и `region_id` (kacho-geo), `instance_id` (kacho-compute). Существование проверяется
вызовом владельца на пути запроса; исчезнувшую ссылку сервис переживает мягко.

:::info Взаимная ссылка томов и снимков
`volumes.source_snapshot_id → snapshots` и `snapshots.source_volume_id → volumes`
ссылаются друг на друга. В миграции это развязано порядком: сначала создаются обе таблицы
**без** этих двух ключей, затем оба добавляются `ALTER TABLE`. Это единственный корректный
порядок для взаимной ссылки без отложенной проверки — на момент добавления каждая таблица
уже существует.
:::

## Статус выводится, а не хранится

У тома в базе лежит колонка `state` со значениями `CREATING`, `READY`, `DELETING`,
`ERROR`. Значений `AVAILABLE` и `IN_USE` в ней **нет** — они выводятся из наличия строки
привязки:

| Строка в базе | Что видит клиент |
|---|---|
| `state='READY'`, привязки нет | `AVAILABLE` |
| `state='READY'`, привязка есть | `IN_USE` |
| `state='CREATING' \| 'DELETING' \| 'ERROR'` | как есть |

Хранить «привязан ли том» отдельной колонкой значило бы завести второй источник истины о
том же факте. Два источника расходятся — вопрос лишь когда. Здесь их один.

## Проверки значений

Правила полей выражены `CHECK`-констрейнтами, то есть держатся независимо от того, каким
путём пришла запись:

- имя — `^[a-z]([-a-z0-9]{0,61}[a-z0-9])?$` либо пусто;
- описание — не длиннее 256;
- метки — не более 64 пар, ключ по своему шаблону, значение до 63 байт (проверяется
  функцией схемы);
- размер тома `> 0`, размер блока `> 0`;
- состояние — из закрытого перечня;
- формат образа — из закрытого перечня;
- у образа источник — снимок **либо** том, но не оба.

## Миграции

Схема ведётся goose-миграциями в `internal/migrations`. Опорные:

| Миграция | Что вносит |
|---|---|
| `0001_initial` | Схема и служебное |
| `0002_operations` | Таблица долгих операций |
| `0003_storage_domain` | Тома, снимки, привязки, каталог типов |
| `0004_seed_disk_types` | Наполнение каталога типов |
| `0006_fga_register_outbox` | Очередь регистрации владельца |
| `0007_image_and_volume_source_image` | Образы и происхождение тома от образа |
| `0008`–`0010` | Индексы и обслуживание очереди регистрации |
| `0011_drop_storage_outbox` | Снятие неиспользуемой очереди |
| `0013_tenant_cursor_indexes` | Индексы под курсорную выдачу страниц |

Применённая миграция не редактируется — изменение вносится новой.

## Каталог типов диска

Каталог наполняется миграцией и правится только через внутренний листенер; публичного
создания типов нет. Текущий состав:

| id | Класс | Назначение |
|---|---|---|
| `block-standard` | `standard` | Экономичный надёжный том |
| `block-balanced` | `balanced` | Сбалансированный, общего назначения |
| `block-fast` | `fast` | Высокий IOPS, низкая задержка |
| `block-single` | `single` | Однорепличный, без резервирования |
| `block-io-max` | `io-max` | Максимальные IOPS и пропускная способность |

Названия — собственные, они описывают класс надёжности и производительности, а не
маркетинговую линейку. Поле `zone_ids` ограничивает доступность типа зонами; пустой
список означает, что ограничения нет.
