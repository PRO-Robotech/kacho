# Операции

Любая мутация тома, снимка или образа возвращает не ресурс, а **операцию** — запись о
начатой работе. Клиент поллит её до завершения. Синхронно возвращаются только чтения.

## Контракт

```protobuf
message Operation {
  string id = 1;                    // "sop" + 17 символов
  string description = 2;
  google.protobuf.Timestamp created_at = 3;
  bool done = 4;
  google.protobuf.Any metadata = 5;
  oneof result {
    google.rpc.Status error = 6;
    google.protobuf.Any response = 7;
  }
}
```

Клиент опрашивает `OperationService.Get(id)`, пока `done` не станет `true`. Подписки на
операции у платформы нет и не предполагается: событие журнала пишется в той же транзакции, что
и строка ресурса, поэтому у провалившейся операции события нет вовсе — наблюдатель ресурсов не
отличил бы «ещё делается» от «упало».

Поток изменений **ресурсов** storage отдаёт: сервис — владелец журнала подписки платформы, и
край проецирует его наружу одной ручкой `GET /subscription/v1/events` (Server-Sent Events).
Строку журнала пишет триггер базы в той же транзакции, что и мутацию, поэтому в него попадают и
те изменения, которые совершает сверщик мимо репозиториев, — прежде всего перевод ресурса из
`CREATING` в `READY`. У создания и правки событие несёт **полное состояние** предмета полем
`state` — у всех трёх видов, в той же форме, что отдаёт `Get`; у снятия состояния нет, и его
отсутствие приходит признаком `stateUnavailable.reason = NOT_PRODUCED`. Состав и оговорки —
на странице [обзора API](/api/overview).

Идентификатор операции несёт префикс `sop` — отдельный от префиксов ресурсов. По нему
шлюз маршрутизирует опрос операции в нужный сервис, не разбирая, какого она ресурса.

## Что означает `done`

`done = true` означает ровно одно: **предмет мутации зафиксирован в базе**. Строка тома
создана, имя занято, намерение закоммичено.

`done` **не означает**, что видны все побочные эффекты. Их два, и оба лежат вне предмета
операции:

| Побочный эффект | Кто его доводит | Как узнать |
|---|---|---|
| Владелец ресурса материализуется в модели прав | Очередь регистрации, доставка не менее одного раза | Первое обращение к своему свежему ресурсу может кратко ответить `403`/`404` |
| Объект появляется у бэкенда хранения | Сверщик | `status` ресурса: `CREATING` → `AVAILABLE`/`READY`, либо `ERROR` с `statusReason` |

:::danger `done` не равно «ресурс готов к работе»
Ресурс рождается в `CREATING` и остаётся в нём, пока сверщик не увидит объект у бэкенда.
Опрашивать нужно **обе** величины: `done` операции отвечает за намерение, `status` ресурса
— за исход провижининга.

Почему провижининг не входит в предмет операции: функция операции исполняется под потолком
времени, а разрешитель осиротевших операций через несколько минут признаёт строку
завершённой, читая **нашу** базу. Если бы создание объекта шло внутри функции, толстое
выделение дольше этого потолка дало бы арендатору **ложное «готово»** при отсутствующем
объекте — худший из возможных исходов, потому что он неотличим от настоящего успеха.
:::

:::info Почему `done` не ждёт прав
Соблазн понятен: дождаться, пока права станут видимы, и только тогда сказать «готово».
Так делать нельзя, и причина не в производительности.

Во-первых, это подменяет предмет операции. Клиент просил «создать том», а не
«распространить запись о правах» — операция обязана отвечать за то, о чём её просили.

Во-вторых, при закрытом отказе рождается **ресурс-фантом**: строка уже закоммичена, имя
занято уникальным индексом, но операция помечена ошибкой. Клиент видит отказ, повторяет
запрос и получает `ALREADY_EXISTS` на ресурс, которого, по его сведениям, не существует.

В-третьих, ограниченная задержка чтения превращается в неограниченный жёсткий отказ, как
только нагрузка на модель прав вырастет.

Правильное место для этого — **ограниченный повтор на клиенте**: первое обращение к
только что созданному своему ресурсу может кратко получить `403` или `404`, и это
проходит за секунды.
:::

## Идентификатор ресурса приходит в `metadata`

Метаданные операции несут идентификатор ресурса — он выделяется **до** начала
асинхронной работы. Отсюда важное следствие для любого, кто читает `metadata`:

**Идентификатор присутствует и в операции, завершившейся ошибкой.** Прочитать его, не
проверив `result.error`, значит получить идентификатор ресурса, которого нет. Дальше он
уходит в последующие запросы, и отказ проявляется далеко от места, где возник.

Порядок обязателен: дождаться `done` → убедиться, что `error` пуст → только тогда брать
идентификатор.

## Перечисление операций по ресурсу

История операций доступна по каждому из трёх ресурсов:

- `GET /storage/v1/volumes/{volumeId}/operations`
- `GET /storage/v1/snapshots/{snapshotId}/operations`
- `GET /storage/v1/images/{imageId}/operations`

Ответ постраничный, теми же правилами, что и остальные списки. Паритет здесь не
косметика: снимок — такой же ресурс с длящейся работой, и отсутствие у него журнала
означало бы, что о ходе его создания узнать неоткуда.

## Справочники — без операций

Административные методы внутреннего листенера синхронны и возвращают сам ресурс:
регистрация классов диска, бэкендов, ревизий привязки и внесённых образов. Долгой работы
за записью в справочник нет, и оборачивать её в операцию значило бы заставить
администратора поллить то, что уже готово.

Это осознанное отступление от общего правила «мутации асинхронны», а не недоделка:
правило существует ради работы, которая действительно длится.

## Пагинация списков

Курсорная, по паре `(created_at, id)` по возрастанию. `page_token` — непрозрачный
маркер; клиент его не разбирает и не конструирует.

| Параметр | Правило |
|---|---|
| `page_size` | `0` → 50, максимум 1000. Значение вне диапазона **отвергается**, а не обрезается |
| `page_token` | Испорченный маркер → `INVALID_ARGUMENT` |

Формат проверяется **до** сужения по правам. Иначе вызывающий без грантов получал бы
пустую страницу вместо ошибки на испорченном курсоре, и поведение контракта зависело бы
от состояния прав.

:::note Известный размен курсора
Маркер следующей страницы может кодировать позицию строки, которая самому вызывающему не
видна: он содержит отметку времени и идентификатор, но не содержимое. Это цена курсорной
семантики, при которой ни одна строка не пропускается и не дублируется между страницами.
Альтернатива — пересчитывать позицию после фильтрации — приводила бы к пропускам.
:::
