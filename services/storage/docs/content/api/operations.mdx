# Operation

Каждая мутация тома, снимка или образа возвращает **операцию** — запись о начатой работе.
Ресурс синхронно не возвращается.

## Форма

```protobuf
message Operation {
  string id = 1;                              // "sop" + 17 символов
  string description = 2;
  google.protobuf.Timestamp created_at = 3;
  bool done = 4;
  google.protobuf.Any metadata = 5;           // несёт id ресурса
  oneof result {
    google.rpc.Status error = 6;
    google.protobuf.Any response = 7;
  }
}
```

| Поле | Смысл |
|---|---|
| `id` | Идентификатор операции, префикс `sop` |
| `done` | Работа завершена. **Не** означает, что видны все побочные эффекты |
| `metadata` | Метаданные, включая идентификатор ресурса |
| `error` | Заполнено, если работа завершилась неуспехом |
| `response` | Заполнено, если работа завершилась успехом |

## Опрос

<ApiOperation method="GET" endpoint="/operations/{operationId}">

Возвращает состояние операции. Клиент опрашивает её, пока `done` не станет `true`.

#### Пример

<CodeBlock language="bash">
  {dedent`
    curl -H "Authorization: Bearer $TOKEN" \\
      https://api.kacho.local/operations/sopa1b2c3d4e5f6g7h8j
  `}
</CodeBlock>

Интервал в несколько секунд покрывает задачу. Опрос без паузы создаёт нагрузку и ничего
не ускоряет.

## Порядок чтения результата — обязателен

:::danger Идентификатор ресурса есть и в неуспешной операции
Идентификатор ресурса выделяется **до** начала асинхронной работы, поэтому он присутствует
в `metadata` и тогда, когда операция завершилась ошибкой.

Прочитать его, не проверив `error`, значит получить идентификатор ресурса, **которого не
существует**. Дальше он уходит в последующие запросы, и отказ проявляется далеко от места,
где возник, — обычно как непонятная ошибка соседнего сервиса.

Порядок обязателен:

1. опрашивать, пока `done` не станет `true`;
2. убедиться, что `error` **пуст**;
3. только тогда брать идентификатор из `metadata`.
:::

## Что означает `done`

`done = true` означает: **предмет мутации зафиксирован**. Строка закоммичена, имя занято,
намерение принято.

Два побочных эффекта в предмет операции **не входят**, и оба доводятся отдельно:

- **права владельца** материализуются очередью в ограниченном окне после коммита. Поэтому
  первое обращение к только что созданному **своему** ресурсу может кратко ответить `403`
  или `404`; это закрывается ограниченным повтором на стороне клиента;
- **объект у бэкенда** создаёт сверщик. Поэтому ресурс рождается в `CREATING` и переходит
  в `AVAILABLE`/`READY`, когда сверщик подтвердил объект, либо в `ERROR` с `statusReason`.

Отсюда правило чтения: `done` отвечает за намерение, `status` ресурса — за исход
провижининга. Ждать готовности по одному `done` — значит принять «заказ принят» за «работа
сделана».

Обоснование, почему барьер на сервере здесь был бы хуже, — в разделе
[Операции](/architecture/operations).

Ответ постраничный, по тем же правилам, что остальные списки.

## Маршрутизация опроса

Префикс `sop` отделён от префиксов ресурсов намеренно: по нему шлюз направляет опрос
операции в этот сервис, не разбирая, какого ресурса она касается. Поэтому добавление
нового ресурса не требует менять маршрутизацию операций.
