# Развёртывание

Сервис поставляется Helm-чартом `services/storage/deploy` и входит в общий зонтичный
чарт платформы.

## Что разворачивается

| Объект | Назначение |
|---|---|
| `Deployment` | Сам сервис; init-контейнер прогоняет миграции |
| `Service` | Три порта: публичный 9090, внутренний 9091, метрики 9095 |
| `ConfigMap` | Несекретные настройки `KACHO_STORAGE_*` |
| `Certificate` | Серверные сертификаты для mTLS на обоих листенерах |
| `ServiceMonitor` | Сбор метрик |

Имя ресурсов зафиксировано как `kacho-storage` (`fullnameOverride`). Это несущее
требование, а не косметика: потребители обращаются именно по этому имени, и оно же входит
в имена в сертификатах. Без фиксации имя стало бы производным от имени релиза — DNS
перестал бы резолвиться, а имена в сертификате не совпали бы.

## Отдельный бинарь миграций

Миграции применяет `cmd/migrator`, а не сам сервис при старте. Разделение намеренное:
запуск сервиса и изменение схемы — разные операции с разными правами и разным правом на
повтор.

Применённая миграция не редактируется. Изменение вносится новой.

## Требования production-посадки

Стенд любого рода — локальный, тестовый, промышленный — поднимается в
**production-посадке**. Небезопасная посадка на развёрнутом кластере запрещена: она
маскирует ровно те дефекты, ради которых существуют проверки.

Обязательный минимум, без которого сервис не стартует:

| Ключ values | Значение |
|---|---|
| `config.authMode` | `production` |
| `db.sslMode` | `require` (или строже) |
| `config.authzIamGrpcAddr` | адрес внутреннего листенера kacho-iam |
| `config.trustedForwarderSANs` | **непустой** список |
| `listFilter.enabled` | `true` |
| `mtls` | включён на обоих листенерах |

«Зелёный dev» не доказывает готовность к production: он обходит проверку прав, оставляет
непроверенные каналы и не запускает проверки при загрузке. Полный перечень условий отказа
— в разделе [Конфигурация](/install/configuration).

## Каталог классов на свежем стенде — шаг подъёма, а не умолчание

Каталог классов диска стартует **пустым**: класс не предлагается арендатору раньше, чем
объявлено, чем он обслуживается. Пока каталог пуст, **каждое** создание тома отвечает
«класс не найден», а снимки и образы не заводятся вовсе.

Поднятый, но не засеянный стенд непригоден — и **ни один «под Ready» этого не
показывает**: сервис исправно поднялся, проверки при загрузке прошли, а работать с ним
нельзя. Поэтому посев базового каталога — отдельный, громко отказывающий шаг подъёма:

<CodeBlock language="bash">
  {dedent`
    make -C deploy seed-storage
  `}
</CodeBlock>

Шаг заводит кластер данных, классы и действующие ревизии привязки «класс × зона». Он идёт
**строго после** посева каталога размещения (`seed-geo`): зоны привязок спрашиваются у
владельца географии, а не выписываются — имена зон произвольны, и выписанная копия
разъехалась бы с каталогом молча.

Отказ громкий: нет базы, не применился SQL, ноль открытых зон или ноль действующих
привязок — ненулевой код возврата. Тихий пропуск означал бы стенд, отчитавшийся поднятым и
не способный создать ни одного тома.

## Секреты

Пароль базы **никогда** не лежит в values — они версионируются. Он берётся из секрета по
ссылке (`db.passwordSecretName` / `db.passwordSecretKey`) и монтируется в контейнер
миграций и в основной контейнер.

## Проверка после развёртывания

Проверять надо **живой процесс**, а не объекты конфигурации.

<CodeBlock language="bash">
  {dedent`
    # что процесс объявил о своей посадке при старте
    kubectl logs deploy/kacho-storage | grep -E 'auth_mode|db_sslmode|mtls'

    # шифрование со стороны базы — подтверждение, которое настройкой не подделать
    kubectl exec -it <pod-postgres> -- psql -U storage -d kacho_storage \\
      -c "SELECT ssl, count(*) FROM pg_stat_ssl JOIN pg_stat_activity USING (pid) GROUP BY ssl;"
  `}
</CodeBlock>

:::caution «Под готов» не доказывает посадку
Готовность пода означает лишь, что он не падал. Если настройки приезжают через `envFrom`,
правка конфигурации **не меняет шаблон пода** — под не перекатывается, процесс живёт со
старым окружением, и проверка при загрузке не выполняется, потому что старта не было.
Контроль при этом присутствует, написан верно и полностью обойдён.

Поэтому: шаблон пода привязан к содержимому настроек контрольной суммой, а проверять надо
то, что процесс **объявил при старте**, плюс шифрование со стороны базы — независимое
подтверждение.
:::

## Обновление зависимостей чарта

Зонтичный чарт берёт подчарт из собранного архива, а не из каталога с исходником. Если
править `services/storage/deploy` и сразу рендерить шаблон, отрендерится **прошлая**
версия чарта, и проверка подтвердит не то, что написано в values.

Порядок: обновить зависимости чарта, затем рендерить или устанавливать.

## Метрики и здоровье

Диагностический листенер на 9095 отдаёт `/healthz` и метрики. Он не несёт доменных данных
и наружу не публикуется.

## Откат выкатки

Неудачная выкатка откатывается в **три шага, и порядок в них несущий**. Схему
возвращают ДО образа: down-миграция лежит в том образе, который её принёс, и
вернув образ первым, вы останетесь без файла, которым откатывать.

Отдельно про то, чего `helm rollback` не делает сам: миграции едут
initContainer'ом и прогоняются `up` **на каждом старте пода**, поэтому возврат
образа перекатывает под и снова накатывает схему до головы своей цепочки.
Возврат образа сам по себе схему не возвращает.

### Шаг 1. Решить, нужен ли откат СХЕМЫ

| что несла выкатка | нужен ли откат схемы |
|---|---|
| только образ, миграций нет | нет — сразу шаг 3 |
| миграции аддитивные (новая таблица, новая колонка) | как правило нет: прежний код их не читает, и это самый дешёвый путь |
| миграция несовместима с прежним кодом (переименование, сужение типа, снятие колонки) | да — шаг 2 |
| миграция снесла таблицу или колонку | схему вернуть можно, **данные — нет**; см. рамку ниже |

### Шаг 2. Откатить схему — образом, который эту миграцию несёт

```bash
# ДО helm rollback, пока в поде ещё НОВЫЙ образ: у него есть down-файл.
kubectl -n <namespace> exec deploy/<деплой kacho-storage> -- \
  /usr/local/bin/kacho-migrator status
kubectl -n <namespace> exec deploy/<деплой kacho-storage> -- \
  /usr/local/bin/kacho-migrator down --target <версия, до которой откатываем>
```

### Шаг 3. Вернуть образ

```bash
helm history <релиз>
helm rollback <релиз> <ревизия>
```

:::danger `down` возвращает форму, а не данные
Down-миграция воссоздаёт схему **пустой**. Строки, которые снёс `DROP`, она не
возвращает: «восстановимо» про снос означает «восстановима схема». Единственный
путь назад для снесённых строк — резервная копия базы.

Продукт защищает это на своей стороне: накат считает живые строки в каждой
таблице, которую уронит ещё не применённая миграция, и **отказывает**, пока снос
не одобрен явно — переменной `KACHO_MIGRATOR_DROP_APPROVED` с именем конкретного
сноса. Отказ на выкатке стоит одной выкатки; восстановление из копии — сильно
дороже, и узнаёте вы о нужде в нём уже после.
:::

### Чем проверить, что откат состоялся

Проверять надо **три** вещи, и «под Ready» само по себе ни одной из них не
доказывает:

| что | чем |
|---|---|
| ревизия релиза вернулась | `helm history <релиз>` — последняя запись со статусом `deployed` |
| под работает нужным образом | `kubectl -n <namespace> get pod -l app=<деплой kacho-storage> -o jsonpath='{..image}'` |
| схема на ожидаемой версии | `kacho-migrator status` — головная применённая версия |
| зависимости сервиса живы | `readinessProbe` спрашивает `/readyz`, поэтому `kubectl get pods` показывает готовность **по зависимостям**, а не по открытому сокету: под в `0/1` — это отказ зависимости, а не «ещё поднимается» |
