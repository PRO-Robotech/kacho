# Конфигурация

Kachō Registry конфигурируется через переменные окружения с префиксом **`KACHO_REGISTRY_`** (загрузка
через corelib `config.LoadPrefixed("KACHO_REGISTRY")`). Значения из окружения переопределяют дефолты.
Эта страница перечисляет ключевые ключи и даёт пример.

### Secure by default

По умолчанию (`breakglass=false`) операции control-plane **без авторизации и mTLS запрещены**: per-RPC
authz `Check` (через kaname) и mTLS на **обоих** gRPC-listener'ах обязательны — иначе сервис
**откажется стартовать**. Это инвариант «AuthN + AuthZ везде» (internal `:9091` не освобождён).

В любом production-режиме к этому добавляется **непустой список доверенных отправителей**
(`KACHO_REGISTRY_AUTHZ_TRUSTED_FORWARDER_SANS`). Проверенный сертификат отвечает на вопрос «кто
звонит», но не на вопрос «вправе ли он говорить от чужого имени»: без списка любой пир, чей
сертификат выдал тот же внутренний центр, присылает заголовки личности произвольного пользователя,
и решение о правах принимается от его имени. Список сужает круг до перечисленных отправителей —
у registry это api-gateway, и только он.

:::warning В боевом режиме обхода НЕТ — breakglass не поднимает сервис, а гарантирует, что он не встанет
`KACHO_REGISTRY_AUTHZ_BREAKGLASS=true` запускает сервис, **пропуская per-RPC Check и не требуя mTLS**,
**только** при `KACHO_REGISTRY_AUTH_MODE=dev`. В `production` и `production-strict` взведённая ручка —
**отказ старта** отдельным стражем: «`production mode (<режим>): KACHO_REGISTRY_AUTHZ_BREAKGLASS must not
be enabled`».

Отсюда практическое следствие для дежурного: если боевой сервис не встаёт из-за нехватки адреса iam или
mTLS, **breakglass не является следующим шагом** — он даст второй отказ и ещё один цикл выкатки, пока
сервис лежит. Следующий шаг называет сам текст отказа: задать `KACHO_REGISTRY_AUTHZ_IAM_GRPC_ADDR` либо
взвести `KACHO_REGISTRY_PUBLIC_SERVER_MTLS_ENABLE` / `KACHO_REGISTRY_INTERNAL_SERVER_MTLS_ENABLE`. Отказ
в боевом режиме breakglass **не предлагает** именно поэтому.
:::

## Data-plane (OCI auth-proxy)

Data-plane аутентифицирует `docker`/`helm` по identity-JWT. **Издатель токена — множество:**
платформа чеканит свои токены сама, а прежний издатель на переходе остаётся, и у каждого
принимаемого издателя **своя объявленная запись источника ключей**. Объединить наборы было бы
дешевле и уничтожило бы ровно ту защиту, ради которой развязка делается: ключ одного издателя
проверял бы токен, объявляющий другого.

:::warning Адрес набора **объявляется**, а не выводится из издателя
Издатель приходит **от предъявителя** — это недоверенный вход. Кроме прямого вреда, производный
адрес получался бы у **всякого** издателя, поэтому состояние «записи источника нет» не наступало бы
никогда, и страж старта остался бы в тексте, не имея возможности упасть.
:::

<table>
  <thead><tr><th>Переменная</th><th>По умолчанию</th><th>Описание</th></tr></thead>
  <tbody>
    <tr><td><code>KACHO_REGISTRY_TOKEN_ISSUERS</code></td><td><em>(пусто)</em></td><td>Перечень принимаемых <code>iss</code> через запятую. Страж старта считает <strong>элементы</strong>, а не длину строки: <code>","</code> — непустая строка с нулём элементов. Пусто → <strong>отказ в старте, в любом режиме</strong>: пустой перечень означает «принимаем любого издателя», и послабления на этом поле нет ни у одной посадки</td></tr>
    <tr><td><code>KACHO_REGISTRY_TOKEN_ISSUER_KEYSETS</code></td><td><em>(пусто)</em></td><td>Привязка <code>издатель=адрес набора ключей</code> через запятую. Издатель без записи → отказ в старте; запись без принимающего её издателя → тоже отказ. В production каждый адрес обязан быть <code>https</code></td></tr>
    <tr><td><code>KACHO_REGISTRY_PLATFORM_TOKEN_ISSUER</code></td><td><em>(пусто)</em></td><td>Издатель, под которым чеканит наша платформа. Выбирает полосу приёма: тип токена <code>at+jwt</code> (RFC 9068) и чтение отзыва на предъявлении. Непусто, но вне <code>TOKEN_ISSUERS</code> → отказ в старте</td></tr>
    <tr><td><code>KACHO_REGISTRY_TOKEN_REVOCATION_URL</code></td><td><em>(пусто)</em></td><td>Адрес авторитета отзыва (интроспекция RFC 7662) на cluster-internal слушателе iam. Обязателен, когда наш издатель принимается. В production обязан быть <code>https</code></td></tr>
    <tr><td><code>KACHO_REGISTRY_TOKEN_REVOCATION_MTLS_*</code></td><td><em>(выключено)</em></td><td>Учётные данные ребра к авторитету отзыва (<code>ENABLE</code>/<code>CERTFILE</code>/<code>KEYFILE</code>/<code>CAFILES</code>/<code>SERVERNAME</code>). Якорь объявлен и непригоден → <strong>отказ в старте</strong>, а не откат на системные корни</td></tr>
    <tr><td><code>KACHO_REGISTRY_SERVICE_AUD</code></td><td><code>registry.kacho.local</code></td><td>Ожидаемый <code>aud</code> identity-JWT. Токен обязан нести <code>aud ⊇ ServiceAud</code> (иначе federation-out не даёт доступа)</td></tr>
    <tr><td><code>KACHO_REGISTRY_TOKEN_REALM</code></td><td><code>https://api.kacho.local/iam/token</code></td><td>realm для <code>WWW-Authenticate</code> — docker идёт туда за Bearer-токеном (token-шим kaname)</td></tr>
    <tr><td><code>KACHO_REGISTRY_DATAPLANE_TLS_TERMINATED_EXTERNALLY</code></td><td><code>false</code></td><td>Подтверждение, что data-plane стоит за внешней TLS-терминацией. В production/production-strict обязан быть <code>true</code></td></tr>
  </tbody>
</table>

:::note Отзыв читается **на предъявлении**
Контроль, действующий только там, где удостоверение выдают, отзывом не является: он лишь не выдаёт
нового. Окно удержания утвердительного ответа берётся из объявленной политики платформы, а не
задаётся здесь. Всякий неопознанный исход авторитета — не 200, не JSON, <code>401</code>, обрыв,
истечение срока — закрывает доступ.

Ребро к авторитету **своё**, а не общее с загрузкой набора ключей: набор несёт только публичный
материал и потому открыт задокументированным исключением, а маршруту отзыва присылают
**предъявленный токен**. Обращение обязано нести клиентский сертификат.
:::

:::info Снято с контракта
`KACHO_REGISTRY_HYDRA_JWKS_URL` (эта страница называла его, а сервис читал другое имя),
`KACHO_REGISTRY_IAM_JWKS_URL` и `KACHO_REGISTRY_HYDRA_ISSUER` **больше не консультируются**.
Посадка, задавшая только их, не принимает ни одного издателя и потому **отказывает в старте**, а не
работает вслепую. Прежний издатель объявляется своей записью в `TOKEN_ISSUERS` /
`TOKEN_ISSUER_KEYSETS`.
:::

## mTLS (per-edge)

Транспортные client/server-creds задаются **на каждое ребро отдельно** (без общего TLS-синглтона).
Каждая структура читает независимый набор ENV `KACHO_REGISTRY_<EDGE>_<NAME>`:

<table>
  <thead><tr><th>Ребро</th><th>ENV-сегмент</th><th>Назначение</th></tr></thead>
  <tbody>
    <tr><td>registry → iam internal (Check + fga-proxy, client)</td><td><code>KACHO_REGISTRY_IAM_AUTHZ_MTLS_&lt;NAME&gt;</code></td><td>Client-creds на iam :9091 (ServerName <code>kaname-internal.&#42;</code>)</td></tr>
    <tr><td>registry → iam public (ProjectService.Get, client)</td><td><code>KACHO_REGISTRY_IAM_PROJECT_MTLS_&lt;NAME&gt;</code></td><td>Client-creds на iam :9090 (ServerName <code>kaname.&#42;</code>)</td></tr>
    <tr><td>public listener (server)</td><td><code>KACHO_REGISTRY_PUBLIC_SERVER_MTLS_&lt;NAME&gt;</code></td><td>Server-creds для публичного control-plane (:9090)</td></tr>
    <tr><td>internal listener (server)</td><td><code>KACHO_REGISTRY_INTERNAL_SERVER_MTLS_&lt;NAME&gt;</code></td><td>Server-creds для cluster-internal listener (:9091)</td></tr>
  </tbody>
</table>

У каждой TLS-структуры есть флаг `..._ENABLE` (по умолчанию `false` — insecure back-compat для dev).
В production оба server-флага и client-флаги ребёр к iam должны быть `true`. ServerName public и
internal ребёр к iam различаются, поэтому это **два** отдельных client-conn (единый некорректен под
`RequireAndVerifyClientCert`).

## Пример YAML

<CodeBlock language="yaml" title="kacho-registry.yaml">
  {dedent`
    KACHO_REGISTRY_DB_HOST: postgres.kacho.svc
    KACHO_REGISTRY_DB_PORT: "5432"
    KACHO_REGISTRY_DB_USER: registry
    KACHO_REGISTRY_DB_PASSWORD: <из секрета>
    KACHO_REGISTRY_DB_NAME: kacho_registry
    KACHO_REGISTRY_DB_SSLMODE: verify-full

    KACHO_REGISTRY_GRPC_PORT: "9090"
    KACHO_REGISTRY_INTERNAL_PORT: "9091"
    KACHO_REGISTRY_DATAPLANE_ADDR: ":8080"

    KACHO_REGISTRY_ZOT_ADDR: http://zot.kacho.svc:5000
    KACHO_REGISTRY_ENDPOINT_BASE: registry.kacho.local

    KACHO_REGISTRY_AUTH_MODE: production-strict
    KACHO_REGISTRY_AUTHZ_IAM_GRPC_ADDR: kaname-internal.kacho.svc:9091
    KACHO_REGISTRY_IAM_PROJECT_GRPC_ADDR: kaname.kacho.svc:9090
    KACHO_REGISTRY_AUTHZ_TRUSTED_FORWARDER_SANS: spiffe://kacho.cloud/ns/kacho/sa/kacho-api-gateway
    KACHO_REGISTRY_AUTHZ_BREAKGLASS: "false"

    # data-plane: приём identity-JWT — издатель множество, у каждого своя запись
    KACHO_REGISTRY_TOKEN_ISSUERS: https://iam.kacho.local,https://hydra.api.kacho.cloud
    KACHO_REGISTRY_TOKEN_ISSUER_KEYSETS: >-
      https://iam.kacho.local=https://kaname-internal.kacho.svc:9097/.well-known/kacho/jwks.json,
      https://hydra.api.kacho.cloud=https://kaname-internal.kacho.svc:9097/.well-known/jwks.json
    KACHO_REGISTRY_PLATFORM_TOKEN_ISSUER: https://iam.kacho.local
    KACHO_REGISTRY_TOKEN_REVOCATION_URL: https://kaname-internal.kacho.svc:9097/internal/tokens/introspect
    KACHO_REGISTRY_SERVICE_AUD: registry.kacho.local
    KACHO_REGISTRY_DATAPLANE_TLS_TERMINATED_EXTERNALLY: "true"

    # per-edge mTLS (включить в production)
    KACHO_REGISTRY_PUBLIC_SERVER_MTLS_ENABLE: "true"
    KACHO_REGISTRY_INTERNAL_SERVER_MTLS_ENABLE: "true"
    KACHO_REGISTRY_IAM_AUTHZ_MTLS_ENABLE: "true"
    KACHO_REGISTRY_IAM_PROJECT_MTLS_ENABLE: "true"
    KACHO_REGISTRY_TOKEN_REVOCATION_MTLS_ENABLE: "true"
  `}
</CodeBlock>

:::tip Локальный dev
Для локального запуска достаточно `KACHO_REGISTRY_DB_PASSWORD` и `KACHO_REGISTRY_ZOT_ADDR` (остальное
берёт дефолты). Режим `dev` поднимет сервис без mTLS. Сборка и миграции — в
[Быстром старте](/getting-started).
:::
