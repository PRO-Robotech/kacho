# Модуль `vpc-network`

Модуль описывает сеть целиком: сеть, её подсети, группы безопасности, таблицы
маршрутов, сетевые интерфейсы, адреса и шлюз общего исхода. Это типовая единица —
её заводят целиком, а не по частям.

Модуль требует OpenTofu/Terraform **1.9 и выше**: его проверки входа ссылаются на другие
переменные (ключ таблицы маршрутов у подсети, ключ подсети у интерфейса и у внутреннего
адреса), а межпеременные проверки появились именно там.

## Использование

```hcl
module "vpc" {
  source = "github.com/PRO-Robotech/kacho//terraform/modules/vpc-network"

  project_id       = var.project_id
  name             = "production"
  description      = "сеть production-контура"
  ipv4_cidr_blocks = ["10.10.0.0/16"]

  route_tables = {
    "egress" = {
      routes = [
        { destination_prefix = "0.0.0.0/0", next_hop_address = "10.10.0.1" },
      ]
    }
  }

  subnets = {
    "production-a" = {
      zone_id           = "ru-central1-a"
      ipv4_cidr_primary = "10.10.1.0/24"
      route_table       = "egress"
    }
    "production-b" = {
      zone_id           = "ru-central1-b"
      ipv4_cidr_primary = "10.10.2.0/24"
    }
    "production-anycast" = {
      region_id         = "ru-central1"
      ipv4_cidr_primary = "10.10.9.0/24"
    }
  }

  security_groups = {
    "web" = {
      rules = [
        {
          direction      = "INGRESS"
          protocol_name  = "tcp"
          ports          = { from_port = 443, to_port = 443 }
          v4_cidr_blocks = ["0.0.0.0/0"]
        },
        {
          direction      = "EGRESS"
          v4_cidr_blocks = ["0.0.0.0/0"]
        },
      ]
    }
  }

  addresses = {
    "web-vip" = {
      internal_ipv4 = { subnet = "production-a" }
    }
  }

  network_interfaces = {
    "web-0" = {
      subnet             = "production-a"
      security_group_ids = [] # см. ниже: пусто означает «ни одной группы»
    }
  }

  create_gateway = true
}
```

## Как модуль связывает ресурсы

### Внутри модуля ссылаются КЛЮЧОМ, за его пределы — идентификатором

Подсеть называет таблицу маршрутов ключом (`route_table`), интерфейс называет подсеть
ключом (`subnet`), внутренний адрес — тоже ключом. Причина одна: идентификатор присваивает
край при создании, поэтому у ресурса, которого ещё нет, его нет и у вызывающего. Ключ
модуль разрешает в идентификатор сам — и тем строит граф зависимостей.

Готовый идентификатор принимается там, где ресурс заведён **вне** модуля: `route_table_id`
у подсети, `security_group_id` у правила группы, `security_group_ids` / `v4_address_ids` /
`v6_address_ids` у интерфейса.

У интерфейса идентификатор подсети **не** принимается намеренно: он разорвал бы ребро
графа, и порядок сноса стал бы произвольным.

### Порядок сноса

Группы, таблицы, подсети и интерфейсы ссылаются на сеть или на подсеть по идентификатору,
поэтому граф строится сам: интерфейсы и адреса снимаются раньше своей подсети, подсети —
раньше сети.

Часть этого порядка край подкрепляет: подсеть, из адресов которой кто-то выделен, и
подсеть с живым интерфейсом он удалять не станет.

:::warning Не полагайтесь на «неверный порядок даст ошибку»
Часть связей платформы при неверном порядке удаления **не падает, а молча обнуляется** —
ссылка подсети на таблицу маршрутов объявлена `ON DELETE SET NULL`. Порядок обязан
держаться графом ссылок, а не наблюдением за ошибками. Поэтому в модуле подсеть ссылается
на `.id` ресурса, а не на переменную с тем же значением.
:::

## Сеть

| Имя | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `project_id` | `string` | — | Проект-владелец. Сменить нельзя. |
| `name` | `string` | — | Имя сети в проекте. |
| `ipv4_cidr_blocks` | `list(string)` | — (непустой) | Супернет сети. |
| `description` · `labels` | — | `""` / `{}` | Описание и метки сети. |
| `create_default_security_group` | `bool` | `false` | Заводить ли группу безопасности по умолчанию. |

### Почему `ipv4_cidr_blocks` обязателен и непуст

Сеть без объявленного супернета **не примет ни одной подсети**: край отвергнет её словами
`network declares no IPv4 supernet`. Модуль создаёт сеть вместе с подсетями, поэтому
допускать порядок «сеть сейчас, супернет потом» ему нельзя — проверка стоит прямо в
переменной и срабатывает до обращения к платформе.

### `create_default_security_group = false` задано ЯВНО, а не оставлено краю

Незаданное поле здесь **не** означает «как обычно»: контракт объявляет его необязательным и
при отсутствии откатывается на настройку **развёртывания** края. То есть одна и та же
конфигурация давала бы на разных стендах разный итог — и разный молча, потому что решение
принимал бы не тот, кто пишет конфигурацию.

Итог не косметический: группа по умолчанию заводится с правилами «любой протокол отовсюду»
в обе стороны. Такое решение принимают, а не получают по невнимательности.

:::warning Смена значения ПЕРЕСОЗДАЁТ сеть
Край это поле в ответе не возвращает, и провайдер объявил его требующим замены. Следствие,
которое надо знать до обновления модуля: у того, чья сеть заведена стендом с включённой
настройкой, значение в состоянии не записано вовсе, и первый же план после обновления
покажет замену.
:::

Выход `default_security_group_id` — **пустая строка**, когда группу не заводили. Пусто здесь
означает «группы нет», а не «идентификатор пока неизвестен»: подставив эту строку в ссылку
не проверив, вы сошлётесь в никуда.

## Подсети

| Поле записи | Назначение |
|---|---|
| `zone_id` / `region_id` | Ровно один якорь размещения. |
| `ipv4_cidr_primary` | Блок адресов подсети. |
| `route_table` | КЛЮЧ карты `route_tables` этого модуля. |
| `route_table_id` | Готовый идентификатор таблицы, заведённой вне модуля. |
| `description` · `labels` | Описание и метки. |

Зональная и региональная подсети — разные вещи, а не два способа сказать одно. У
региональной (anycast) зоны нет вовсе, и зональные проверки согласованности к ней не
применяются.

`route_table` и `route_table_id` — два написания одного поля, и заданные вместе они
отвергаются: выбрать за вас, какое имелось в виду, модуль не вправе. Не задано ни одного —
таблицу подставит край из `default_route_table_id` сети.

:::note Подсеть получает таблицу в момент СВОЕГО создания
Заведение таблицы само по себе ни одну существующую подсеть не трогает. Чтобы таблица
применялась, назовите её ключ в `route_table` нужных подсетей.
:::

## Группы безопасности

Ключ карты — имя группы в проекте. Группа заводится в сети этого модуля, и сеть у неё
**неизменяема**: операции переноса группы между сетями у края не существует, смена сети
пересоздаёт группу.

:::danger Группа без правил не пропускает НИЧЕГО
Это её смысл, а не пробел описания. Правила только **разрешают**: запрещающего правила в
контракте нет, приоритета и порядка у правил тоже нет, и что не разрешено явно — не
проходит. Поэтому `rules = []` (и опущенное поле) означает интерфейс, закрытый в **обе**
стороны, включая исходящий трафик: `EGRESS` тоже выдаётся правилом.
:::

### Поля правила

| Поле | Назначение |
|---|---|
| `direction` | `INGRESS` либо `EGRESS`. Своей копии перечня модуль не держит — имена сверяет провайдер по таблице контракта. |
| `protocol_name` / `protocol_number` | Одно из двух, не оба. Ни одного — любой протокол. Номер `0` отвергает провайдер (см. ниже). |
| `ports` | Обе границы вместе либо ничего: полудиапазона край не знает. Опущен — любой порт. |
| `v4_cidr_blocks` · `v6_cidr_blocks` / `security_group_id` / `cidr_group` · `cidr_group_id` | Цель — ровно одна из трёх. Ветвь предопределённого имени снята с контракта: она была свободной строкой без словаря и без ветвления. |
| `description` · `labels` | По умолчанию `null`, а не `""` и `{}`. |

Описание и метки **правила** по умолчанию `null` — в отличие от полей самой группы: пустая
строка и пустая карта означают для края то же, что опускание, и обратно он отдаёт
опускание. Два написания одного смысла разошлись бы между настройкой и состоянием на первом
же плане.

`protocol_number = 0` отвергает **провайдер**, а не край, и вот почему это правильно:
хранилище держит «протокол не задан» тем же нулём, поэтому такое правило доехало бы и
читалось бы как «любой протокол» — шире, чем вы просили. Для протокола IANA с номером 0
пишите `protocol_name = "hopopt"`; для «любого» — уберите оба поля протокола.

`security_group_id` — **внешний** идентификатор, и ключом карты этого модуля он быть не
может by construction: ссылка группы на группу того же блока — самоссылка, и конфигурация
была бы отвергнута циклом ещё до края. Вторая цепочка групп заводится вторым экземпляром
модуля, и выход `security_group_ids` даёт идентификаторы, которые она примет на вход.
Группа-цель обязана лежать в той же сети — это требование края, и оно на вызывающем.

`cidr_group` / `cidr_group_id` — третья цель: **именованный набор префиксов**. Правило
называет набор, а не его состав, поэтому перечень сетей, повторяющийся в двадцати правилах,
правится один раз — в самом наборе. Внутри модуля набор называется **ключом** карты
`cidr_groups` (идентификатор модуль подставит сам и тем построит граф); готовый
`cidr_group_id` — для наборов, заведённых вне модуля. Оба написания сразу модуль отвергает:
выбирать за вас, какое имелось в виду, он не вправе.

Набор обязан лежать в **том же проекте** и не быть **пустым** — правило, ссылающееся на
набор без единого члена, край отвергает: такое правило либо потеряло бы фильтр, либо
перестало пропускать что-либо, и оба исхода молчаливы. Модуль ловит это на `plan`, называя
группу и индекс правила.

:::warning Пустая строка в цели делает правило ШИРЕ написанного
Край читает её как «цель не задана», сохраняет правило без цели и ничем не жалуется. То же
с `cidr_blocks` без единого блока. Модуль отвергает обе формы на `plan` и называет виновную
группу и индекс правила.
:::

Правила задаются **списком**, а край хранит их **набором**: порядок не значит ничего, а два
дословно одинаковых правила — одно правило (собственной личности, кроме своего значения, у
правила нет). Список выбран ради адреса отказа: сообщение называет ключ группы и индекс в
том списке, который написали вы.

## Именованные наборы префиксов

Ключ карты `cidr_groups` — имя набора в проекте. Набор принадлежит **проекту**, а не сети:
поля сети в его контракте нет вовсе, и с сетью этого модуля его связывают правила, которые
на него ссылаются.

| Поле | Назначение |
|---|---|
| `v4_cidr_blocks` · `v6_cidr_blocks` | Члены набора по семьям. Семьи — **разные** поля: член чужого семейства край отвергает на входе. |
| `description` · `labels` | Описание и метки набора. |

Состав правится **отдельными действиями края** (`:add-cidr-blocks` / `:remove-cidr-blocks`),
а не обычной правкой: в маске изменения состава нет вовсе. Провайдер вычисляет разницу
набора сам и вызывает оба действия — сначала добавление, потом снятие. Порядок не произволен:
обратный провёл бы набор через состояние, где семья пуста, а опустошение семьи, на которую
ссылается живое правило, край отвергает.

Цена этого порядка названа честно: в промежуточном состоянии набор держит и новые члены, и
старые, поэтому **полная** замена состава у набора, уже близкого к потолку (64 члена на
семейство), упрётся в потолок. Такая замена делается в два применения — сначала снятие
лишнего, затем добавление.

Выход `cidr_group_ids` даёт идентификаторы для правил, заводимых **вне** модуля; выход
`cidr_groups` — состав и посчитанное краем число членов.

## Таблицы маршрутов

Ключ карты — имя таблицы в проекте. Маршрут задаётся назначением (`destination_prefix`,
запись CIDR с нулевыми разрядами узла) и следующим узлом (`next_hop_address`, IP-адрес).

Маршруты — список, и порядок сохраняется дословно: край адресует свои отказы индексом
(`static_routes[2]…`), и у списка этот индекс — тот самый, что вы написали. Два маршрута с
одним назначением через разные следующие узлы — законная запись (равноценные пути), и она
сохраняется как написана.

:::warning Ветки «следующий узел — шлюз» в модуле нет — и это отставание, названное прямо
**Край её принимает.** У статического маршрута следующий узел — ровно одна из двух ветвей:
адрес либо идентификатор шлюза; названный шлюз резолвится на пути запроса и проверяется на
ту же сеть, ту же зону и то же семейство (см. [Gateway](../api/gateway.mdx)).

Через этот модуль ветка **недоступна**: ключа для ссылки на шлюз у переменной нет, а
провайдер такого атрибута не объявляет — неизвестный аргумент даёт терминальный отказ ещё
на разборе конфигурации. То есть ссылку «следующий узел — шлюз» средствами Terraform
сегодня выразить нечем, и обходного пути нет. Причина — в оснастке, а не в контракте.

Здесь раньше стояло обратное объяснение — «край отвергает такую ветку синхронно, у шлюза
нет и собственного адреса». Оно пережило свой предмет: ветка появилась в контракте вместе с
видом шлюза и якорем размещения. Утверждение про край снято, ограничение модуля осталось —
разница между ними и есть работа, которую предстоит сделать.
:::

Проверок входа у этой переменной **нет намеренно**. Годность записи CIDR и адреса проверяет
провайдер тем же разбором, каким их читает край, и называет виновный индекс; проверка на
HCL была бы вторым, более слабым предикатом того же предмета — а расходятся такие пары
молча и именно там, где расхождение не видно.

## Сетевые интерфейсы

Ключ карты — имя интерфейса в проекте.

| Поле записи | Назначение |
|---|---|
| `subnet` | КЛЮЧ карты `subnets`. Идентификатор здесь не принимается. |
| `security_group_ids` | По умолчанию **пуст**, и это значит «ни одной группы». |
| `v4_address_ids` · `v6_address_ids` | Не более одного адреса каждого семейства. |
| `description` · `labels` | Описание и метки. |

Привязки к машине здесь нет и быть не может: край отвергает `instance_id` и `index` на
создании интерфейса синхронно и с именем поля. Подключение выполняет владелец машины —
только он может проверить инварианты привязки (та же зона, принадлежность машины, номер
слота).

Группу сети по умолчанию модуль в `security_group_ids` не подставляет: при умолчании
`create_default_security_group = false` её не существует вовсе, и подставилась бы пустая
строка — ссылка в никуда. А там, где её заводят, она разрешает любой протокол отовсюду в
обе стороны: привязка **такой** группы к интерфейсу — решение вызывающего, а не умолчание
модуля.

Пустая строка в любом из трёх списков отвергается: край ответит на неё отказом об
отсутствии ресурса, которого вызывающий не называл.

Несколько адресов одного семейства набираются несколькими интерфейсами.

## Адреса

Ключ карты — имя адреса в проекте. Адрес принадлежит **проекту**, а не сети: поля сети в
его контракте нет вовсе. С сетью этого модуля его связывает подсеть — внутренний адрес
выдаётся из её блоков.

Вид задаётся **ровно одной** спецификацией из четырёх — `external_ipv4`, `internal_ipv4`,
`internal_ipv6`, `external_ipv6` — и после создания **не меняется**: в маске изменения края
спецификации нет вовсе, поэтому правка вида, зоны, подсети или самого адреса пересоздаёт
ресурс. Меняются только имя, описание, метки и защита от удаления.

`address` в любой спецификации необязателен: не задан — край выдаст адрес сам (внутренний
из блоков подсети, внешний из пула). Заданный внутренний обязан лежать в блоках своей
подсети.

**Пустая зона внешнего адреса законна** — это адрес из глобального пула, зоне не
принадлежащий. Существование названной зоны модуль не проверяет: справочник зон ведёт край,
а выводить его содержимое разбором строк запрещено — такая проверка молча проходила бы
всегда, выглядя исполненной.

Адреса в **чужой** подсети здесь нет намеренно: такой адрес к сети модуля не относится и
заводится ресурсом рядом с модулем, где его подсеть видна вызывающему целиком.

:::warning `deletion_protection` провайдер НЕ снимает сам
Пока защита включена, край отказывает в удалении адреса. Поставьте `false`, примените, и
лишь затем удаляйте. Отказ `destroy` при включённой защите — правильный отказ.
:::

## Шлюз общего исхода

| Имя | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `create_gateway` | `bool` | `false` | Заводить ли шлюз. |
| `gateway_name` | `string` | `null` | `null` — вывести из имени сети с суффиксом `-gw`. |
| `gateway_description` · `gateway_labels` | — | `""` / `{}` | Описание и метки шлюза. |

Умолчание `false` — сохранение поведения: до сих пор модуль сеть без шлюза создавал, и
вызывающий, ничего не менявший, не должен получить новый ресурс от обновления модуля.

**Флаг заводит ресурс, а не открывает исход.** Сам по себе шлюз трафик никуда не
направляет — направляет таблица маршрутов, называющая его следующим узлом. Читать флаг
как выключатель доступа наружу нельзя. (И см. выше: средствами Terraform назвать шлюз
следующим узлом сегодня нечем — ветка есть у края, но не у оснастки.)

**Шлюз принадлежит проекту, а не сети:** ссылки на сеть у ресурса нет вовсе. Поэтому два
вызова этого модуля в одном проекте с включённым флагом заведут **два** шлюза, а не поделят
один. Ребра графа между шлюзом и сетью не возникает — снос идёт независимо; дописать
`depends_on` ради видимости порядка нельзя, это объявило бы гарантию, которой край не даёт.

Имя шлюза и имя сети подчиняются **одной** форме платформы — DNS label по RFC 1123
(`^[a-z0-9]([-a-z0-9]{0,61}[a-z0-9])?$`): строчные латинские буквы, цифры и дефис, длина до
63. Отдельной, более строгой формы у шлюза нет, поэтому имя, годное для сети, годится и для
выведенного из него имени шлюза. Проверка **выведенного** имени стоит предусловием у самого
шлюза, а не в переменной: она смотрит на сочетание двух переменных и обязана молчать, пока
шлюз не заводят.

:::caution Предусловие модуля строже формы края на один знак
Край принимает **цифру первым знаком** (`9net` — законное имя), а предусловие модуля
требует буквы. Поэтому сеть с именем от цифры и включённым флагом упирается в отказ модуля
на `plan`, хотя край такое имя шлюза принял бы; обходится явным `gateway_name`.

Само имя **сети** модуль не проверяет вовсе: негодное по форме имя проходит `plan` и
отвергается краем уже на `apply`.
:::

Отдельные переменные для меток шлюза заведены не для симметрии: `labels` объявлена метками
**сети**, и распространить её на новый ресурс значило бы сменить смысл переменной у тех,
кто модуль уже вызывает, — молча и на применении, а не на чтении.

Выход `gateway_id` — `null`, когда шлюз не заводили. Это «ресурса нет», а не «неизвестно».

## Проверки входа

Все они срабатывают на `plan`, до обращения к краю:

- пустой `ipv4_cidr_blocks`;
- у подсети задано не ровно одно из `zone_id` и `region_id`;
- подсеть ссылается на ключ, которого нет в `route_tables` (отказ перечисляет известные
  ключи);
- у подсети заданы и `route_table`, и `route_table_id`;
- интерфейс ссылается на ключ, которого нет в `subnets`;
- у интерфейса больше одного адреса IPv4 или IPv6;
- пустая строка среди идентификаторов интерфейса;
- у правила группы задано не ровно одно из трёх видов цели;
- у правила протокол задан и именем, и номером;
- цель правила задана пустой строкой;
- у адреса задано не ровно одно из четырёх видов;
- внутренний адрес ссылается на ключ, которого нет в `subnets`;
- `gateway_name` не подходит под форму имени шлюза — как заданное явно, так и выведенное из
  имени сети.

## Выходы

| Имя | Что содержит |
|---|---|
| `network_id` | Идентификатор сети; по нему выполняется импорт. |
| `default_security_group_id` | Группа по умолчанию — **пустая строка**, когда её не заводили. |
| `default_route_table_id` | Таблица маршрутов, созданная краем вместе с сетью. |
| `subnet_ids` · `subnets` | Идентификаторы и подсети целиком: размещение, таблица маршрутов, блок адресов. |
| `security_group_ids` | Идентификаторы групп по ключам карты. |
| `route_table_ids` | Идентификаторы таблиц по ключам карты. |
| `cidr_group_ids` · `cidr_groups` | Идентификаторы наборов по ключам карты и наборы целиком: состав по семьям и посчитанное краем число членов. |
| `network_interface_ids` · `network_interfaces` | Идентификаторы и интерфейсы целиком: подсеть, группы, статус. |
| `address_ids` · `addresses` | Идентификаторы и адреса целиком: вид по данным края и сам выданный IP. |
| `gateway_id` | Идентификатор шлюза; `null`, когда шлюз не заводили. |

`status` интерфейса выведен наружу намеренно: `AVAILABLE` означает «интерфейс создан, но ни
к какой машине не подключён», а `ACTIVE` — «подключён и трафик идёт». Подключение выполняет
владелец машины, вне этого модуля, и это единственное место, где итог его действия виден без
обращения к краю.

У адреса выход собирает сам выданный IP из **выбранной** спецификации: адрес живёт внутри
ветки, а какая ветка выбрана, знает только конфигурация. `type` и `ip_version` называет
край — они и подтверждают, что выбранная ветка означала то, что предполагалось.

`route_table_ids` подсетям **этого** модуля не нужны: там таблица называется ключом, и
идентификатор модуль подставляет сам. Они для подсетей, заводимых вне модуля.

## Что модуль намеренно не делает

- **Не создаёт машины и не подключает к ним интерфейсы.** Подключение — действие владельца
  машины.
- **Не заводит группу безопасности по умолчанию без явной просьбы** (см. выше).
- **Не удаляет чужие ресурсы ради успеха своего плана.** Если сеть не пуста, `destroy`
  вернёт отказ платформы дословно — `Network <id> is not empty`, — а не станет вычищать то,
  чем модуль не управляет.

## Чем проверяется сам модуль

У модуля есть пробы: `tests/wiring.tftest.hcl`, гоняются командой `tofu test` из каталога
модуля. Провайдер в них подменён (`mock_provider`), то есть край не участвует — падение
означает ошибку в модуле, а не состояние стенда.

Проб **45**, из них **24** отрицательные. Положительные закрепляют **связывание**: подсеть
ссылается на сеть по идентификатору, региональная подсеть не несёт зоны, группа и таблица
заводятся в сети модуля, поля правила и маршрута доезжают до ресурса без подмены и в
написанном порядке, подсеть берёт таблицу по ключу карты, интерфейс и внутренний адрес
берут подсеть по ключу, адреса попадают в блок своего вида, группа без правил остаётся
закрытой, шлюз отсутствует по умолчанию и появляется по флагу, явное имя шлюза сильнее
выведенного, метки шлюза отделены от меток сети, предусловие шлюза молчит, пока
шлюз не заводят. Отрицательные закрепляют **отвержение** — все условия из раздела выше.

Второе не менее важно первого: без отрицаний положительные пробы зеленели бы и на модуле,
принимающем что угодно.

Конвейер требует пробы от КАЖДОГО модуля и падает на модуле без них.
