# Модуль `vpc-network`

Модуль описывает сеть вместе с её подсетями — типовую единицу, которую заводят целиком, а
не по частям.

## Использование

```hcl
module "vpc" {
  source = "github.com/PRO-Robotech/kacho//terraform/modules/vpc-network"

  project_id       = var.project_id
  name             = "production"
  description      = "сеть production-контура"
  ipv4_cidr_blocks = ["10.10.0.0/16"]

  subnets = {
    "production-a" = {
      zone_id           = "ru-central1-a"
      ipv4_cidr_primary = "10.10.1.0/24"
    }
    "production-b" = {
      zone_id           = "ru-central1-b"
      ipv4_cidr_primary = "10.10.2.0/24"
    }
    "production-anycast" = {
      region_id         = "ru-central1"
      ipv4_cidr_primary = "10.10.9.0/24"
    }
  }
}
```

## Входные переменные

| Имя | Тип | Обязательна | Назначение |
|---|---|---|---|
| `project_id` | `string` | да | Проект-владелец |
| `name` | `string` | да | Имя сети в пределах проекта |
| `ipv4_cidr_blocks` | `list(string)` | да, непустой | Супернет сети |
| `subnets` | `map(object)` | нет | Подсети; ключ — имя подсети |
| `description` | `string` | нет | Описание сети |
| `labels` | `map(string)` | нет | Метки сети |

### Почему `ipv4_cidr_blocks` обязателен и непуст

Сеть без объявленного супернета **не примет ни одной подсети**: край отвергнет её словами
`network declares no IPv4 supernet`. Модуль создаёт сеть вместе с подсетями, поэтому
допускать порядок «сеть сейчас, супернет потом» ему нельзя — проверка стоит прямо в
переменной и срабатывает до обращения к платформе.

### Почему у подсети ровно один якорь размещения

Зональная и региональная подсети — разные вещи, а не два способа сказать одно. У
региональной (anycast) зоны нет вовсе, и зональные проверки согласованности к ней не
применяются. Модуль проверяет это условие сам:

```
У каждой подсети задаётся ровно одно из zone_id и region_id.
```

## Выходные значения

| Имя | Что содержит |
|---|---|
| `network_id` | Идентификатор сети; по нему выполняется импорт |
| `default_security_group_id` | Группа безопасности, созданная краем вместе с сетью |
| `default_route_table_id` | Таблица маршрутов, созданная краем вместе с сетью |
| `subnet_ids` | Карта «имя подсети → идентификатор» |
| `subnets` | Подсети целиком: идентификатор, размещение, таблица маршрутов, блок адресов |

## Порядок удаления

Подсети ссылаются на сеть по идентификатору, поэтому граф зависимостей строится сам, и
`destroy` снимает подсети раньше сети.

:::warning Не полагайтесь на «неверный порядок даст ошибку»
Часть связей платформы при неверном порядке удаления **не падает, а молча обнуляется** —
например, ссылка подсети на таблицу маршрутов. Порядок обязан держаться графом ссылок, а
не наблюдением за ошибками. Поэтому в модуле подсеть ссылается на `network_id` ресурса, а
не на переменную с тем же значением.
:::

## Что модуль намеренно не делает

- **Не создаёт группы безопасности и таблицы маршрутов.** Край создаёт их вместе с сетью
  сам, и их идентификаторы доступны в выходных значениях.
- **Не удаляет чужие ресурсы ради успеха своего плана.** Если сеть не пуста, `destroy`
  вернёт отказ платформы дословно — `Network <id> is not empty`, — а не станет вычищать
  то, чем модуль не управляет.
