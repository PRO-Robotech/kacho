# Subnet

**Subnet** — это диапазон адресов внутри сети, из которого выделяются внутренние IP.
Подсеть отвечает на практический вопрос «откуда брать адреса для ресурсов»: вы задаете
один или несколько CIDR-блоков (IPv4 и/или IPv6), и из них автоматически выделяются
внутренние адреса (`Address`) и сетевые интерфейсы (`NetworkInterface`). Так вы сами
планируете адресацию приложения — разбиваете сеть на сегменты под разные зоны, ярусы
или команды.

Способ размещения подсети выражен дискриминатором `placementType`. Он **output-only**:
вызывающий задаёт `zoneId` ЛИБО `regionId`, а дискриминатор сервер выводит и возвращает при
чтении. Immutable на всю жизнь подсети:

- **ZONAL** — подсеть живет в одной зоне доступности (`zoneId`); адреса unicast,
  привязаны к зоне. Классический сегмент под ресурсы конкретной зоны.
- **REGIONAL** — подсеть region-scoped (`regionId`); ее префикс анонсируется
  active-active из здоровых зон региона (anycast). Используется, когда адрес должен быть
  доступен из всего региона без привязки к одной зоне (например, региональный VIP
  network load balancer).

Ровно одно из полей `zoneId` / `regionId` заполнено — в зависимости от `placementType`.
Подсеть принадлежит одной виртуальной сети (`networkId`). Платформа гарантирует, что
**CIDR-блоки подсетей одной сети не пересекаются** (контроль на уровне БД,
EXCLUDE-constraint) — это исключает «двойную адресацию» и связанные с ней инциденты еще до
того, как адрес будет кому-то выдан. Подсеть может быть привязана к таблице маршрутов
(`routeTableId`); если ее не указать — выполняется авто-ассоциация с самой ранней
`RouteTable` сети.

`networkId`, `placementType`, `zoneId` и `regionId` — **immutable** после создания
(сегмент нельзя «переехать» в другую сеть, зону, регион или сменить тип размещения). Набор
CIDR-блоков меняется **не** через `Update` (там они отвергаются как immutable), а через
специальные действия `:add-cidr-blocks` / `:remove-cidr-blocks` — отдельные операции, чтобы
расширение/сжатие адресного пространства было явным и проходило проверку на пересечения.

:::info Идентификатор и размещение
ID подсети — префикс `sub` + 17 символов crockford-base32 (например,
`sub7k2m9p4q1r8s3t6vw`). Зона (`zoneId`) и регион (`regionId`) — ресурсы отдельного домена
`kacho-geo`; их существование проверяется при `Create` синхронным вызовом `kacho-geo`
(несуществующая зона/регион → `InvalidArgument "unknown zone id '<id>'"` /
`"unknown region id '<id>'"`, недоступность домена → `Unavailable`).
:::

## Create

<ApiOperation method="POST" endpoint="/vpc/v1/subnets" async>

Создает подсеть в указанной сети. Возвращает `Operation` (async).

`placementType` **не задаётся вызывающим** — он выводится сервером из того, что из двух полей
размещения заполнено: `zoneId` → **ZONAL** (подсеть в одной зоне), `regionId` → **REGIONAL**
(префикс анонсируется по региону). Непустой `placementType` в теле отвергается синхронно:
`InvalidArgument "placement_type is server-derived; set zone_id or region_id instead"`.
Оба поля размещения сразу или ни одного — тоже синхронный отказ.

Хотя бы один адресный якорь обязателен: `ipv4CidrPrimary` либо `ipv6CidrPrimary`. Пустыми оба
быть не могут (из такой подсети нельзя выделить ни один адрес), одно — можно: v4-only и v6-only
подсети законны. Размер IPv4-подсети — в диапазоне `/16../28` включительно с обеих сторон.

Несуществующая зона/регион отклоняются **синхронно** (`InvalidArgument`); несуществующая сеть, дубль имени
и пересечение CIDR — тоже синхронно (`NOT_FOUND "Network %s not found"` / `ALREADY_EXISTS` /
`FAILED_PRECONDITION "Subnet CIDRs can not overlap"`). В worker'е: проверка существования
проекта → вставка Subnet (FK + EXCLUDE + CHECK-размещения — атомарный backstop) → запись
событий в outbox.

**Диапазоны, зарезервированные платформой.** Часть адресного пространства обслуживает саму
платформу. Подсеть, объявленная поверх такого диапазона, проходила бы все проверки и **не
работала бы**, причём симптом выглядел бы сетевым, а причина лежала бы в перекрытии. Поэтому
объявляемый префикс, пересекающийся со служебным диапазоном, отвергается **синхронно** —
`InvalidArgument`, до создания `Operation`. Форма ответа (префикс в примере — иллюстративный,
в вашем ответе стоит присланное вами значение):

<CodeBlock language="text">
  {dedent`
    ipv4CidrPrimary 192.0.2.0/24 overlaps an address range reserved by the platform
  `}
</CodeBlock>

Что здесь важно знать:

- **Отказ называет ваше поле и ваше собственное значение.** На `Create` вы присылаете
  `ipv4CidrPrimary` / `ipv6CidrPrimary` — их отказ и называет. Индекса здесь нет и не
  бывает: это одиночный якорь, а не набор. Значение в сообщении — ровно то, что вы
  прислали.
- **Этот отказ различим машинно — не разбирайте прозу.** В `details` ответа приходит
  `google.rpc.ErrorInfo` с `reason = "SUBNET_CIDR_RESERVED"`, `domain = "vpc.kacho.cloud"` и
  метаданными `field` / `value` (ваш слот и ваше значение). Автомат, планирующий адресацию,
  ветвится по нему: `SUBNET_CIDR_RESERVED` означает «префикс служебный, берите следующий
  кандидат», прочий `INVALID_ARGUMENT` — «ввод негоден по форме, повтор с другим префиксом
  не поможет». Тон сообщения стабилен, но парсить его не надо и не следует.

<CodeBlock language="json">
  {dedent`
    {
      "code": 3,
      "message": "ipv4CidrPrimary 192.0.2.0/24 overlaps an address range reserved by the platform",
      "details": [
        {
          "@type": "type.googleapis.com/google.rpc.ErrorInfo",
          "reason": "SUBNET_CIDR_RESERVED",
          "domain": "vpc.kacho.cloud",
          "metadata": { "field": "ipv4CidrPrimary", "value": "192.0.2.0/24" }
        }
      ]
    }
  `}
</CodeBlock>

- **Перечень служебных диапазонов не публикуется** — ни в ответе, ни в этой документации,
  ни отдельным методом. В отказе присутствует только присланный вами префикс; диапазонов,
  которых вы не называли, ответ не раскрывает. Признак выше кругов **не убавляет** — он
  делает их различимыми для автомата; это меньше, чем публикация перечня, и это всё, что
  можно дать, не раскрывая служебную адресацию.
- **Перечень задаётся посадкой, а не продуктом.** Он зависит от того, как развёрнута
  платформа, и у разных установок отличается; узнать его состав можно у оператора вашей
  установки — там он объявлен значением `dataplane.reservedPrefixes` в профиле
  развёртывания. Из этого следует практическое правило: планируйте адресацию так, чтобы не
  занимать пространство, которое вам не выдавали, а автоматический подбор стройте на
  признаке `SUBNET_CIDR_RESERVED`, а не на счёте попыток.
- **Пересечение ловится в обе стороны вложенности.** Отвергается и подсеть внутри служебного
  диапазона, и подсеть **шире** него — «взять диапазон побольше» служебные адреса не отдаёт.
  Соседство границами пересечением не считается: подсеть, примыкающая к служебному диапазону
  вплотную, законна.
- Проверка стоит **до** обращения к домену `kacho-geo`: такой префикс не станет законным ни
  при каком ответе о зоне, поэтому отказ приходит раньше и не зависит от доступности соседа.

## Update

<ApiOperation method="PATCH" endpoint="/vpc/v1/subnets/{subnetId}" async>

Изменяет mutable-поля подсети (`name`, `description`, `labels`, `route_table_id`).
Поля `network_id`, `placement_type`, `zone_id`, `region_id` —
hard-immutable (явно в `update_mask` → `InvalidArgument "<field> is immutable after
Subnet.Create"`).

Диапазоны (`ipv4CidrPrimary`, `ipv6CidrPrimary`, `ipv4CidrBlocks`, `ipv6CidrBlocks`),
названные в `updateMask`, — тоже `InvalidArgument "<field> is immutable after
Subnet.Create"`: набор меняется только парой `:add-cidr-blocks` / `:remove-cidr-blocks`.

## AddCidrBlocks

<ApiOperation method="POST" endpoint="/vpc/v1/subnets/{subnetId}:add-cidr-blocks" async>

Добавляет CIDR-блоки к подсети. Это **штатный** способ расширить адресное пространство
(в отличие от `Update`, который диапазоны не меняет вовсе). CIDR'ы внутри запроса не должны
пересекаться между собой (sync-проверка), а также с соседними подсетями той же сети
(EXCLUDE-constraint → `FailedPrecondition "Subnet CIDRs can not overlap"`).

**Диапазоны, зарезервированные платформой — то же правило, что и на `Create`.** `Create` и
`:add-cidr-blocks` — единственные два действия, которыми диапазон подсети **объявляется**
(`Update` держит набор неизменным, `:remove-cidr-blocks` только сужает), поэтому проверка
стоит на обоих: иначе служебный диапазон добавлялся бы к уже созданной подсети вторым
запросом. Отказ синхронный, `InvalidArgument`, до создания `Operation`, и называет слот
присланного набора вместе с вашим значением (префикс ниже — иллюстративный):

<CodeBlock language="text">
  {dedent`
    ipv4CidrBlocks[0] 192.0.2.0/24 overlaps an address range reserved by the platform
  `}
</CodeBlock>

Проверяется **присланный** набор, а не накопленный: уже записанные блоки этот запрос не
объявляет, поэтому расширение подсети, созданной до появления диапазона в перечне, не
блокируется задним числом. Перечень служебных диапазонов ответ не раскрывает — см.
подробности в разделе [Create](#create).

## Сценарии использования

- **Планирование адресации по зонам (ZONAL).** Разбейте сеть на подсети — по одной на
  зону — с непересекающимися диапазонами (`10.0.0.0/24`, `10.0.1.0/24`, …). Из них
  платформа сама раздает внутренние адреса интерфейсам ресурсов.
- **Региональный сегмент (REGIONAL).** Создайте подсеть с `placementType=REGIONAL` и
  `regionId`, когда адрес должен быть доступен из всего региона без привязки к одной зоне —
  например, под региональный VIP network load balancer (префикс анонсируется active-active
  из здоровых зон региона).
- **Расширение без простоя.** Когда диапазона перестает хватать, добавьте новый CIDR-блок
  через `:add-cidr-blocks` — это штатный путь увеличить адресное пространство подсети, не
  пересоздавая ее и не трогая уже выданные адреса.
- **Dual-stack (IPv4 + IPv6).** Задайте и `ipv4CidrBlocks`, и `ipv6CidrBlocks` — интерфейсы
  смогут получать адреса обоих семейств (≤ 1 v4 и ≤ 1 v6 на интерфейс).
- **Аудит занятости.** `ListUsedAddresses` показывает, какие адреса заняты и какие ресурсы
  на них ссылаются (`references`) — удобно перед сжатием диапазона или удалением подсети.

## Подводные камни

:::caution Пересечение CIDR
CIDR-блоки подсетей одной сети не должны пересекаться. Конфликт ловится на уровне БД
(EXCLUDE-constraint) и при `Create` / `:add-cidr-blocks` возвращается синхронно как
`FAILED_PRECONDITION "Subnet CIDRs can not overlap"`. Блоки внутри одного запроса тоже не
должны перекрывать друг друга.
:::

:::caution Удаление непустой подсети
Подсеть нельзя удалить, пока в ней есть внутренние `Address` или `NetworkInterface` — FK
`ON DELETE RESTRICT` отдает `FAILED_PRECONDITION`. Сначала освободите ресурсы в порядке
`NetworkInterface → Address`, затем удаляйте подсеть.
:::

:::caution placement_type задается один раз
`placementType` обязателен при `Create` (`UNSPECIFIED` → `InvalidArgument`, в `ZONAL` не
дефолтит) и immutable. Для `ZONAL` заполняется `zoneId`, а `regionId` должен быть пуст; для
`REGIONAL` — наоборот. Лишнее поле размещения → `InvalidArgument`
(`"region_id must be empty for ZONAL placement"` / `"zone_id must be empty for REGIONAL
placement"`). Сменить тип размещения нельзя — создайте новую подсеть.
:::

:::caution host-биты CIDR обязаны быть нулевыми
Адрес сети должен быть выровнен по маске: `10.0.0.0/24` — корректно, `10.0.0.5/24` →
`InvalidArgument`. Это относится и к `Create`, и к `:add-cidr-blocks`.
:::

:::note CIDR не меняются через Update
В `Update` поля `ipv4CidrBlocks` / `ipv6CidrBlocks`, названные в `updateMask`,
**отвергаются** (`InvalidArgument "<field> is immutable after Subnet.Create"`).
Единственный способ изменить диапазоны — `:add-cidr-blocks` / `:remove-cidr-blocks`. Поля `networkId`,
`placementType`, `zoneId`, `regionId` — hard-immutable: явное указание в `updateMask` →
`InvalidArgument`.
:::

## Рекомендации

- **Закладывайте запас, но не дробите чрезмерно.** Выбирайте размер блока с учетом роста
  числа интерфейсов в зоне; расширяться позже можно через `:add-cidr-blocks`.
- **Непересекающаяся раскладка заранее.** Спланируйте диапазоны подсетей одной сети так,
  чтобы они гарантированно не накладывались — это избавит от `FAILED_PRECONDITION` при
  массовом создании.
- **Освобождайте перед сжатием.** Перед `:remove-cidr-blocks` убедитесь через
  `ListUsedAddresses`, что в удаляемом диапазоне нет занятых адресов.
