# Намеренные дизайн-решения Kachō VPC

Это **не баги** и **не задачи** — осознанные решения формы API и поведения, которые
могут удивить ревьюера. Файл существует, чтобы их не «фиксили» по второму разу. Все
решения описаны в собственных терминах Kachō (конвенции API — `06-conventions.md`).

## 1. NetworkInterface — first-class ресурс VPC

NIC — отдельный ресурс домена VPC (`NetworkInterfaceService`
Get/List/Create/Update/Delete/ListOperations), а не вложенная часть Instance.
Принадлежит `Subnet`, ссылается на `Address`-ресурсы по id, привязывается к
Compute-Instance через `nic_id`. Multi-IP на VM собирается из нескольких NIC.
Проекция — lean, control-plane-only (инфра/data-plane полей нет).

## 2. Подсеть может быть одной семьи — но не «без CIDR вообще как норма»

CIDR-якорь задаётся **на Create** и immutable: `ipv4_cidr_primary` / `ipv6_cidr_primary`.
Пустым может быть **один** из двух (v4-only и v6-only подсети легальны); тогда аллокация
отсутствующей семьи в эту подсеть даёт `FailedPrecondition "subnet %s has no IPv4 CIDR"`.
Дополнительные диапазоны — только через `:add-cidr-blocks`.

> [!warning] Здесь стояли два пункта об «опциональности», и оба пережили свой предмет
> Первый — «`Subnet.v4_cidr_blocks` опционально на Create»: поля с таким именем в контракте
> Create больше нет, его номер зарезервирован (VPC-1 F7), место занял immutable-якорь.
> Второй — «`SecurityGroup.network_id` опционально, network-less SG легальна»: use-case
> отвергает пустое значение синхронно, а комментарий колонки в baseline-миграции называет
> её `mandatory and immutable after Create`.
> Реестр намеренных решений опаснее прочей документации ровно этим: он существует, чтобы
> решения «не фиксили по второму разу», — то есть запись здесь **запрещает** приводить
> поведение к тому, что записано неверно.

## 3. IPv6 — симметрично IPv4

Симметрия — требование, а не наблюдение: предикат, который читает только одну
семью, оставляет зеркальную половину без защиты (так `AddressPool:removeCidrBlocks`
считал занятость лишь по IPv4, а глобальная уникальность внешнего адреса
энфорсилась лишь в полосе IPv4). При добавлении проверки на набор, принимающий
обе семьи, читать обе — обязательно.

`:add-cidr-blocks`/`:remove-cidr-blocks` принимают обе семьи (`ipv4_cidr_blocks` и
`ipv6_cidr_blocks`); у сети — `ipv4_cidr_blocks`/`ipv6_cidr_blocks` супернета. Internal IPv6 —
`Address.internal_ipv6_address` oneof + `InternalAddressService.AllocateInternalIPv6`;
внешний IPv6 — `AllocateExternalIPv6` и глобальная уникальность на DB-уровне (0026),
зеркально IPv4.

## 4. ListOperations переживает удаление ресурса

Для Network/Subnet/Address/NetworkInterface `ListOperations` отдает историю даже
после удаления самого ресурса: precondition `repo.Get` убран (handler best-effort —
жив → project-ownership; NotFound → пропуск). Строки `operations` не каскадятся.
RouteTable/SecurityGroup/Gateway по-прежнему гейтят на `repo.Get`.

## 5. Geography (Region/Zone) — не в kacho-vpc

Канонический владелец Geography — leaf-сервис `kacho-geo`. В `kacho-vpc` `zone_id`-колонки
(`subnet.zone_id`, `address_pool.zone_id`, `address.external_ipv4.zone_id`) — `TEXT`-id
без FK, валидируются на request-path через `geo.v1.ZoneService.Get`.

## 6. REST-пути неоднородны по форме — НЕ нормализовать

Стиль `google.api.http`-аннотаций в `proto/kacho/cloud/vpc/v1/` намеренно смешанный:
kebab у custom-методов (`:addCidrBlocks`), child-list под ресурсом, camelCase у
top-level (`routeTables`, `securityGroups`, `addressPools`), `/operations/{id}` без
`/vpc/v1/`-префикса. Это зафиксированная форма поверхности API — «причесывание»
сломает контракт. Карта путей — `04-api-surface.md`.

## 7. Тело ошибки JSON-transcoding — стандартный JSON `{code,message}`

На неверный тип JSON-поля (`description`=число, `labels`=строка, oneof `address_spec`
задан дважды) api-gateway отдает стандартный grpc-gateway error-handler с JSON
(`400` + непустое тело). Кастомный error-handler ради иного формата тела не делаем.
Кейсы `*-CR-VAL-DESC-INT-TYPE` / `*-CR-VAL-LABELS-STRING-TYPE` / `ADR-CR-VAL-BOTH-SPEC` —
defensive (фиксируют `400` + непустое тело).

## 8. Пустое repeated-поле в List-ответе — отдается `[]`

`GET /vpc/v1/networks?projectId=<пустой>` → `{"networks":[]}` (а также
`nextPageToken:""`). Это `EmitUnpopulated`-настройка grpc-gateway marshaller'а; смена
затронула бы все ответы (напр. `done:false` в Operation), blast radius неоправдан.
Кейсы `NET-LST-*` — defensive (`j.networks || []`).

## 9. ~~Subnet.Update с `v4CidrBlocks` в mask — no-op~~ — СНЯТО вместе с предметом

Решение состояло в том, чтобы **принять и не применить** CIDR в `Update`. Сегодня принимать
нечего: в `UpdateSubnetRequest` CIDR-полей нет вовсе, их номера зарезервированы (VPC-1 F7).
То есть исход выбран третий из трёх законных — «снять с контракта», а не «молча
игнорировать»; именно его `api-conventions.md` §«Принято-и-проигнорировано» и называет
предпочтительным по умолчанию.

Действующее поведение: `ipv4_cidr_primary`/`ipv4_cidr_blocks` (и v6) в `update_mask` →
sync `InvalidArgument "ipv4_cidr_primary is immutable after Subnet.Create"` —
immutable-switch стоит **до** `corevalidate.UpdateMask`, чтобы ответ нёс контракт-тон
immutable, а не generic «unknown field». Кейс `SUB-UPD-STATE-IMMUTABLE-CIDR` это и
проверяет; кейс, ожидающий здесь `200`, — находка, а не подтверждение.

Запись оставлена, а не удалена, потому что решение переменилось на противоположное, и
следующий читатель обязан увидеть **какое** и **почему**, а не пустое место.

## 10. OperationService.Get/Cancel с bad id

malformed id → `InvalidArgument` с текстом `invalid operation id "<X>"` (кавычки
двойные: их ставит глагол `%q` производителя, и цитата с одинарными здесь стояла —
она не совпадала с ответом края ни одним прогоном, #1400); well-formed id (известный
prefix, но бэкенд не подключен) → `NotFound "operation <X> not found"`; id с prefix
домена с подключенным бэкендом → роутится туда.

Текст второй полосы — не выбор края: он приходит из общего производителя
`operations.NotFoundStatus`, которым отвечает и владелец операции. Обе полосы
клиент видит на одном адресе, поэтому различие хоть в один байт отличало бы «нет
доступа» от «не существует» и называло бы, какие бэкенды край держит
подключёнными. Прежде край писал этот текст сам, с прописной буквы (#1370).

Реализация — `gateway/internal/opsproxy/proxy.go`
(каталог края в монорепо; прежнее имя отдельного репозитория края координатой не является
и здесь не воспроизводится).

## 11. Два error-mapper'а НЕ слиты в общий classifier — намеренно

Общий repo-sentinel→gRPC classifier — `serviceerr.classifyRepoSentinel`
(обёртки `MapRepoErr` для публичных сервисов и `MapRepoErrLeakSafe` для
Internal/admin-handler'ов). В него **сведены** три бывших full-switch дубликата
(`MapRepoErr`, `handler.internalMapErr`, `addresspool.mapPoolErr`). Ещё два
mapper'а оставлены отдельными **осознанно**:

- **`handler.mapAllocErr`** (`internal_address_allocate_handler.go`) — политика
  IPAM-allocate-пути намеренно **у́же** (compute→vpc внутренний edge): классифицируется только
  `ErrNotFound`, все прочие repo-ошибки (в т.ч. `ErrPoolNotResolved`,
  `ErrPoolExhausted`, `ErrInvalidIPv4`) сворачиваются в `Internal "internal
  allocator error"`. Это **другая** политика, чем superset-classifier
  (`ErrPoolNotResolved`→`FailedPrecondition`): маппинг на внутреннем edge влияет
  на retry-логику вызывающего Compute, менять его в рамках чисто-рефакторинга
  нельзя. Дублирования switch'а нет — функция узкая (NotFound + passthrough +
  fallback).
- **отображение repo-ошибки операции в код** (`pkg/operations/operationspb/handler.go`, общий слой) — оперирует sentinel'ами
  **другого семейства**: `operations.ErrNotFound` / `operations.ErrAlreadyDone`
  из `pkg/operations`, а не `repo.Err*`. К repo-sentinel classifier'у
  отношения не имеет.

Если появится необходимость дать IPAM-allocate-пути богаче классификацию — это
поведенческое изменение внутреннего edge (нужен отдельный тикет + согласование с
Compute-retry), а не «причёсывание» дубликата.

## 12. `authn.trusted-forwarder=true` без server-mTLS — осознанный escape-hatch

В `authn.mode=production` (non-strict) публичный `:9090` listener принимает
**переданную** личность вызывающего как обычные метаданные соединения — то есть без
криптографической привязки этой личности к самому соединению, — **если** оператор явно
выставил `authn.trusted-forwarder=true` и НЕ включил public server-mTLS. Это
**намеренный** escape-hatch для деплоя за аутентифицирующим forwarder'ом /
service-mesh, который сам терминирует identity до `:9090` (типовой ingress-mTLS /
SPIFFE-mesh паттерн).

Гардрейлы, которые делают это безопасным-by-default:

- `authn.trusted-forwarder` по умолчанию `false` (fail-closed) — plaintext-
  principal без mTLS требует **явного** opt-in оператора.
- `ValidateServerMTLS` в production требует **ЛИБО** `PublicServerMTLS.Enable`,
  **ЛИБО** `trusted-forwarder=true` — «ни того ни другого» = отказ старта.
- `authn.mode=production-strict` **игнорирует** флаг: server-mTLS обязателен
  всегда (escape-hatch не действует). Для сред, где cryptographic binding identity
  к соединению обязателен, — это правильный режим.
- Круг тех, кто вправе **передавать** личность, сужается отдельно от этого флага —
  непустым allow-list'ом личностей клиентского сертификата (`cfg.TrustedForwarders()`
  → `grpcsrv.WithTrustedForwarders`, замок `trusted_forwarders_test.go`), и посадка
  сообщает это измерение о себе в самоотчёте (`cmd/vpc/bootposture.go`). Причина, по
  которой список обязан быть непустым, а не «может быть»: контракт corelib сужает
  круг **только когда список непуст**, а на пустом отвечает «доверяем» любому пиру,
  прошедшему проверку сертификата — то есть пустой список означает «не сужаем», а
  вовсе не «запрещаем».
- При активном escape-hatch на boot'е печатается WARN.

Trade-off осознан: при `trusted-forwarder=true` личность вызывающего не связана с
соединением криптографически, поэтому безопасность опирается на сетевую изоляцию
`:9090` (NetworkPolicy / mesh-sidecar) плюс allow-list выше — доступ к листенеру в
обход forwarder'а обесценивал бы принятую личность (CWE-290). Кто не может
гарантировать сетевую изоляцию — использует `production-strict` (server-mTLS).
Дефолт менять на «всегда требовать mTLS» нельзя: это сломало бы поддерживаемые
mesh-деплои, где identity терминируется вне процесса.

## 13. Dev-посадка снимает authN/authZ на internal-листенере — и потому запрещена вне локальных фикстур

В dev-посадке (не-production режим при неподключённом authz-эндпоинте) authz-интерсептор
не навешивается вовсе — только WARN, — а AuthN-guard принципала не требует. Следствие
ровно такое, как звучит: на internal-листенере admin-поверхности и чтения, несущие
инфра-поля, отвечают **без** аутентификации и авторизации. Это **намеренное**
dev-поведение (локальный стенд / port-forward / тесты без поднятого kacho-iam), и
единственное, что делает его терпимым, — то, что развёрнутый стенд в этой посадке
не работает (гардрейлы ниже) и работать не должен (core rule #16: production-mode
обязателен ВЕЗДЕ, включая локальный стенд).

Production жёстко защищён и это **не** обходится:

- `Config.Validate` (`internal/apps/kacho/config/validate.go`) **отказывает в старте**,
  если в production не задан authz-эндпоинт — анонимный admin в production невозможен.
  Там же — требование непустого круга отправителей чужой личности, причём **на любом**
  старте, а не только в боевом режиме: вне production пустой круг остаётся возможным, но
  как явный опт-ин, который надо попросить.
- `ValidateServerMTLS` требует internal `:9091` server-mTLS в **ЛЮБОМ**
  production-режиме (не только strict; SEC-hardening r6 2026-07-05) — internal —
  это service→service, mTLS обязателен, trusted-forwarder escape-hatch на него не
  распространяется. Без mTLS на internal старт в production **отказывает**.
- Internal-only ресурсы (`AddressPool`, `VRFID`-несущий `GetNetwork`) по контракту
  живут только на cluster-internal `:9091`, который не публикуется на external TLS
  endpoint и не проксируется api-gateway на публичную поверхность (Запрет #6).

Требование к оператору: `:9091` в любом shared/staging окружении должен быть за
NetworkPolicy (cluster-internal), а authz включается выставлением `authz.iam-endpoint`.
«Скопировали dev-values на общий стенд» — конфиг-ошибка оператора, а не дефолт:
production-дефолт (`authn.mode=production`) fail-closed.

## 14. `cmd/vpc/main.go:runServe` — единый линейный composition root, намеренно длинный

`runServe` длинный (весь boot-sequence в одной функции): signal-setup, пулы
master/slave, ops-repo, метрики, mTLS load+validate, dial'ы vpc→iam / vpc→geo /
authz, list-filter, registrar/drainer, два gRPC-listener'а, graceful-shutdown.
Правило воркспейса `architecture.md` **предписывает** `cmd/<svc>/main.go` (здесь —
`cmd/vpc/main.go`) как **единственное** место wiring
(composition root) — размазывать инициализацию по пакетам запрещено. Длина —
следствие этого правила плюс плотных inline-комментариев с security-обоснованием
каждого fail-closed гардрейла (ValidateServerMTLS, mTLS-creds-ветвления).

> Прежняя редакция называла здесь третьим примером предупреждение аварийного
> обхода. Ручки нет: она снята вместе с переходом на общий носитель контура, и
> состояние, которое она включала, больше не представимо — ребро решения о
> доступе требуется в любом режиме. Пример убран, а не переписан: перечислять
> снятое среди действующих обоснований значит объяснять длину корня тем, чего в
> нём не осталось.

Тело — почти линейная последовательность `create → defer Close()` без глубокого
ветвления; порядок `defer`-ов (pool/conn Close, cancel) значим и завязан на
scope самой `runServe`. Когезивные под-шаги уже вынесены в помощники
(`buildAuthorizeConn` / `buildListFilter` / `buildSyncRegistrar` /
`startRegisterDrainer` / `buildServices`). Дальнейшее «дробление ради длины» без
теста на composition root несёт ровно тот риск (сбитый порядок `defer`/bind-до-
guardrail), от которого предостерегает сам ресурс — поэтому не делается как
чистый рефакторинг. Новые под-шаги выносятся в помощник, только когда появляется
**самостоятельная** когезивная единица (как перечисленные выше), а не для
сокращения счётчика строк.

## 15. DTO record→proto реестр (`internal/dto`) — единый entry-point, boot-checked

Конвертация `record → proto` идёт через generic-реестр `internal/dto`
(`Transfer(FromTo(rec,&dst))`), а маппинг-реализации (`toproto/*.go`)
регистрируются `init()`-функциями в **выделенном** пакете `internal/dto/toproto`,
который composition root подключает blank-import'ом. Это **намеренный** дизайн, а
не tech-debt:

- Цель — **единый entry-point** вместо россыпи прямых `toproto.Network(d)`-хелперов
  по сервису (пакет-doc `dto/base.go`). Форма вывода proto идентична прямому вызову
  (контракт не меняется).
- `init()` вне `cmd/` — известное отступление от буквы `architecture.md` («no
  init()-side-effects outside cmd/»), но оно **локализовано** в одном dedicated
  пакете `toproto` (не размазано), и разрыв «зарегистрирован ли трансфер» закрыт
  **двумя** гардами: (а) compile-time closed-union `Transferrable` — вызвать
  `Transfer` с незарегистрированной парой `(F,T)` невозможно на этапе компиляции;
  (б) boot-time `dto.MustBeRegistered()` (зовёт composition root на старте) —
  потерянный blank-import → **паника на старте** (fail-fast), а не `codes.Internal`
  на первом live `Get/List`. То есть failure-mode — startup, как у миграций.
- Замена реестра на прямые exported-функции — поведенчески-нейтральный
  рефакторинг ~28 call-site'ов в ~16 файлах; выигрыш спорный (компайл-ошибка
  вместо boot-паники), а blast radius в security-ветке неоправдан. Если делать —
  отдельным clean-refactor тикетом с полным newman-прогоном, не в hardening-pass.

## 16. `AddressFamily` / `ResolvedPool` живут в use-case-пакете `addresspool`

Типы `AddressFamily` (`FamilyV4`/`FamilyV6`) и value-object `ResolvedPool`
объявлены в use-case-пакете `internal/apps/kacho/api/addresspool`
(`helpers.go`), а не в `internal/domain`. Use-case `address` потребляет их через
port `PoolService` (`address/iface.go`), из-за чего `address` импортирует
sibling use-case-пакет `addresspool` (`iface.go` / `allocate.go` / `create.go`)
ради этих определений типов.

Это **осознанный** выбор, а не layering-break: port-абстракция соблюдена
(impl `*addresspool.ResolverService` подключается в composition root; `address`
не зовёт `addresspool` напрямую), а единый источник enum'а family и
resolve-результата — сам pool-resolver, поэтому вызывающий код прозрачно
переиспользует его константы вместо параллельного типа (см. doc-комментарий
`address/iface.go`).

Trade-off: strict Clean Architecture предпочёл бы, чтобы сигнатуры port'а
оперировали `internal/domain`-типами, и тогда слайсы зависели бы только от
domain, а не друг от друга. Вынос `AddressFamily`/`ResolvedPool` в
`internal/domain` — поведенчески-нейтральный cross-package рефактор (трогает
`addresspool` helpers/resolve/poolHasFamily, `address` iface/allocate/create и
их тесты); выигрыш — компайл-когезия, риск в security-hardening-проходе
неоправдан. Делается отдельным clean-refactor тикетом, не здесь.

## 17. ~~`List`/`ListByIDs` в pg-ридерах — рукописные~~ — СНЯТО (`ListByIDs` удалён)

Раньше каждый pg-ридер держал `List` и `ListByIDs` как две почти идентичные
рукописные сборки запроса, расходящиеся только authz-предикатом
`WHERE id = ANY($allowed_ids)`, — и это несло риск дрейфа filter-whitelist'ов
между парой.

Дивергенция **снята**: `ListByIDs` больше не существует ни на одном ресурсе.
Per-object видимость перестала быть SQL-сужением по «списку всего, что subject'у
можно» (перечислительный запрос прежнего внешнего движка прав нёс жёсткий
server-side предел без continuation-token'а, из-за которого собственный ресурс
тенанта мог стать невидимым; сегодня такого RPC на контракте нет) и стала
per-page вопросом «видны ли ЭТИ id»
(`AuthorizeService.BatchCheck`) уже ПОСЛЕ чтения страницы. Подробности —
package-doc `internal/authzfilter`.

Следствие: у каждого ресурса остался ровно ОДИН list-запрос (`List`), пара
whitelist'ов исчезла вместе с риском их расхождения. CI-гейт
`make audit-list-filter` теперь требует в List-пути `FilterVisibleIDs`.

## 18. `Writer.Commit()`/`Abort()` финализируют TX на `context.Background()` — намеренно

`writerImpl.Commit()` / `Abort()` (`internal/repo/kacho/pg/repository.go`) вызывают
`tx.Commit(context.Background())` / `tx.Rollback(context.Background())`, а не request-ctx.
Порт `RepositoryWriter.Commit()`/`Abort()` намеренно БЕЗ ctx-аргумента: терминальная
финализация TX не должна отменяться отменой request-контекста.

Почему так, а не thread-ctx:

- commit по уже-отменённому ctx (клиент отвалился / deadline истёк ПОСЛЕ успешного DML)
  должен **завершиться**, иначе успешная бизнес-операция откатывается «из-за таймаута
  клиента» — хуже, чем чуть дольше подержать соединение. Rollback по Background
  симметричен: abort обязан отработать всегда.
- верхняя граница на всю обработку RPC уже стоит: `handler.Unary/StreamTimeoutInterceptor`
  (request-timeout, outermost) + bounded pgxpool (`pool_max_conns`) + statement/lock
  таймауты БД. Отдельный per-commit timeout добавил бы риск оборвать легитимно-медленный
  commit без выигрыша — blast-radius уже ограничен пулом.

Trade-off: под зависшим primary commit по Background ждёт нижних (pgx/OS) таймаутов, а не
request-deadline. Это осознанный выбор «всегда финализировать TX», а не пропущенная
ctx-propagation.

## 19. Два TTL-кеша сервиса НЕ сведены в общий primitive (третий уехал в общий дом)

В `services/vpc` осталось **два** собственных кеша, и они держат по своей
mutex+map+expiry-реализации намеренно — политики eviction/invalidation разные, а не один
primitive:

- `internal/clients/existence_cache.go` — обобщённый `valueCache[T]`, positive-only, без
  bound (region/zone — low-cardinality: рост ограничен числом зон/регионов в деплое);
- `internal/clients/project_cache.go` — `CachedProjectClient`: true-LRU с раздельными
  positive/negative TTL + clock-injection под unit-тесты.

**Третий кеш сервису больше не принадлежит.** Кеш вердиктов видимости списочной страницы
уехал в общий дом `pkg/listnarrow`; в `internal/authzfilter/` осталось только то, что у
сервиса действительно своё — словарь типов, аудит-строки действий и предикат членства
страницы (`actions.go`, `narrower.go`, `relations.go`), а `Narrower` — псевдоним общего
типа. Посадка кеша задаётся полями `CacheTTL`/`CacheMaxEntries` в `authzfilter.Config`.
Прежняя редакция называла здесь файл с механикой сужения — такого файла в дереве нет:
механика жила в четырёх почти дословных копиях у vpc/compute/nlb/storage и сведена в одну.

Свойство самого кеша вердиктов при этом не изменилось и остаётся важным: кешируются только
**положительные** вердикты, отрицательный не кешируется вовсе. Поэтому свежая выдача видна
сразу, а снятый доступ перестаёт действовать самое позднее через TTL — мгновенное снятие
потребовало бы канала уведомлений от владельца выдач, то есть отдельного межсервисного
ребра и отдельного решения.

Единый `ttlcache[V]`, покрывающий LRU + clock + copy-hook, нёс бы больше
policy-knob-сложности, чем убирает дублирования — net-negative для LEAN-цели. Оба
оставшихся кеша индивидуально оправданы (hot-path RTT-removal) и покрыты `-race`
unit-тестом. Сведение оправдано, только если появится третий с той же политикой.

## 20. Migrator `Dialect`-интерфейс сохранён при единственной реализации — тонкий seam

`internal/apps/migrator` держит интерфейс `Dialect` + `DialectSpec` при единственной
реализации `postgresDialect` (продукт Postgres-only: Postgres 16, database-per-service).
Registry-таблица под один элемент, тип `dialectFactory`, `listDialects` и алиас
`ResolveDialect` **убраны** (LEAN r9b) — `NewDialect` резолвит прямой веткой.

Сам интерфейс оставлен намеренно (НЕ speculative multi-DB задел): `Runner` /
`Config.Dialect` зависят от него — тонкая обёртка делегирует Up/Down/Status/Create без
if-веток, изолируя goose-пакетные глобалки, и держит CLI-контракт `--dialect postgres`
(unknown → ошибка). Второй диалект добавляется реализацией интерфейса, если станет
реальным требованием.

## 21. `InternalNetworkInterfaceService/ListByInstance` авторизуется данными, а не per-RPC Check'ом

Единственный RPC vpc, помеченный `ScopeFiltered` (interceptor не задаёт за него
единичный вопрос модели). Отклонение осознанное, потому что единичного объекта, про
который можно спросить заранее, у этого RPC нет: инстансы называет **вызывающий**, а
ответ касается интерфейсов, у каждого из которых свой владелец.

Прежний вопрос задавался про **отношение глобального справочника** (то самое, которым
читают регионы, зоны, типы дисков) на кластерном singleton'е. Такое отношение по замыслу
выполняется подстановочной выдачей — справочник обязан читать любой аутентифицированный
субъект, иначе платформой нельзя пользоваться. Поэтому проверка формально стояла, а
сужала **ничего**: она отвечала «да» каждому, кто аутентифицирован, то есть означала
«аутентифицирован», а не «авторизован». Ответ этого RPC справочными данными не является,
и авторизации у него фактически не было.

**Тяжесть — чтобы реестр годился для приоритизации.** Радиус был **межаккаунтным**, а не
внутрипроектным: сужения не было ни на одной границе, а не только на ближней. Ответ при
этом несёт не одни идентификаторы — в нём поля привязки интерфейса. Из этих двух величин
и складывался приоритет; без них запись читается как рядовая неточность, а она ею не была.
Перечня полей здесь нет намеренно — для приоритизации хватает уровня границы и того, что
данные не справочные, а поимённый состав ответа превратил бы запись в описание добычи.

Класс общий и не про этот RPC: **прежде чем объявить RPC с кластерным отношением,
спроси, какие выдачи это отношение выполняют.** Если среди них есть подстановочная —
проверка отвечает всем, и годится она только для глобального справочника. Никакой обзор
диффа такую запись от настоящего гейта не отличит: форма у них одинаковая.

Как решается теперь: страница читается из своей БД, и модель спрашивается про
идентификаторы **этой страницы** (`viewer ∪ v_list` на `vpc_network_interface:<id>`,
батчами ≤100) — та же дисциплина, что у публичных List. Плюс три следствия, которые
важно не потерять при рефакторинге:

- метод попадает в `check.ScopeFilteredRPCs()`, поэтому в production
  `config.ValidateListFilter` **не даёт сервису стартовать** без включённого и
  резолвимого list-filter'а — защита не висит на одной конфигурационной ручке;
- пустой subject отсекается **безусловно** (не «если фильтр подключён», как у публичных
  List): у тех остаётся per-RPC Check, а здесь его нет, и привязка fail-closed к наличию
  фильтра вернула бы ровно исходную дыру;
- список `ScopeFiltered`-методов закрыт и сверяется точным равенством
  (`scope_filtered_rpcs_test.go`): новый метод в наборе роняет тест.

Отличие от публичных List (`NetworkService/List` и соседи) намеренное: у них есть
осмысленный объект (`project:<project_id>`), поэтому per-RPC Check там сохранён и
остаётся единственной авторизацией при выключенном фильтре (SEC audit 2026-07-05).

## 22. ~~Gateway — строгий контракт имени, остальные ресурсы — разрешительный~~ — РАСХОЖДЕНИЯ БОЛЬШЕ НЕТ

**Закрыто решением владельца #715.** Форма имени в дереве одна — DNS label по
RFC 1123 — и действует на все девять ресурсов сервиса одинаково.

Раздел оставлен, а не удалён, ради урока о самом жанре. Расхождение объявлялось
**намеренным** и подкреплялось всем, чем принято подкреплять решение: godoc обеих
функций, `domain.Gateway.Validate`, отражение в SDK, unit-тест. Ни один из этих
артефактов не был ложью — и ни один не отвечал на вопрос, ради которого различие
завели: *зачем арендатору два разных правила для одного и того же поля.*

Ответа не было. Две формы означали, что имя, годное у сети, отвергалось у шлюза,
и наоборот, — а запись «различие намеренное» делала это состояние неоспоримым:
следующий читатель видел решение, а не долг. Замер показал ЧЕТЫРЕ формы в дереве,
разошедшиеся по трём осям; из них «намеренной» называлась одна пара.

**Признак для будущих разделов этого файла:** запись о расхождении обязана
называть не только ЧТО отличается и чем это закреплено, но и ЧЕЙ вопрос это
решает. Расхождение, у которого нет такого вопроса, — не решение, а несведённая
копия, и подкрепление артефактами лишь продлевает ей жизнь.

Почему это записано здесь. Общий генератор e2e-кейсов раскатывает набор
`*-CR-VAL-NAME-*` на все шесть ресурсов и до 2026-07-31 утверждал на всех
шести один и тот же исход — «заглавные разрешены контрактом». Для пяти
ресурсов это верно, для Gateway — нет, и прогон в боевой посадке дал ровно одно
упавшее утверждение на `GW-CR-VAL-NAME-UPPERCASE`. Продукт при этом ответил
правильно: `400` с именем поля и полным текстом ограничения. Генератор получил
параметр `strict_name`, кейс Gateway теперь утверждает отказ.

Остальные исходы набора (пустое имя, границы длины, начало с цифры или дефиса,
спецсимволы) у обоих контрактов совпадают, поэтому расходится ровно один кейс.

## 23. `-1` как «любой порт» — второе написание рядом с объявленным `0-65535`

`PortRange.from_port`/`to_port` объявлены в сообщении интервалом `0-65535`, и
контракт там же говорит, как сказать «любой порт»: **не заполнять `ports` вовсе**.
Продукт при этом принимает и второе написание — `-1` на **обеих** границах сразу.

Это отступление, а не расширение интервала: `-1` вне объявленных границ. Оно
старше проверки, которая появилась 2026-07-31 (`validateSGRulePorts`): значение
задокументировано в доменной модели (`SecurityGroupRule.FromPort // -1 = any`),
его пишут интеграционные тесты сервиса и e2e-кейс `SG-URL-VAL-PORT-ANY-MINUS-1`.
Снять его значило бы сделать ломающее изменение под видом ужесточения, поэтому
проверка его сохраняет, а запись существует, чтобы отступление было названо.

Следствия, которые надо знать:

- у «любого порта» два написания — незаполненный `ports` и `-1/-1`. Они **не**
  нормализуются друг в друга: незаполненный сохраняется **нулём** (ветка присваивания
  не выполняется, обе границы остаются в нулевом значении) и на чтении снова
  опускается (`dto/toproto`), а `-1/-1` так и возвращается в ответе. Величина названа
  намеренно: обходимого контроля за ней нет — проверка полей посажена, — а инженерная
  нагрузка есть, и её несёт тот, кто будет писать обратное заполнение;
- поэтому `-1` виден на публичной поверхности, хотя объявленный интервал его не
  содержит. Свести два написания к одному — отдельная работа с миграцией
  хранимых правил и своим acceptance, а не побочный эффект валидации;
- полудиапазон (`-1` на одной границе и число на другой) **отвергается**: «от
  любого до 80» — не диапазон, а два разных утверждения в одном поле.

**Замер 2026-07-31 (что именно придётся мигрировать).** Написаний оказалось не
два, а три, и **нижняя граница объявленного интервала — порт `0` — невыразима**:
её запись в хранилище совпадает с записью «поле не заполнено» (обе суть нуль, см.
первое следствие выше), и различить их нечем. Это тот же класс, что закрыт в §25
для протокола, но здесь у него **нет запасного написания**: там невыразимое
значение адресуется именем, здесь адресовать нечем.

> [!note] Внешний якорь этой записи
> Утверждение проверяется **не чтением кода**, а замком:
> `internal/apps/kacho/api/securitygroup/rule_ports_protocol_test.go` фиксирует, какие
> написания принимаются и какие отвергаются, а e2e `SG-URL-VAL-PORT-ANY-MINUS-1` —
> поведение на публичной поверхности. Якорь добавлен намеренно: без него запись
> утверждала о продукте то, что подтвердить может только чтение исходников, и попадала
> в класс «декларация переживает поведение» — ровно тот, который этот реестр и ловит.
> **Если запись о невыразимости `0` перестанет быть верной, первым обязан покраснеть
> замок, а не читатель.**

Починка требует различать **эти два намерения** в **самом хранилище**
(ключи `FromPort`/`ToPort` в JSONB правила), то есть менять представление и
мигрировать каждое сохранённое правило, попутно решая, какое из трёх написаний
остаётся каноническим.

> [!warning] Пока работа не сделана
> Правило, записанное этой величиной, применяется **не в том объёме**, в каком
> его просили. **Направление** расхождения здесь намеренно не приведено —
> дисциплина публичного репозитория (`security.md`). Механику соседние разделы
> §24 и §25 разбирают открыто как закрытый случай, поэтому обещать сокрытие
> входа было бы обещанием, которое не держится: не держащееся обещание хуже
> обеих крайностей, потому что читатель верит, что деталь лежит где-то ещё.
> Направление и следствие — в
> проверках домена рядом с ограничением из миграции 0027 и в приёмке этой
> работы. До закрытия величину не использовать.
>
> **Формулировки выше намеренно не называют, с чем именно совпадает запись этой
> величины, и как кодируется незаполненный интервал.** Прежняя редакция называла
> и то, и другое — и тогда направление расхождения вычислялось из двух её же
> предложений в этом самом разделе, то есть оговорка про сокрытие не держалась
> ровно там, где формулировалась. Не возвращать: оговорка стоит либо честно, либо
> не стоит вовсе.

Объём, измеренный по дереву: 4 файла прод-кода читают/пишут границы диапазона
(`domain/security_group.go`, `domain/security_group_protocol.go`,
`apps/.../securitygroup/helpers.go`, `dto/toproto/security_group.go`, всего 16
вхождений), 9 файлов тестов, 12 вхождений в наборе e2e-кейсов, плюс функция
ограничения базы из миграции 0027 и обратное заполнение под неё. Это **отдельная
работа со своей приёмкой** (ломающее изменение либо контракта, либо хранимых
данных) — не побочный эффект правки валидации.

## 24. Правило, которое продукт выразить не может, удаляется обратным заполнением

Миграция `0027_security_group_rules_domain` выражает область значений правила
(порты, имя и номер протокола) **ограничением таблицы** — до неё этот инвариант
жил только синхронной проверкой запроса, то есть отвечал одному вызывающему, а
не каждому писателю.

Добавление ограничения валидирует уже лежащие строки, поэтому миграция сначала
**переписывает** наборы правил, записанные до появления проверки: правило с
портом вне `0-65535` (кроме `-1/-1`), с перевёрнутым диапазоном, с именем
протокола вне набора или с номером вне `0-255` **удаляется из набора**.

Почему удаление, а не приведение к границе:

- правила группы **разрешающие** (`Allows ingress/egress traffic`), поэтому
  снятие разрешающего правила доступ не расширяет — это единственная
  нормализация, у которой такое свойство есть by construction;
- «подтянуть 65536 к 65535» выбрало бы порт за вызывающего;
- «заменить несуществующий протокол на любой» **расширило бы** правило до всех
  протоколов — то есть починка стала бы дырой.

Обмен назван, а не спрятан: невыразимое правило исчезает из проекции ресурса.
Альтернатива хуже — строка, которую нельзя ни применить, ни отредактировать:
без заполнения любая последующая запись такой группы (переименование соседнего
правила, добавление или удаление другого) отбивалась бы ограничением, и
единственным путём остался бы полный `Update` с заменой всего набора.

Действие **необратимо** — `Down` снимает только проверку, восстанавливать
удалённые правила неоткуда. Число переписанных строк и снятых правил печатается
миграцией всегда, чтобы «ноль» был отличим от «заполнение не выполнялось».

Набор имён протокола существует теперь в двух местах (код и база). Их паритет
**доказывается** гейтом `TestSGRulesDomain_ProtocolNameSetParityWithCode`: он
перечисляет **оба** набора (`domain.KnownProtocolNames` и SQL-функцию
`kacho_sg_protocol_names()`) и сверяет их как множества **в обе стороны**.
Односторонний опрос «спроси базу про каждое имя кода» был бы формой без
содержания: он доказывает только «код ⊆ база», а опасна ровно обратная сторона —
имя, добавленное в базу и отсутствующее в коде, делает ограничение **шире**
продукта, то есть отменяет смысл самого ограничения. Гейт также
регистронезависим, сверяет отрицательную половину тем же предикатом кода и
утверждает объём осмотренного числом (сейчас 150 против 150).

Ограничение **никогда не возбуждает исключение**: и неожиданный JSON-тип, и
число, не являющееся целым нужного размера (`1.5`, `1.0`, `1e999`), отвечают
`false`, а не ошибкой разбора. Иначе вызывающий получал бы ошибку совсем другого
класса (`22P02`/`22003`), которую маппер репозитория относит к разбору
идентификатора, а обратное заполнение на такой строке прерывалось бы вместо
нормализации.

## 25. Выбранная ветка `oneof protocol` с нулевым значением — отказ, а не «любой протокол»

`SecurityGroupRuleSpec.protocol` — `oneof` из `protocol_name` и
`protocol_number`. Прочитанная геттером, ветка номера отдаёт `0` и когда
вызывающий **выбрал** её со значением 0 (это HOPOPT, номер 0 реестра IANA), и
когда не выбирал вовсе. Конверсия сравнивала результат геттера с нулём, поэтому
два **разных намерения** вызывающего сходились в одно и становились
неразличимы. Симметрично `protocol_name: ""`.

Это «принято-и-проигнорировано»: успех на параметр, которого продукт не
применил. Из трёх законных исходов выбран второй — **отвергать явно**, называя
поле, синхронно, до создания операции:

- `protocol_number: 0` → `INVALID_ARGUMENT`, поле `<field>.protocol_number`,
  текст указывает на `protocol_name: "hopopt"`;
- `protocol_name: ""` → `INVALID_ARGUMENT`, поле `<field>.protocol_name`, текст
  указывает опустить `protocol` целиком.

Почему не «реализовать» (0 = HOPOPT): «протокол не задан» лежит в хранилище тем
же нулём (`SecurityGroupRule.ProtocolNumber`), и отличить одно от другого нечем
без смены представления и миграции **каждого** сохранённого правила.
Выразимость при этом не теряется — HOPOPT адресуется именем, оно входит в набор.
Ветка `protocol` не выбрана вовсе — по-прежнему законное «любой протокол».

## 26. Гранулярная правка маршрутов — отказ с причиной, а не молчаливый 501

`RouteTableService` объявляет три verb-RPC поверх набора маршрутов:
`AddRoutes`, `RemoveRoutes`, `UpdateRoute`. Ни один не был переопределён над
встроенной заглушкой, то есть все три отвечали `UNIMPLEMENTED` **молча** — без
причины и без записи здесь. Сайт документации при этом описывал их полностью:
отдельными разделами, с телом запроса, примерами `curl` и таблицей кодов, а
соседнее предупреждение у `Update` прямо советовало пользоваться ими, чтобы «не
потерять остальные маршруты». Продукт обещал то, чего нет, и советовал это как
рекомендованный путь.

**Почему не «реализовать» — предмета нет в трёх слоях сразу.** Два из трёх
методов адресуют маршрут по идентификатору (`RemoveRoutes.route_ids`,
`UpdateRoute.route_id`), а `StaticRoute` идентификатора **не несёт**:

| слой | что есть |
|---|---|
| контракт | `destination_prefix` · `next_hop_address` · `gateway_id` (отвергается) · `labels` |
| домен | те же три поля (`internal/domain/route_table.go`) |
| хранилище | `static_routes jsonb NOT NULL DEFAULT '[]'` — массив объектов без ключа |

То есть комментарии этих запросов ссылаются на `StaticRoute.id`, которого не
существует ни на одном уровне. Дописать поле — не «дореализовать метод», а
завести **идентичность маршрута**: адресуемая идентичность в этом продукте
обязана быть неизменяемой и присваиваться сервером (ban #15), значит нужны
правила присвоения, миграция каждой сохранённой строки и решение, что происходит
с идентификаторами при полной замене набора через `Update`. Это отдельный
инкремент со своей приёмкой, а не хвост чужого.

**Выбран исход 2 — отвергать явно.** Все три метода переопределены и отвечают
`UNIMPLEMENTED` с названной причиной и указанием рабочего пути (`Update` с
`update_mask: ["static_routes"]`). Тот же исход и по той же причине уже применён
в compute к `AddOneToOneNat`/`RemoveOneToOneNat`/`UpdateNetworkInterface`.

**Почему не «снять с контракта»** (исход, который правило называет умолчанием):
удаление RPC из публичного контракта — ломающее изменение, которое гейт
`buf breaking --against main` обязан поймать, и принимать его следует
осознанно, а не попутно с починкой документации. Решение отложено **не как
работа**, а как выбор владельца: снятие уместно приурочить к следующему
объявленному ломающему изменению домена vpc.

**Предикат снятия этой записи:** появится идентичность маршрута (поле `id` у
`StaticRoute` в контракте И в хранилище) — запись теряет предмет вместе с
отказом; либо три RPC уйдут из контракта — тогда она уходит вместе с ними.
Проверяется одной командой:
`git grep -c 'string id' proto/kacho/cloud/vpc/v1/route_table.proto`.

## 27. Перечень служебных диапазонов НЕ выставляется — цена названа, а не спрятана

**Решение.** Адресные диапазоны, которые платформа держит за собой
(`dataplane.reserved-prefixes`), наружу не отдаются: ни ответом, ни отдельным
RPC, ни этой документацией. Отказ на пересечении называет **только присланный
вызывающим** слот и его собственное значение.

**Почему.** Служебное пространство — это адреса узлов, адреса служб внутри
подсети и точка получения метаданных экземпляра, то есть underlay. Публичная
поверхность ресурса показывает намерение и результат арендатора, а не то, как
разложена физика; отказ, печатающий диапазон, отдал бы карту служебного
пространства за **один** пробный запрос. Доменное значение перечня такой печати
и не позволяет — у него нет метода, отдающего диапазоны.

**Цена клиенту названа прямо, а не подразумевается.** Планировщик адресации
ходит кругами «запрос → отказ → другой префикс», и число кругов не ограничено
сверху ничем, кроме удачи. Круг при этом дёшев: отказ **синхронный**, до создания
`Operation` и до обращения к домену Geography.

**Что сделано, чтобы отказ восстанавливал следующий шаг хотя бы машинно.** Отказ
несёт признак полосы `SUBNET_CIDR_RESERVED` в `google.rpc.ErrorInfo`
(производитель — `serviceerr.ReservedCIDROverlap`, домен `vpc.kacho.cloud`,
метаданные `field`/`value` — только присланное). До этого автомат не мог даже
разветвиться: «префикс служебный, бери следующий кандидат» было неотличимо от
«ввод негоден по форме, чинить надо код», а разбирать прозу сообщения контракт
прямо запрещает (`api-conventions.md` §By-lane code-split).

**Границы решения — обе названы:**

- признак **кругов не убавляет**. Он делает их машинно различимыми, и это меньше,
  чем публикация перечня. Это всё, что можно дать, не отдавая карту;
- перечень **задаётся посадкой**, а не продуктом: у разных установок он разный.
  Поэтому шаг «узнать состав у оператора установки» остаётся, и адрес у него
  конкретный — значение `dataplane.reservedPrefixes` в профиле развёртывания
  (`services/vpc/deploy/values.yaml`), из которого чарт собирает
  `dataplane.reserved-prefixes`. Оператор публикует его своим арендаторам сам;
  продукт публиковать его за оператора не вправе.

**Рассмотрено и отвергнуто:**

| вариант | почему нет |
|---|---|
| назвать диапазон в тексте отказа | это и есть карта по одному запросу |
| публичный RPC «перечислить служебные диапазоны» | та же карта, только без пробы |
| `Internal*`-RPC на `:9091` | арендатору недоступен by construction, то есть цену клиенту не снимает вовсе; оператору перечень и так виден в профиле |

**Предикат снятия этой записи:** решение владельца о публикации перечня либо
появление у доменного значения метода, отдающего диапазоны. Проверяется одной
командой: `git grep -n 'func (r ReservedPrefixes)' services/vpc/internal/domain/reserved_prefixes.go`
— метода, возвращающего сами диапазоны, среди них быть не должно.
