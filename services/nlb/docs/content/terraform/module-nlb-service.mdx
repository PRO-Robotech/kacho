# Модуль `nlb-service`

Модуль описывает балансировщик целиком: группу целей, сам балансировщик и его слушателей.
Это типовая единица — по отдельности их заводят редко, потому что слушатель без группы
трафик раздавать не может, а группа без балансировщика никем не опрашивается.

## Использование

```hcl
module "web" {
  source = "github.com/PRO-Robotech/kacho//terraform/modules/nlb-service"

  project_id   = var.project_id
  region_id    = "ru-central1"
  name         = "web"
  placement    = "INTERNAL_ZONAL"
  backend_port = 8080

  v4_source = { subnet_id = kacho_vpc_subnet.app.id }

  health_check = {
    http = { path = "/healthz", expected_codes = "200-299" }
  }

  targets = [
    { instance_id = kacho_compute_instance.app_a.id },
    { instance_id = kacho_compute_instance.app_b.id, weight = 50 },
  ]

  listeners = {
    http = { port = 80, target_port = 8080 }
  }

  labels = { origin = "terraform" }
}
```

## Что модуль решает за вас

### Регион задаётся один раз

Край требует, чтобы регион группы целей совпадал с регионом балансировщика. Две переменные
позволили бы задать расхождение, которое обнаружится только на `apply`, — поэтому
переменная одна.

### Окно вывода по умолчанию `0s`, а не `300s`

Край подставляет `300s`, если окно не задано. Для ресурсов под управлением Terraform это
плохое умолчание: удаление цели двухфазное, и каждый `destroy` ждал бы пять минут. Модуль
ставит `0s`; большее значение задавайте осознанно через `deregistration_delay`.

### Порядок сноса строится ссылками

Слушатели ссылаются на балансировщик и группу **по идентификатору**, а не по имени. Ссылка
строит граф зависимостей, и `destroy` идёт в обратном порядке — слушатели раньше группы,
которую они держат. Это несущее свойство: край не удаляет группу, на которую ссылаются.

## Переменные

| Имя | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `project_id` | `string` | — | Проект-владелец. |
| `region_id` | `string` | — | Регион балансировщика **и** группы целей. |
| `name` | `string` | — | Основа имён: группа получает суффикс `-tg`, слушатели — ключ своей записи. |
| `placement` | `string` | — | `EXTERNAL_REGIONAL`, `INTERNAL_REGIONAL` или `INTERNAL_ZONAL`. |
| `v4_source` | `object` | `null` | Откуда взять адрес IPv4: ровно одно из `subnet_id` и `address_id`. |
| `v6_source` | `object` | `null` | То же для IPv6. |
| `backend_port` | `number` | — | Порт, на который группа раздаёт трафик. |
| `health_check` | `object` | `{ tcp = {} }` | Проверка живости; ровно одна проба из четырёх. |
| `targets` | `list(object)` | `[]` | Цели; у каждой ровно одна форма адресации. |
| `deregistration_delay` | `string` | `"0s"` | Окно вывода цели. |
| `listeners` | `map(object)` | `{}` | Слушатели: ключ — суффикс имени. |
| `labels` | `map(string)` | `{}` | Метки на все ресурсы модуля. |

Проверки на входе ловят до обращения к краю: посадку вне трёх допустимых значений, две
пробы живости вместо одной, две формы адресации у одной цели, оба поля источника адреса
сразу.

## Выходы

| Имя | Что это |
|---|---|
| `load_balancer_id` | Идентификатор балансировщика. |
| `target_group_id` | Идентификатор группы целей. |
| `v4_address_id` / `v6_address_id` | Идентификатор **ресурса адреса**, а не строка адреса. |
| `listener_ids` | Идентификаторы слушателей по ключам входной карты. |
| `listener_substatus` | `OK` или `MISCONFIGURED` по каждому слушателю. |

:::tip Смотрите на `listener_substatus`
`MISCONFIGURED` означает, что слушатель создан, но раздавать ему некуда. Ресурс при этом
существует и `apply` проходит — без этого выхода расхождение видно только обращением к краю.
:::

## Посадка и подсеть обязаны быть согласованы

Зональный балансировщик берёт адрес из зональной подсети, региональный — из региональной.
Несогласованность край отвергает сообщением `subnet placement does not match load balancer
placement`; проверить это на стороне Terraform нельзя — посадка подсети известна только краю.

## Порт цели у слушателя обязателен

Контракт объявляет `target_port` необязательным: не задан — наследуется порт группы целей.
Край на сегодня ведёт себя иначе и отвергает создание, причём называет в отказе поле `port`,
а не `target_port`. Поэтому модуль требует его явно. Когда край начнёт исполнять своё
умолчание, требование снимется — это не сломает существующие конфигурации.

## Смена веса цели снимает её на короткое время

Добавление уже существующей цели край принимает как no-op и вес **не** меняет. Значит смена
веса выражается снятием и добавлением, и в промежутке цель из группы выходит. Порядок именно
такой намеренно: обратный оставил бы прежний вес и молча разошёлся бы с настройкой.

## Чем проверяется сам модуль

У модуля есть пробы: `tests/wiring.tftest.hcl`, гоняются командой `tofu test` из каталога
модуля. Провайдер в них подменён (`mock_provider`), то есть край не участвует — падение
означает ошибку в модуле, а не состояние стенда.

Пробы закрепляют две вещи: **связывание** (что на что ссылается, откуда берутся имена, что
доезжает до ресурса) и **отвержение** негодного входа. Второе не менее важно первого: без
отрицаний положительные пробы зеленели бы и на модуле, принимающем что угодно.

Конвейер требует пробы от КАЖДОГО модуля и падает на модуле без них.
