# Провайдер Terraform: ресурсы балансировщика

Провайдер `kacho` один на всю платформу — установка и настройка описаны на
странице «Провайдер Terraform» в документации VPC. Здесь только то,
что относится к балансировщику.

## Ресурсы

| Ресурс | Что описывает |
|---|---|
| `kacho_nlb_target_group` | Группа целей: куда раздаётся трафик и как проверяется живость |
| `kacho_nlb_load_balancer` | Сам балансировщик: посадка, источник адреса, группы безопасности |
| `kacho_nlb_listener` | Слушатель: порт, протокол, группа целей |

Типовую связку из всех трёх описывает [модуль `nlb-service`](module-nlb-service).

## `kacho_nlb_target_group`

```hcl
resource "kacho_nlb_target_group" "web" {
  project_id = var.project_id
  region_id  = "ru-central1"
  name       = "web-tg"
  port       = 8080

  deregistration_delay = "0s"

  health_check = {
    interval            = "5s"
    timeout             = "2s"
    healthy_threshold   = 2
    unhealthy_threshold = 2
    http = {
      path           = "/healthz"
      expected_codes = "200-299"
    }
  }

  targets = [
    { instance_id = kacho_compute_instance.a.id },
    { external_ip = { address = "203.0.113.10", zone_id = "ru-central1-a" }, weight = 50 },
  ]
}
```

### Цели — набор, а не список

Порядок целей край **не сохраняет**: он читает их упорядоченными по времени создания и
идентификатору, а у целей одного запроса время совпадает, и спор разрешает случайный
идентификатор. Поэтому цели описаны набором. Списком они давали бы сверку по индексу, и
перестановка читалась бы как изменение — `apply` падал бы на «unexpected new value».

### Вес по умолчанию задаётся опусканием поля

`weight = 0` и означает «вес по умолчанию». Два способа сказать одно и то же разошлись бы
между настройкой и состоянием, поэтому провайдер отвергает явный ноль и просит опустить поле.

### Смена веса снимает цель на короткое время

Добавление уже существующей цели край принимает как no-op и вес не меняет — значит смена
веса выражается снятием и добавлением. Порядок именно такой: обратный оставил бы прежний вес.

### Состав меняется своими действиями края

Край отвергает `targets` в маске изменения явно и требует отдельных действий, у которых
свои права. Их можно выдать независимо от права менять саму группу. Провайдер это делает
сам; знать об этом нужно, когда выдаёте права: одного `v_update` для управления составом
не хватит.

:::warning Окно вывода оплачивается временем `destroy`
Если `deregistration_delay` не задан, край подставляет `300s`. Удаление группы требует
пустого состава, а цель снимается лишь по истечении окна — то есть каждый `destroy` будет
ждать столько, сколько там указано. Для ресурсов под управлением Terraform ставьте `0s`.
:::

## `kacho_nlb_load_balancer`

```hcl
resource "kacho_nlb_load_balancer" "web" {
  project_id = var.project_id
  region_id  = "ru-central1"
  name       = "web"
  placement  = "INTERNAL_ZONAL"

  v4_source = { subnet_id = kacho_vpc_subnet.app.id }
}
```

### Источник адреса и выделенный адрес — разные атрибуты

`v4_source` — **ввод**: ровно одно из `subnet_id` (край выделит адрес сам) или `address_id`
(готовый адрес). `v4_address_id` — **вывод**: идентификатор выделенного ресурса адреса.

Одно имя на оба смысла обошлось бы дорого: вычисляемое значение планируется неизвестным, а
«изменение требует замены» видит неизвестное как другое значение — и балансировщик
пересоздавался бы на каждой правке меток.

### Посадка задаёт и обращённость, и зональность

`placement` принимает `EXTERNAL_REGIONAL`, `INTERNAL_REGIONAL` или `INTERNAL_ZONAL`.
Отдельных переключателей «внешний/внутренний» и «зональный/региональный» нет, а поле `type`
(`EXTERNAL`/`INTERNAL`) — вывод, его выводит край.

Подсеть источника адреса обязана быть согласована с посадкой: зональному балансировщику —
зональная подсеть, региональному — региональная. Расхождение край отвергает сообщением
`subnet placement does not match load balancer placement`.

:::warning Защита от удаления остановит `destroy`
Провайдер **не снимает** `deletion_protection` сам. Тихо обойдённая защита от удаления
бессмысленна; снимите её отдельным `apply` и повторите.
:::

## `kacho_nlb_listener`

```hcl
resource "kacho_nlb_listener" "http" {
  load_balancer_id = kacho_nlb_load_balancer.web.id
  name             = "web-http"
  protocol         = "TCP"
  port             = 80
  target_port      = 8080
  target_group_id  = kacho_nlb_target_group.web.id
}
```

`port`, `target_port`, `protocol` и `load_balancer_id` пересоздают слушателя: край их не
меняет. Меняются метки, описание и группа целей.

:::note `target_port` обязателен, хотя контракт объявляет его необязательным
По контракту незаданный порт цели наследуется от группы целей, а фактический виден в
`resolved_backend_port`. Край на сегодня так не делает: без этого поля он отвергает
создание — и называет в отказе поле `port`, а не `target_port`.

Провайдер требует его явно и **не** подставляет порт слушателя молча: наследуется по
контракту порт группы, и это разные числа.
:::

### `substatus` показывает то, чего не видно по статусу

`ACTIVE` + `MISCONFIGURED` означает, что слушатель создан, но раздавать ему некуда.
`apply` при этом проходит — расхождение видно только по этому полю.

## Импорт

Все три ресурса импортируются по идентификатору:

```bash
tofu import kacho_nlb_target_group.web  tgr...
tofu import kacho_nlb_load_balancer.web nlb...
tofu import kacho_nlb_listener.http     lst...
```

Формат проверяется по общему каталогу префиксов платформы **до** обращения к краю: заведомо
негодная строка получает внятный отказ, а не уезжает в сеть за ответом «не найдено», который
для неё ничего не значит.
