# kacho-nlb — 08-known-divergences

Осознанные by-design отклонения kacho-nlb. Здесь фиксируются решения, которые
могут выглядеть как расхождение со «стандартом» (прежней схемой, интуицией
аудитора), но приняты намеренно — чтобы будущий разработчик/аудитор не заводил
на них баг-тикеты повторно.

> Мера отклонения — **свой** опубликованный контракт и конвенции Kachō
> (именование, error-format, timestamp truncate, update_mask discipline). Состав
> методов и ресурсов проектируется под задачу, а не по чужому образцу, поэтому
> непохожесть на чей-то API предметом записи здесь быть не может.

## Формат чужого id (VIP-источники) проверяется синхронно — узкое, записанное отступление от B4

**Что.** `api-conventions.md` §By-lane code-split, пункт **B4** предписывает:
format-check — **только для собственных** id; чужие проверяются **существованием**
через владельца. `resolveVipSources` (`apps/kacho/api/loadbalancer/vip_source.go`)
всё же прогоняет `v4Source/v6Source.subnetId` и `.addressId` — оба **vpc-owned** —
через `corevalidate.ResourceID` **ДО** peer-validate. Решение — **оставить** эту
проверку; ниже — что она на самом деле делает и почему это лучше для вызывающего.

**Чего она НЕ делает (и что об этом писали неверно).** Она **не** сверяет
«свой vpc-prefix `sub`/`adr`». `corevalidate.ResourceID` **family-agnostic по
контракту**: аргумент `expectedPrefix` в теле функции демонстративно не
используется (`_ = expectedPrefix`, см. её godoc — «enp-id как subnet-id должен
доходить до repo.Get → NotFound, а не отбиваться InvalidArgument здесь»).
Проверяется ровно одно: первый сегмент строки входит в **платформенный** каталог
префиксов — `ids.KnownPrefixes()` / `ids.KnownHyphenPrefixes()` плюс два
config-расширения (`KACHO_EXTRA_RESOURCE_ID_PREFIXES`,
`KACHO_EXTRA_RESOURCE_ID_HYPHEN_PREFIXES`). Прежняя формулировка в acceptance-доках
(«format-check своего vpc-prefix'а `sub`/`adr`») и строка блокера B4 в
`docs/plans/kacho-redesign-2026/00-unified-system-design.md` («nlb-примеры: общий
prefix») **обе фактически неверны**: `sub` и `adr` — **разные** префиксы, общего у
них нет, и ни один из них проверкой не сверяется.

> [!note] Оба названных документа живут в **соседнем** репозитории `kacho-workspace`,
> не здесь — отсюда их существование не проверяется. Правка внесена там же
> (`rules: a syntactic gate on someone else's id is allowed only when it is written
> down`); из этого дерева утверждение о ней подтвердить нельзя, поэтому оно названо
> вместе с местом, где проверяется.

**Почему это не тот риск, который запрещает B4.** Обоснование B4 — «чужой prefix
не наш словарь»: consumer не должен носить копию приватного словаря владельца,
иначе владелец меняет/добавляет префикс, а consumer начинает отвергать валидные id.
Здесь копии словаря нет: каталог живёт в общем платформенном пакете (`pkg/ids` →
`pkg/validate`; в polyrepo-раскладке — тот же `pkg/`), он **единый
источник истины** для prefix→type-роутера всех сервисов и расширяется конфигом без
релиза. Локального утверждения о **типе** чужого ресурса тоже нет: id с чужим для
подсети префиксом (`nlb…`) проверку **проходит** и уезжает к владельцу — тип и
существование решает vpc. То есть нарушается **буква** B4 (format-check на чужом
поле), но не его **предмет**.

**Почему так лучше для вызывающего (это и есть предмет решения).** Снять проверку
можно — существование и так подтверждает vpc, — но каждый из трёх наблюдаемых
эффектов был бы хуже:

1. **Терминальность.** С проверкой явно-не-id отвергается синхронно и
   **окончательно**. Без неё тот же запрос при недоступном/непровязанном vpc
   отвечает `UNAVAILABLE` — «повтори позже» на ввод, который валидным не станет
   никогда. Заперто тестом `…_Malformed_TerminalEvenWhenOwnerUnavailable`.
2. **Правдивость текста.** Без проверки `subnetId="garbage!!"` возвращается как
   `"subnet garbage!! not found"` — контракт-тон **отсутствия ресурса** на строку,
   которая ресурсом быть не может. С проверкой — `"invalid subnet id 'garbage!!'"`,
   называющий настоящую проблему.
3. **Стоимость.** Явный мусор не оплачивается вызовом к соседу
   (`…_SyncFormatRejectWithoutPeer` проверяет, что владельца не дёрнули).

**Что проверка НЕ трогает.** Существование, тип, ownership, placement — всё это
по-прежнему решает vpc (`resolveOneSource` / `resolveLinkedAddress`). Чужой id,
не резолвящийся у владельца, отвечает **полосой peer-validate**
(`InvalidArgument "subnet <id> not found"` / generic `"Illegal argument addressId"`),
и **никогда** own-полосой `NOT_FOUND` — та означает «не нашёл СВОЮ строку».
Прочие чужие id nlb (`projectId`, `regionId`, `securityGroupIds`, instance/nic-таргеты)
остаются **existence-only**, без format-check — отступление узкое, ровно на два поля.

**Смежный фикс в том же месте.** `corevalidate.ResourceID` по контракту
пропускает пустую строку (required-проверка — отдельная ответственность), а
`resolveVipSources` её не делал: выбранная ветка oneof с пустым значением уезжала
к владельцу и возвращалась как **`"subnet  not found"`** — контракт-тон miss'а с
вырезанным id, утверждающий отсутствие ресурса, который caller не называл. Теперь
пустая ссылка отбивается как форма запроса: `"<v4|v6>_source.subnet_id: required"` /
`"…address_id: required"`, владельцу такой вопрос не задаётся.

**Тесты.** `loadbalancer/foreign_vip_id_lane_test.go` — по одному кейсу на каждое
утверждение выше (точные тексты, а не только коды; факт обращения/необращения к
владельцу; `NOT_FOUND` не используется на чужой полосе).

## VIP-уникальность живёт на LoadBalancer, а не на Listener

**Что.** Партиальный `UNIQUE listeners_region_vip_uniq (region_id,
allocated_address, port, protocol) WHERE status<>'DELETING'`, существовавший в
baseline-миграции `0001`, **намеренно снят** в миграции `0009`
(`DROP INDEX IF EXISTS ... listeners_region_vip_uniq`). Комментарий 0009:
«VIP-уникальность переехала на LoadBalancer».

**Почему.** Модель VIP переехала на уровень LB: anycast-VIP региона уникален как
свойство самого LoadBalancer'а. Инвариант теперь энфорсится
`load_balancers_region_v4_uniq` / `load_balancers_region_v6_uniq` (партиальные
`UNIQUE (region_id, address_vN) WHERE address_vN <> ''`), а AttachVIP-CAS
полагается на их `23505`. Валидность этих индексов дополнительно само-лечится
миграцией `0012`. Race-тест инварианта — `load_balancer_vip_concurrent_integration_test.go`.

**Следствие для аудита.** На уровне Listener **нет** within-service инварианта
region-VIP-уникальности, и его отсутствие — не пробел в покрытии. Комментарий в
`listener_integration_test.go`, ранее ссылавшийся на несуществующий
`TestListener_RegionVipUnique_RaceTest`, исправлен (sec-hardening r3, finding #6).

## Move ↔ Attach: двусторонний DB-guard (не только CAS на move-стороне)

**Что.** `LoadBalancer.MoveProject` и `TargetGroup.MoveProject` несут атомарный
guard `UPDATE ... WHERE NOT EXISTS(attached_target_groups ...)`, а
`AttachedTargetGroups.Attach` — locking-read `... FOR NO KEY UPDATE OF lb, tg` в
своём `INSERT ... SELECT`-JOIN'е.

**Почему обе стороны.** Guard на move-стороне закрывает только порядок
«attach закоммичен раньше». Обратный порядок (move выполнил свой `UPDATE`, держит
row-lock, ещё не закоммичен; конкурентный Attach под READ COMMITTED plain-read'ом
видит *stale* до-move project и вставляет cross-project attach) закрывается только
locking-read'ом на стороне Attach: он блокируется на move'нутой row-е и после
commit'а Move через EvalPlanQual пере-оценивает project-JOIN на свежем project →
mismatch → 0 rows → `FailedPrecondition`. `FOR NO KEY UPDATE` (не `FOR KEY SHARE`
от FK) обязателен — только он конфликтует с `FOR NO KEY UPDATE`, который Move
берёт на свою row-у. Обоснование и race-тесты — `sec_hardening_r3_integration_test.go`
(sec-hardening r3, finding #1).

**Тот же паттерн у `Listener.Insert`.** Листенер несёт денормализованное
зеркало `project_id`/`region_id` родительского LB. Раньше `Listener.Insert` был
plain-`INSERT` с software-captured (в sync-фазе Create) project_id — тот же
move-first TOCTOU: `LoadBalancer.MoveProject` каскадит
`UPDATE listeners SET project_id ... WHERE load_balancer_id=$lb` под
`FOR NO KEY UPDATE` на LB-row, а plain-INSERT берёт лишь FK `KEY SHARE` (не
конфликтует) → листенер персистится со stale project_id, а Move-каскад его не
видит. Фикс (sec-hardening r6, finding DATA #2): `Insert` теперь
`INSERT ... SELECT lb.project_id, lb.region_id ... FROM load_balancers lb
WHERE lb.id=$lb FOR NO KEY UPDATE OF lb` — сериализуется с MoveProject точно как
Attach. Race-тест — `TestListenerCreate_MoveFirst_ProjectConsistent`
(`sec_hardening_r6_integration_test.go`).

## lb_status_recompute — CAS-guard на финальной записи статуса

**Что.** Триггер `lb_status_recompute()` (пересчёт `INACTIVE↔ACTIVE` при
listener/attach INSERT/DELETE) пишет статус через
`UPDATE ... WHERE id=$1 AND status=cur_status` и эмитит outbox-событие только при
`ROW_COUNT>0` (миграция `0013`).

**Почему.** Прежний безусловный `UPDATE` мог затереть конкурентный explicit-переход
(`ACTIVE→STOPPING`/`→DELETING`) lost-update'ом: recompute читал `ACTIVE`, explicit
CAS коммитил `STOPPING`, а безусловная запись возвращала `ACTIVE`/`INACTIVE`.
CAS-guard + row-lock сериализуют пересчёт с `SetStatusCAS`; при проигранном CAS
статус не трогается и spurious-outbox не эмитится (sec-hardening r3, finding #2).

## Composition-root `runServe` — намеренно линейный, длинный wiring (не «толстая функция»)

**Что.** `cmd/kacho-loadbalancer/main.go:runServe` — единственный composition-root
(правило воркспейса `architecture.md` называет единственным местом wiring'а
`cmd/<svc>/main.go`; здесь `<svc>` — `kacho-loadbalancer`, и путь выше это уже
раскрывает). Функция длинная
(~300 строк, из них ~190 кода — остальное inline-документация каждого шага), но это
**не** нарушение layering'а и не «толстый сервис».

**Почему by-design (а не рефакторить в helper'ы дальше).** Тяжёлые шаги уже вынесены
в `wiring.go`/`observability.go`/`backstop.go`: `assembleBackgroundWorkers`,
`startLROWorker`, `buildReadinessCheckers`, `describeDiagnosticSurface`. Остаток
`runServe` — (1) плоская последовательность создания ресурсов с `defer`-cleanup'ами
(`cancel`/`pool.Close`/`repo.Close`/`closeAll`) наверху функции, где порядок виден
целиком, и (2) когезивная shutdown-оркестрация (`triggerShutdown` sync.Once + errgroup
`g.Go`-блоки). Дальнейшее дробление shutdown-блока в отдельный helper потребовало бы
протащить ~12 локалов (`cancel`, `healthAgg`, `background`, ожидание диагностической
поверхности, `cfg`, `logger`) через struct и **разнесло бы** порядок
`defer`/GracefulStop по двум функциям — ровно тот defer-ordering риск, который аудит и
называет опасностью. Держать этот порядок в одной линейной функции с явными
комментариями — сознательный trade-off читаемости-vs-безопасности в пользу второго
(sec-hardening r5b, LEAN-finding «runServe 308 lines»).

> [!note] Четыре имени из прежней редакции сняты вместе со своим предметом (перемерено 2026-08-11)
> Абзац называл четыре вынесенных шага — фабрику перехватчика, сборку цепочек, регистрацию
> служб и подъём диагностического слушателя. В дереве нет **ни одного**; имена здесь
> намеренно не воспроизводятся в форме координаты: цитата мёртвого имени в обратных кавычках
> читается как живое утверждение и заново отправляет читателя искать его в дереве. Сборка
> цепочек, регистрация служб и оба слушателя переехали в общий носитель контура
> (`pkg/servicehost`), а диагностическая поверхность поднимается его же профилем по
> объявлению `describeDiagnosticSurface`. Фабрика перехватчика снята целиком — вместе с
> ручкой аварийного пропуска, которой у носителя нет by construction.
>
> Размер функции перемерен на той же ревизии: **306** строк (прежняя редакция называла
> ~300 и «308» в ссылке на находку — числа расходились между собой уже тогда).

## Package-local `shared.*`-делегаторы — намеренная per-package конвенция (не дубль)

**Что.** Каждый use-case пакет (`loadbalancer`, `targetgroup`, `listener`, `announce`,
`operation`) держит тонкие package-local функции, форвардящие в единый `shared.*`:
`mapDomainErr`→`shared.MapDomainErr`, `errInvalidArg`→`shared.ErrInvalidArg`,
`operationToProto`→`shared.OperationToProto`, `stripSentinel`→`shared.StripSentinel`,
`peerErrToStatus`→`shared.PeerErrToStatus`. Тела 2-3 строки и byte-идентичны между
пакетами.

**Почему by-design (а не удалять wrapper'ы).** Логика **уже** консолидирована в
`shared.*` (единый источник истины — audit ARCH #7 / LEAN #10 / #11); package-local
делегаторы оставлены сознательно, чтобы use-case код звал короткое неквалифицированное
имя (`peerErrToStatus(err, kind, id)` вместо `shared.PeerErrToStatus(...)`) — единый
call-site стиль там, где делегатор есть. Дрейф поведения невозможен: изменение правится
в одном `shared.*`, wrapper'ы его лишь пробрасывают (sec-hardening r5b, LEAN-finding
«peerErrToStatus wrappers»).

> [!note] «5 видов × 5 пакетов» — число не подтвердилось, довод от него отвязан (перемерено 2026-08-11)
> Прежняя редакция обосновывала сохранение делегаторов тем, что это «repo-wide конвенция:
> 5 видов делегаторов × 5 пакетов», и называла удаление одного из них «непоследовательным
> churn против устоявшейся конвенции». Матрица разрежена, а не полна: делегаторов **13**
> из 25 клеток, и распределены они неровно — `loadbalancer` несёт все пять,
> `targetgroup` — четыре, `listener` — два, `announce` и `operation` — по одному.
> Предикат (повторяем им, а не памятью):
>
> ```sh
> for p in loadbalancer targetgroup listener announce operation; do
>   for f in mapDomainErr errInvalidArg operationToProto stripSentinel peerErrToStatus; do
>     grep -rlq "^func $f" services/nlb/internal/apps/kacho/api/$p/ && echo "$p $f"
>   done
> done | wc -l
> ```
>
> Довод при этом не рухнул — он был просто подпёрт не тем: сохранять делегаторы стоит
> потому, что **логика живёт единожды** в `shared` и дрейфовать ей нечем, а не потому, что
> клетки заполнены все. Число, без которого вывод не меняется, лучше не приводить вовсе:
> оппонент, поймавший его, законно усомнится и в самом выводе.

## Peer-client порты определены в `internal/clients/*`, а use-case их только алиасит

**Что.** `architecture.md` предписывает, что port-интерфейсы (`<Peer>Client`)
определяет внутренний слой (use-case). В kacho-nlb конкретные peer-порты и их
transfer-DTO физически объявлены в adapter-пакетах `internal/clients/*`
(`iam.ProjectClient`+`iam.Project`, `geo.RegionClient`/`ZoneClient`,
`vpc.SubnetClient`/`AddressClient`/`InternalAddressClient` + их request/response
DTO), а `apps/kacho/api/<res>/ports.go` их **алиасит** (`type ProjectClient =
iamclient.ProjectClient`). Формально стрелка зависимости смотрит из use-case в
adapter, а не наоборот.

**Почему by-design (а не инвертировать).** Peer-DTO — это тонкие value-структуры
над gRPC-stub'ами конкретного домена (owner API), у которых **единственный**
консумер — этот сервис; они не несут доменной логики kacho-nlb. Держать их
определение рядом с адаптером, который маршалит их из proto-stub'ов, — единый
источник истины формы; инверсия (объявить порты+DTO в use-case и реализовывать в
adapter) продублировала бы ~6 интерфейсов и ~10 DTO в двух местах и потребовала бы
конвертации proto↔use-case-DTO на каждом вызове ради чистоты стрелки, без выигрыша
в тестируемости (use-case-тесты всё равно строят те же value-структуры через
package-local fake'и). Замена одного консумера или второй контракт — редизайн
adapter-пакета в любом случае. Осознанный trade-off «single-definition DTO vs.
формальная dependency-inversion» в пользу первого (sec-hardening r6, ARCH-finding
«port ownership»). Композиционный wiring остаётся в `cmd/kacho-loadbalancer/main.go`.

## `statement_timeout=30s` энфорсится пулом (corelib), `cmd/migrator` освобождён

**Что.** Пул приложения (`coredb.NewPool` в `cmd/kacho-loadbalancer/main.go`)
ставит `statement_timeout=30000` (30 s) как `RuntimeParam` на КАЖДОМ соединении —
это делает `pkg/db.NewPool` (`cfg.ConnConfig.RuntimeParams["statement_timeout"]
= "30000"`). Server-side верхняя граница на любой request-path и фоновый
reconcile-запрос сверх gRPC-context-deadline. `lock_timeout` /
`idle_in_transaction_session_timeout` намеренно не заданы.

**Почему by-design (targeting ровно тот, которого хотел прежний r6-долг).**
`cmd/migrator` открывает СВОЁ `sql.Open("pgx", …)`-соединение (goose поверх него),
а НЕ `coredb.NewPool` — поэтому легитимно-длинный DDL/`CREATE INDEX`/backfill НЕ
обрывается 30-секундным лимитом (migration-abort был бы хуже удержанного коннекта).
Request-path И фоновые reconcile-джобы (`free_ip_runner`/`target_drain` держат тот
же app-pool `d.pool`) ограничены 30 s. `lock_timeout` не нужен: contested
write-пути — короткие атомарные CAS/`FOR NO KEY UPDATE`/`SKIP LOCKED`, а read-пути
keyset-клампятся (`pageSizeOrDefault` cap 1000, `ListTargets` — `MaxTargetsPerGroup`).
NB: прежняя запись «нет `statement_timeout`» (r6) устарела после апгрейда
`pkg/` (pool теперь ставит 30 s) — факт исправлен как stale
(sec-hardening r8b, DATA-finding «no statement_timeout» → resolved).

## update_mask known-set валидируется per-resource inline, не через corelib `validate.UpdateMask`

**Что.** Три мутируемых ресурса (`loadbalancer`/`targetgroup`/`listener`) держат
собственный inline-цикл по `update_mask.paths` против package-local known-set
(`knownUpdateFields` / `knownUpdateFieldsTG` / `listenerMutableMaskPaths`), а не
зовут corelib `validate.UpdateMask(field, mask, known)`. Тексты unknown-field
ошибок при этом **разные по ресурсам** и намеренно зафиксированы: LB/TG отдают
`"unknown update_mask field: <p>"`, listener — `"field '<p>' is not recognised in
update_mask"`.

**Почему by-design (а не унифицировать в corelib).** Текст и форма error —
**часть контракта** (`api-conventions.md`: «Тексты — часть контракта; меняются
только осознанно (через тикет)»); они заассерчены в unit-тестах
(`targetgroup/update_test.go` — `"unknown update_mask field: foo_bar_baz"`).
Corelib `validate.UpdateMask` эмитит **другой** текст (`"unknown field in
update_mask: <f>"`) в **структурированной** `FieldViolation`-обёртке
(`coreerrors.InvalidArgument().AddFieldViolation`), тогда как nlb сейчас отдаёт
flat-`status.Errorf`. Переключение на corelib поменяло бы wire-текст И форму detail
для всех трёх Update — это ломающее изменение замороженного контракта, а не
contract-safe LEAN. Кроме того immutable-ветка (hard-immutable поле в mask →
фиксированный `"<field> is immutable after <R>.Create"`) — genuinely
resource-specific и в corelib-helper не укладывается. Унификация unknown-field
текста/формы к платформенному стандарту — отдельный **осознанный контрактный
тикет** (обновить unit-тесты + newman в том же PR), не sec-hardening-рефактор
(sec-hardening r7b, LEAN-finding «update_mask reimplemented per-resource»).

## Фоновые reconcile-джобы — raw `*pgxpool.Pool` в use-case-слое (минуя CQRS Repository)

**Что.** Обе фоновые джобы в `services/nlb/internal/apps/kacho/jobs/`
(`free_ip_runner`, `target_drain_runner`) держат `*pgxpool.Pool` и исполняют
hand-written SQL (`SELECT … FOR UPDATE SKIP LOCKED`, `DELETE`, INSERT в
`nlb_outbox`/`fga_register_outbox`) напрямую, минуя `kacho.Repository`/
`RepositoryWriter`, через который идут все per-RPC use-case'ы. Outbox-INSERT'ы в
`free_ip_runner.emitReconcileFinalize` повторяют форму каноничных эмиттеров
`pg.outboxEmitter`/`pg.fgaRegisterEmitter`.

**Почему by-design (а не рефакторить через RepositoryWriter).** Это не
request-path use-case'ы, а multi-replica admin-reconcilers: их суть — claim одной
застрявшей строки под `FOR UPDATE SKIP LOCKED`, удержание row-lock'а на время
внешнего release-вызова (network) и финализация — семантика, которая НЕ ложится на
per-resource CQRS-порт (тот моделирует ресурс-мутации, а не scan-claim-reconcile).
Паттерн — устоявшаяся конвенция сервиса (`TargetDrainRunner` той же формы; перечень
джоб и их предмет — в шапке пакета, `services/nlb/internal/apps/kacho/jobs/doc.go`).

> Здесь стояло «Три … джобы» с третьим именем — обратным заполнением дискриминатора
> источника VIP. Такой джобы в пакете нет: он снят вместе с листенерным VIP миграцией
> `0028_drop_dead_listener_address_columns.sql`, которая прямо это фиксирует. Предикат:
> `git ls-files services/nlb/internal/apps/kacho/jobs/*.go | grep -v _test`. Разбор —
> `14-vip-origin.md`.

Джобы —
**вне** dependency-rule request-path'а (нет доменных инвариантов ресурса, только
housekeeping-VIP-release/target-drain). Дрейф дублированных outbox-INSERT'ов от
каноничных эмиттеров закрыт тестами:
`free_ip_runner_integration_test.go`/`target_drain_runner_integration_test.go`
гоняют реальные INSERT'ы против той же схемы (NOT NULL/CHECK из миграций ловят
рассинхрон колонок на CI). Осознанный trade-off «reconcile-controlflow рядом с
raw-SQL» vs. слой косвенности через Repository, без выигрыша в тестируемости
(sec-hardening r8b, ARCH-finding «jobs bypass CQRS»).

## `domain/` импортирует сторонние value-библиотеки (не только stdlib + стабы контракта)

**Что.** `architecture.md` предписывает `domain/` импортировать ТОЛЬКО stdlib +
сгенерённые стабы `pkg/api/...`. Фактически `internal/domain/` импортирует
`github.com/H-BF/corlib/pkg/{dict,option}` (`types.go`, `target.go`, `listener.go`),
`go.uber.org/multierr` (`loadbalancer.go`, `target.go`, `health_check.go`,
`target_group.go`, `listener.go`) и
`github.com/PRO-Robotech/kacho/pkg/{errors,ids}` (`types.go`, `status.go`,
`builders.go`).

**Почему by-design (а не заменять на stdlib).** Все три — чистые value-библиотеки
(`dict`/`option` — generic-контейнеры, `multierr` — агрегация ошибок, corelib
`errors`/`ids` — in-org error-builder + ID-генерация); НИ pgx, НИ grpc-stubs, НИ
sqlc-типов, НИ adapter-зависимостей domain не тянет — дух dependency-rule (нет
утечки адаптера в entity-слой) соблюдён. `corelib/errors` даёт единый
gRPC-совместимый `InvalidArgument().AddFieldViolation`-формат (часть
error-контракта, см. `api-conventions.md`), а `option`/`dict` устраняют голые
`*T`/`map`-обёртки в self-validating newtype'ах. Замена на stdlib-эквиваленты
продублировала бы эти утилиты внутри сервиса без выигрыша в чистоте (те же
value-типы, но hand-rolled). Sanctioned location для этого отклонения — здесь
(git-youtrack.md «by-design → docs/architecture»), а не только inline-комментарий в
`types.go` (sec-hardening r8b, ARCH-finding «domain imports third-party»).

## `Target` служит и запросом, и ответом: состояние слива — output-only, но отвергается только на путях создания

**Что.** `Target.status` / `Target.drain_started_at` (добавлены 2026-07-31) —
output-only. Сообщение `Target` при этом используется и как вход
(`CreateTargetGroup.targets`, `AddTargets.targets`, `RemoveTargets.targets`), и
как выход (`TargetGroup.targets`). Поэтому:

- `CreateTargetGroup` и `AddTargets` **отвергают** заполненные output-only поля
  синхронно, с именем поля (`targets[i].status` / `targets[i].drain_started_at`);
- `RemoveTargets` те же поля **игнорирует**;
- `UpdateTargetGroup.targets` — **четвёртая** входная поверхность, и она особая:
  замена набора целей на этом RPC не поддерживается вовсе. Явная маска
  `update_mask:["targets"]` отвергается, а при **пустой** маске поле не читает
  ни одна ветка `applyUpdateMaskTG` — весь список принимается с успехом и молча
  выбрасывается. Это **не** следствие текущей правки (так было и до неё), но
  перечень входных поверхностей обязан быть полным: «перечислено три» читается
  как «других нет».

**Почему асимметрия — решение, а не недосмотр.** На путях создания принять
состояние молча значило бы пообещать возможность добавить цель уже
сливающейся — возможности, которой нет («принято-и-проигнорировано»
запрещено). На снятии сопоставление идёт **по идентичности**, и естественный
поток «прочитал группу → передал цель на снятие» обязан продолжать работать:
отказ там наказывал бы за круговой обмен собственным ответом сервиса. Обе
половины закреплены тестами (`target_output_only_fields_test.go`), чтобы
асимметрия оставалась решением.

**Смежное, НЕ закрытое (названо числом).** Того же класса «принято и
проигнорировано» рядом остаётся **2** места, оба старше этой правки и здесь не
тронутые: `weight` в `RemoveTargets.targets` (сопоставление идёт по
идентичности, вес не читается) и весь `targets` в `UpdateTargetGroup` при пустой
маске (см. выше). Исход по общему правилу — отвергать явно либо снять с
контракта; это отдельный предмет со своей приёмкой.

## Публичная проекция группы строится из набора С состоянием, без запасного пути

**Что.** `TargetGroupRecord` несёт два набора целей: встроенный доменный
`Targets` (идентичность + вес) и `TargetStates` (он же плюс `Status` /
`DrainStartedAt`). `dto/type2pb` читает **только** `TargetStates`.

**Почему без отката на `Targets`.** Снятая цель живёт в группе до истечения
`deregistration_delay`. Пока проекция собиралась из доменного набора, состояния
у неё не было вовсе — снятая цель выглядела обычной, и снятие читалось как «не
сработало». Запасной путь «нет состояния → считаем активной» вернул бы ровно то
неверное утверждение, только молча. Поэтому путь чтения, заполнивший один лишь
`Targets`, отдаёт **пустой** набор целей: отсутствие заметно, подмена — нет.
Разложение строк по двум наборам живёт одной функцией (`fillTargets`), чтобы
повтор не стал местом, где один из наборов однажды забудут.

**Смежное, ЗАКРЫТО — перемерено 2026-08-30.** Здесь стояло «целей не подгружает
**3** пути чтения записи — `reader.List`, `writer.Update` и `writer.MoveProject`».
На день этой правки не подгружали **два**: `reader.List` дочитывает цели страницы
одной выборкой (`listTargetsForGroups`) и делает это с тех пор, как поле объявлено
набором в контракте. То есть перечень пережил свой предмет ровно на треть — и
пережил бы дольше, если бы его не перемерили при работе над #1551.

Оставшиеся два закрыты той же задачей: `Update` и `MoveProject` дочитывают цели ТЕМ
ЖЕ разложением (`fillTargets`), в своей же транзакции, сразу за мутацией. Причина не
в красоте ответа: событие журнала вида `nlb_target_group` несёт ПОЛНОЕ состояние, а
собирается оно из той же записи — путь, вернувший её без целей, дал бы подписчику
группу с пустым набором, и он прочёл бы это как «цели удалены».

Следствие для вызывающего, названное отдельно: ответ операции правки и операции
переноса больше не приходит с пустым набором целей при живых целях.

## Ребро проверки прав не имеет своей ручки транспорта — она общая с ребром регистрации

**Что.** До iam у nlb три предмета разговора и **два** соединения: публичное
(`:9090`, `ProjectService.Get`) и внутреннее (`:9091`). Внутреннее несёт **сразу
два** — per-RPC `InternalIAMService.Check`, то есть само решение о доступе, и
`RegisterResource`/`UnregisterResource` (синхронный регистратор + дренаж очереди
регистраций). Клиентские creds на оба задаёт **одна** ручка — `mtls.iam-register`
(поле `MTLSConfig.IAMRegister`, флаг чарта `mtls.edges.iamRegister`,
`mtls.serverName.iamRegister`). Собственной ручки у ребра, по которому
принимается решение о доступе, нет; имя единственной говорит о регистрации.

**Как то же самое сделано у соседей.** Предикат — перечисление полей
`grpcclient.TLSClient` в конфигурации каждого сервиса плюс чтение его
композиционного корня (какими creds поднято каждое соединение):

| Сервис | предметов разговора с iam | ручек транспорта | ребро проверки прав |
|---|---:|---:|---|
| vpc | 3 | 3 | своя ручка (`IAM_AUTHZ_MTLS`) |
| compute | 3 | 3 | своя ручка (`IAM_AUTHZ_MTLS`) |
| registry | 2 | 2 | своя ручка (`IAM_AUTHZ_MTLS`) |
| geo | 1 | 1 | своя ручка (`IAM_AUTHZ_MTLS`) |
| storage | 3 | 1 | общая со всеми рёбрами к iam — записано у storage |
| **nlb** | **3** | **2** | **общая с ребром регистрации (`mtls.iam-register`)** |

**Почему так — причина восстановима из дерева.** Разделение у nlb проведено **по
листенеру**, а не по предмету: `iam-project` и `iam-register` существуют раздельно
потому, что публичный и внутренний dial-host у iam **разные имена**, и единый
`ServerName` не может быть верен для обоих под `RequireAndVerifyClientCert`. Это
записано и в комментарии `peerDialSpecs`, и в шапке `mtls`-блока чарта. `Check`
живёт на том же внутреннем листенере, что и регистрация, — значит по критерию
«имя пира» отдельная ручка ему не требовалась, и её не завели. Причина есть, и она
не выдумана; чего не было — места, называющего это **отступлением** и **выбором**.

**Чего в дереве нет — и это предмет записи.** Ни `docs/architecture/`, ни
комментарии конфигурации не говорят, что ребро решения о доступе не имеет своей
ручки; они описывают деление по листенерам, из которого это лишь следует. Решения
о законности отступления в дереве нет — законность решает владелец. Запись
фиксирует состояние, а не разрешает его.

**Что это стоит уже сегодня.** Стража старта требует mTLS именно на ребре решения
о доступе, и её текст отказа вынужден называть оператору ручку **чужого** имени
(`mtls.iam-register.enable=true` — «insecure Check edge forbidden»). Оператор
читает про регистрацию, а чинит авторизацию. Из того же следует и вторая цена:
раскатка, ротация или временное отключение ребра регистрации двигают ребро
решения о доступе — у соседей это два независимых движения.

**Что должно быть верно, чтобы отступление снять.** У ребра `Check` — своя ручка
транспорта: своё поле конфигурации, свой флаг чарта, свой `ServerName`, равный
имени того листенера, куда сервис фактически ходит (сегодня — внутреннего). Текст
отказа стражи тогда называет ручку своего предмета. Соединение при этом может
остаться одним: предмет записи — **ручка**, а не число сокетов; разделять
соединение ради симметрии значило бы платить за то, чего никто не просил.

**Смежное, НЕ предмет этой записи.** `vpc-public` и `vpc-internal` у nlb тоже
делят одну ручку (`mtls.vpc`), и это разобрано **в коде**: у vpc оба порта
обслуживает один Service, чьё имя входит в SAN, поэтому единый `ServerName` там
верен. Отличие от случая выше — в том, что там общая ручка следует из совпадения
имён пира, а здесь ребро решения о доступе просто не получило своего имени.

**Предикат, от которого зависит запись** — он же её самоистечение: пока у ребра
`Check` нет собственного поля `grpcclient.TLSClient`, запись описывает дерево.
Появится — запись обязана быть снята, а не оставлена: отступление без предмета
читается как действующее ограничение и запрещает работу, которая уже сделана.

## `InternalResourceLifecycleService.Subscribe` — СНЯТ (надгробие)

**Чем был.** Отступлением от `api-conventions.md`, объявляющего, что потокового
чтения в платформе нет: `Get`/`List` синхронны, мутации асинхронны через
`Operation`, клиент поллит. У nlb такой server-stream был, а вызывающего у него не
было — единственным потребителем оставалась проба, доказывавшая, что поверхность
работает.

**Чем стало.** Контракт снят задачей #814; читатель журнала, его порт, раздел
настроек и проба сняты задачей #1043. Отступления больше нет: `api-conventions.md`
описывает nlb без оговорок.

**Что уехало, а не пропало.** Читатель нёс ответ на класс, который к подписке
отношения не имеет и потому пережил её: номер строки журнала выдаётся счётчиком на
вставке, а строка становится видимой на фиксации, поэтому порядок номеров и порядок
фиксаций независимы — отдать номер, за которым ещё может появиться меньший, значит
потерять меньший навсегда. Наблюдение границы устоявшегося по блокировкам таблицы,
разбор отката и названный размен перенесены в `pkg/subscription` (фаза #1018) вместе
с пробой на трёх подслучаях; там же они обобщены до любого владельца журнала.

**Почему запись осталась, хотя предмета нет.** Затем, что снятое решение
свидетельствует о себе: следующий, увидев здесь СВОЮ форму подписки в истории,
иначе решит, что её сняли по недосмотру. Журнал живёт независимо — его строки
читают перемещение балансировщика и перемещение целевой группы; снята была
СОБСТВЕННАЯ ФОРМА подписки, а не журнал и не подписка как таковая.

**Подписка у nlb СНОВА ЕСТЬ, и это не возвращение снятого.** Сервис служит
`InternalSubscriptionService.Subscribe` — форму, объявленную ОДИН раз на всю
платформу и реализованную в фундаменте (`pkg/subscription`); nlb приносит ей только
объявление своего журнала (`internal/subscriptionjournal`). Отступления от
конвенций это не заводит: потоковое чтение перестало быть частной формой домена и
стало формой платформы, а прежняя запись конвенций про «Watch RPC не существует»
приведена в соответствие с деревом фазой контракта.

**Цена названа по видам, а не одной строкой (перемерено 2026-08-30, #1381).**
События вида `nlb_listener` доезжают С ПОЛНЫМ состоянием предмета —
`kacho.cloud.loadbalancer.v1.Listener`, тот же, что отдаёт `Get`, и с метками.
События балансировщика и целевой группы состояния не несут: их нагрузка остаётся
намеренно минимальным снимком, а контракт формы разрешает подписчику читать
непустое состояние как ПОЛНОЕ — отдать частичное значило бы утверждать, что у
балансировщика нет ни меток, ни целей. По этим двум видам подписчик узнаёт, ЧТО
перечитать, и читает предмет отдельным вызовом; отсутствие доезжает причиной
`NOT_PRODUCED`, отличимой машинно от сбоя сборки.

**Здесь стояло «События nlb доезжают БЕЗ состояния предмета» — целиком.** Это было
верно в день записи и перестало быть верным вместе с обогащением вида слушателя.
Утверждение о владельце ЦЕЛИКОМ там, где свойство принадлежит ВИДУ, — тот же
класс, что запись ловит в объявлении нагрузки ниже: оно переживает свой предмет
ровно на одну правку и читается шире, чем верно.

**Чем держится перенос.** Не этой записью: прозе следующий читатель не обязан
верить, а проверить её нечем. Держит гейт `internal/repohygiene`
`TestSettledWatermarkObserverIsSingularAndLivesInTheFoundation` — он требует, чтобы
наблюдатель границы существовал, был один и лежал в фундаменте. Предикат намеренно
поставлен на ПРИЁМ, а не на файл: «файла нет» выполняется удалением, «приём живёт в
фундаменте» — только переносом.

**Предикат этой записи СРАБОТАЛ ДВАЖДЫ, и запись сужена, а не снята.** Она

**Что верно сегодня.**

| вид | нагрузка | читатель |
|---|---|---|
| `nlb_listener` | ЗАПИСЬ ЦЕЛИКОМ под конвертом `state` | сборщик состояния журнала |
| `nlb_target_group` | ЗАПИСЬ ЦЕЛИКОМ, включая набор целей С СОСТОЯНИЕМ | сборщик состояния журнала |
| `nlb_load_balancer` | минимальный снимок (`kachorepo.LifecyclePayload`) | нет |

Сборщик по балансировщику отвечает «не производится», в нагрузку не заглядывая.

**Предикат снятия ОСТАВШЕГОСЯ.** Запись снимается целиком, когда `state` собирает
состояние и у `nlb_load_balancer`. Трудная часть у него ДРУГАЯ, чем была у группы,
и назвать её надо прямо, иначе следующий возьмётся не за то: не количество точек, а
ДВА ЯЗЫКА у одного конверта. Семь точек этого вида — на Go (пять в его собственном
пакете, две в пакете слушателя), восьмая — триггер пересчёта статуса, и
`to_jsonb(строки)` даёт ключи имён КОЛОНОК против имён полей Go у остальных семи.
Две формы одного конверта у одного вида расходятся молча. Цена и два возможных
исхода измерены в шапке пакета `internal/subscriptionjournal`.

**Почему полноту объявляет КОНВЕРТ, а не удача разбора.** Журнал не чистится
(`RetainsEverything`), а подписчик вправе открыть поток с начала — значит строки
ПРЕЖНЕЙ формы доезжают до сборщика и сегодня. Разбор их молча не отвергает:
`encoding/json` сопоставляет имена без учёта регистра, поэтому `id`, `name`,
`protocol`, `port` и `status` минимального снимка попали бы в поля записи, а
проект, родитель, отметка создания и МЕТКИ — нет. Вышел бы предмет, который
разобрался, перенёсся в контракт и оказался ЛОЖНЫМ.

Опасность измерена, а не предположена: инъекция «полноту объявляет удача разбора»
даёт слушателя `id:"nlb-l-…" created_at:{seconds:-62135596800} name:"front"
protocol:TCP port:443 status:ACTIVE substatus:MISCONFIGURED` — без проекта, без
меток и с отметкой создания первого года нашей эры. Именно это подписчик записал бы
как факт.

**Обогащение — ВСЁ-ИЛИ-НИЧЕГО В ПРЕДЕЛАХ ВИДА.** Одна точка эмиссии, отдающая
частичный снимок, делает ложным весь вид, и делает тихо. У слушателя точек пять,
все на Go, и одна из них лежит в пакете БАЛАНСИРОВЩИКА — его переезд каскадом
переписывает проект у слушателей и обязан объявить это своей строкой на каждого
(#1549). Держит это разбор ДЕРЕВА use-case'ов
(`TestEveryEmissionOfAStatefulKindBuildsTheSamePayload`) — он судит УЗЕЛ вызова, а
не подстроку, потому что имя строителя стоит и в самих объяснениях. Доказан
инъекцией в обе стороны: подменённая нагрузка одной точки → красное с координатой;
эмиссии соседнего вида своим строителем → молчание; вид, объявленный несущим
состояние и никем не эмитируемый, → красное («проверка беспредметна»).

Обходится ДЕРЕВО, а не каталог пакета, и это не стиль: точки эмиссии одного вида
лежат в РАЗНЫХ пакетах — правку балансировщика эмитят и его собственный use-case, и
пакет слушателя. Прежняя редакция гейта обходила только свой каталог и таких точек
не видела вовсе.

**Что было неверно в прежней редакции (задача #1452) — остаётся как урок.**
Объявление нагрузки называло потребителя в настоящем времени —
«`InternalResourceLifecycleService.Subscribe` → kacho-iam FGA-sync» — спустя два
снятия подряд: контракт снят задачей #814, его читатель задачей #1043. Зеркало прав
при этом ходит ДРУГОЙ очередью (`fga_register_outbox`, миграция 0002, где
несовместимость схем объявлена решением). Утверждение «единый источник, разделяемый
КАЖДЫМ производителем» тоже не выполнялось: три пути из девяти собирают нагрузку
мимо словаря.

Цена была не в стиле: задача #1381 упиралась в вопрос «что сломается, если
поменять форму нагрузки». По комментарию ответ был «зеркало прав у соседа» — довод
против; по дереву ответ «ничего». Форму нагрузки слушателя #1381 и заменила.

**Что снято помимо прозы.** `ParseLifecyclePayload` — разборщик без вызывающих, тот
же класс, что закрывала #1043. Он был зеркалом собственного строителя: обе стороны
брали одни и те же константы, поэтому его круговая проба не могла отличить верное
имя ключа от любого другого. Замер: значение `PayloadKeyOldProjectID` заменено на
`totally_wrong_key` — **все четыре** пробы обеих сторон остались зелёными.
Утверждения переведены на ПРОВОД: пробы производителей называют ключи строковыми
литералами. Читатель конверта состояния этому не противоречит — он берёт запись
ЦЕЛИКОМ, а не зеркалит строителя по полям, и проверяется сквозной пробой журнала:
от строки в базе до контракта у клиента.

**Проверка `TestJournalStateCannotReadThePayload` СНЯТА вместе со своим предметом.**
Она судила узел: параметр строки журнала у `state` объявлен без имени, то есть
прочитать нагрузку функция не может by construction. Параметр поименован —
послаблению больше нечего исключать, и держать проверку значило бы держать
послабление без предмета. Её собственная шапка это и предписывала.

**Остаток, названный числом.** Строка-производитель в применённой миграции 0001
(`nlb_outbox (D-13 lifecycle stream для kacho-iam)`) несёт то же снятое имя в
комментарии. Применённые миграции не правят (ban #5); переписывать их ради
комментария — не тот размен. Строка одна.
