# schema-rollback.txt — РЕШЕНИЕ ПО КАЖДОЙ МИГРАЦИИ, У КОТОРОЙ НЕТ СЕКЦИИ ОТКАТА.
#
# ЗАЧЕМ ВЕДОМОСТЬ. Мигратор идёт при КАЖДОМ раскате, поэтому штатный откат
# выкатки возвращает ПРЕЖНИЙ ОБРАЗ НА НОВУЮ СХЕМУ. Насколько это выполнимо,
# решает не образ, а цепочка миграций — и отсутствие секции отката у миграции
# сегодня НЕОТЛИЧИМО от обратимости: и то и другое выглядит как «секции нет».
# Пока решение не записано, оператор узнаёт исход ПОСЛЕ отката.
#
# ЧЕГО ЗДЕСЬ НЕТ И БЫТЬ НЕ ДОЛЖНО. Миграции, чьи снятия объявлены машинно в
# `services/<сервис>/internal/migrations/dropguard.json`, сюда НЕ пишутся: их
# необратимость уже объявлена, и вторая запись об одном предмете разошлась бы
# молча. Ведомость покрывает ровно остаток — миграции без секции отката, чьё
# снятие dropguard не объявляет.
#
# ФОРМАТ:  <сервис>|<файл>|<вердикт>|<обоснование>
#   вердикт `необратима`     — данные сняты, восстановить их нечем; версия и
#                              есть точка невозврата;
#   вердикт `откат-не-нужен` — версия остаётся применённой и при откате образа,
#                              и это безвредно: обоснование обязано сказать,
#                              почему прежний образ с ней работает.
#
# ЧЕМ ДЕРЖИТСЯ. Ведомость читает `deploy/scripts/schema-rollback-statement.py`
# (его зовёт рецепт боевой раскатки ДО применения), а её полноту и
# самоистечение — `deploy/schema_rollback_has_a_producer_test.go`: миграция без
# секции отката и без строки роняет прогон, и строка, у которой предмета больше
# нет, — тоже.
#
# ПРАВИТЬ САМУ МИГРАЦИЮ, ДОПИСЫВАЯ ЕЙ СЕКЦИЮ ОТКАТА, ЗАПРЕЩЕНО: применённая
# миграция не редактируется (ban #5). Новая секция у уже накатанной версии
# существует только в дереве и никогда — в базе, где эта версия уже стоит.
