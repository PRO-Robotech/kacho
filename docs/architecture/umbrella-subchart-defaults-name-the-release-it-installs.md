# Умолчание подчарта зонта называет объект, который зонт САМ ставит

**Статус:** посылка задачи #2599 опровергнута замером 2026-09-12 · **Область:**
базовые значения всякого подчарта `deploy/helm/umbrella/` — координаты образа и
базы данных · **Это ЕДИНСТВЕННОЕ место, где различение объявлено**; энфорсмент
назван ниже поимённо и НЕ заводится этой записью.

## Что спрашивали

Задача #2599 утверждала: подчарт `deploy/helm/umbrella/charts/kaname/values.yaml`
несёт пять непустых dev-умолчаний (`image.repository`, `image.tag`, `db.host`,
`db.passwordSecretName`, `db.passwordSecretKey`), стража на пустоту у них нет, а
снятый стандалон-чарт службы доступа такими стражами обладал — значит их надо
завести заново: пустая строка по умолчанию плюс отказ рендера в боевой посадке.

Первым шагом разбора задача называла свою же неизвестную: **накладывается ли
`values.prod.yaml` всегда поверх кластерного профиля или применяется сам по
себе.**

## Ответ на первый шаг: применяется САМ ПО СЕБЕ

Цепочки `-f` объявлены в одном месте дерева — `deploy/stacks.txt`, и все
проверки развёртывания читают его, а не свою копию. Стек `prod` состоит из
**одного** профиля:

```
prod:values.prod.yaml
fe3455:values.prod.yaml,values.fe3455.yaml,values.fe3455-prod.yaml,values.fe3455-ory-posture.yaml
```

То есть посылка задачи в этой части **верна**: боевой профиль не наследует
кластерный слой, и всё, чего он не назвал, приезжает из умолчаний.

Стражей на пустоту `image`/`db` у подчарта действительно нет: отказов рендера в
его шаблонах восемь, и ни один не про эти поля (`grep -rn 'fail ' -- '…/charts/kaname/templates/'`).

## Почему находки всё-таки нет

### 1. Умолчание образа не доезжает НИ ДО ОДНОГО стенда

Задача выводила из «`image` не переопределён в `values.prod.yaml`» следствие
«деплой подставит `kaname:dev`». Следствие **ложно**: между умолчанием подчарта
и профилем стоит третий слой — собственный `values.yaml` зонта, — и helm
применяет его ВСЕГДА, независимо от `-f`. Он называет координату образа явно.

Замер по всем шести стекам `deploy/stacks.txt`: координата образа приезжает из
объявления дерева на **каждом** (у `prod` и `dev` — из `values.yaml` зонта, у
`fe3455`/`prorobotech`/`a8f60d` — из их собственных слоёв). Умолчание
`image.repository: kaname` / `image.tag: dev` не побеждает **нигде**.

### 2. Умолчание базы называет объект, который ставит ЭТОТ ЖЕ релиз

Предикат, по которому судил снятый стандалон-чарт, был не «умолчание пусто», а —
дословно из его собственной шапки — **«базовые значения чарта не называют
объект, которого чарт НЕ СОЗДАЁТ»**. Там же назван и законный близнец: ссылка на
объект, который чарт создаёт сам, стоит в такой же позиции и нарушением не
является.

`kacho-umbrella-pg-iam` был **чужим** для стандалон-чарта, который ставит
сторонний оператор в своём облаке, и он **свой** для зонта: `pg-iam` объявлен в
`deploy/helm/umbrella/Chart.yaml` псевдонимом `postgresql` **без условия**, то
есть ставится всегда. Проверено рендером:

```sh
# одноимённый релиз + псевдоним pg-iam → helm производит ровно это имя
helm template kacho-umbrella <зонт с единственной зависимостью postgresql alias=pg-iam>
#   Service  kacho-umbrella-pg-iam        ← адрес, которым и является db.host
#   Secret   kacho-umbrella-pg-iam        ← создаётся, когда профиль дал auth.password
```

Что имя узла выводится из имени релиза и псевдонима **законно**, записано в
дереве раньше этой задачи — `deploy/stand_psql_names_the_declared_database_test.go`
в границах своего предмета говорит прямо: «она НЕ судит имя узла базы и имя
релиза: и то и другое helm производит из имени релиза и псевдонима подчарта, то
есть выводится ЗАКОННО и по правилу, которое принадлежит helm, а не нам».

### 3. Боевой профиль называет эти координаты — на стороне ВЛАДЕЛЬЦА

Профиль молчит о `kaname.db.*` и при этом объявляет то же самое у производителя:
`values.prod.yaml` и `values.fe3455-prod.yaml` несут `pg-iam.auth` с именем
пользователя, именем базы и ссылкой на существующий секрет. Согласие сторон
перемерено по всем стекам:

```
сверено 98 пар · расхождений 0 · нечего сверять 28
```

Единица счёта — тройка «подчарт × стек × ось», где ось это
`db.user`↔`auth.username`, `db.name`↔`auth.database`,
`db.passwordSecretName`↔`auth.existingSecret`. «Нечего сверять» — стек, чей
профиль производителя не объявил; это состояние названо отдельным числом, чтобы
ноль расхождений был отличим от нуля сверенного.

### 4. `kaname` не был «единственным оставшимся кандидатом»

Задача называла подчарт службы доступа единственным кандидатом. Перемерено по
всем подчартам зонта — из пяти осей на стеке `prod` у `registry` приезжает из
умолчания **4**, у `compute`, `kacho-geo`, `kaname`, `vpc` — **3**, у
`kacho-nlb` — **2**, у `api-gateway` и `storage` — **0**. `kaname` стоит в
середине распределения, а не на его краю.

Из этого следует не «значит и остальных надо чинить», а обратное: свойство,
общее для пяти подчартов из восьми, есть **устройство зонта**, и правка одного
из пяти была бы починкой экземпляра при живом классе.

## Решение

**Базовое значение подчарта зонта ВПРАВЕ называть координату объекта, который
этот же релиз ставит или который его профиль объявляет у владельца. Пустая
строка плюс отказ рендера для таких координат — НЕ заводятся.**

### Почему не заводятся — три довода, каждый достаточен

**Профиль пришлось бы заставить повторять то, что уже сказано.** Боевой профиль
объявляет координаты базы у производителя (`pg-iam.auth`). Требование назвать их
второй раз у потребителя (`kaname.db`) заводит два места об одном предмете —
ровно тот класс, который эти же координаты сегодня не имеют, и который
расходится молча.

**Адрес узла вывел бы helm, а не мы.** `db.host` равен «имя релиза + псевдоним
подчарта». Заставить профиль выписать это значит переписать в него правило
helm — и обязать править профиль при каждой смене имени релиза.

**Предмет стандалон-стража здесь отсутствует.** Его вопрос — «создаёт ли чарт
этот объект»; зонт Service создаёт всегда, а секрет объявляет профиль. Вопрос,
на который страж отвечал, в зонте не задаётся.

### Чем это удержано впредь

Не вниманием. Координата базы **подтверждается на живом стенде** гейтом посадки
`deploy/scripts/assert-production-posture.sh`: он несёт жёсткую таблицу
«развёртывание | служба | узел базы», в которой служба доступа названа поимённо,
и для каждой службы спрашивает у САМОЙ базы через `pg_stat_ssl`, шифрованы ли её
TCP-соединения. Существенно то, что он **падает и на нуле соединений** —
«у узла НЕТ НИ ОДНОГО TCP-соединения — доказывать нечего»: значит неверный
адрес, неверное имя пользователя и неверное имя базы пройти не могут, потому что
живого соединения тогда не возникает вовсе.

Это строго сильнее отказа рендера: отказ рендера доказывает, что профиль что-то
сказал; свидетельство базы доказывает, что процесс действительно подключился.

**Граница названа прямо:** гейт судит ПОДНЯТЫЙ стенд. Согласие потребителя и
владельца на уровне ОБЪЯВЛЕНИЙ (то есть до подъёма) декларативным гейтом
сегодня не удержано — для рецепта справочной цели оператора такая пара
проверяется (`deploy/stand_psql_names_the_declared_database_test.go`), для
потребителя-службы нет. Почему такой гейт не заведён этой записью — ниже, и это
остаток, а не обещание.

## Что осталось и почему не сделано здесь

**Ключ потребителя пишется ДВУМЯ написаниями, и пара до унификации непроверяема.**
Пять подчартов называют имя секрета `db.passwordSecretName`, а
`services/registry/deploy/values.yaml` — `db.existingSecret`; предмет один.
Признак измерен на себе: первая редакция замера выше знала одно написание и
объявила **4 расхождения**, которых нет, — распознаватель не знал второй формы и
молчал о ней. Декларативный гейт пары, построенный на перечне написаний,
унаследовал бы ровно эту слепоту: форма, о которой он не знает, не даёт ни
красного, ни зелёного. Поэтому первый шаг — свести написание к одному, и это
предмет `services/registry/`, а не зонта.

**У секрета базы на боевых стеках не назван производитель.** Профиль объявляет
его как существующий (`auth.existingSecret`), поэтому подчарт его НЕ создаёт —
проверено рендером: с этим ключом Secret'ов в выводе ноль, Service остаётся. При
этом в таблице производителей `deploy/helm/umbrella/cutover-fe3455.sh` его строки
нет, и посев стенда его не заводит. Это **уже объявлено отдельным предметом** —
`deploy/rollout_preflight_covers_required_secrets_test.go` в своей шапке пишет:
«Смежное и другое: объявление `existingSecret` в профилях, у которого нет ни
производителя, ни проверяющего вовсе, — предмет отдельной задачи». Здесь оно
названо, чтобы измерение не потерялось, и не чинится: предмет не зонта.

## Как повторить замер

```sh
# (1) как применяются профили — единственное объявление цепочек
cat deploy/stacks.txt

# (2) отказы рендера подчарта: восемь, ни один не про image/db
grep -rn 'fail \|required(' deploy/helm/umbrella/charts/kaname/templates/

# (3) откуда приезжает каждая координата на каждом стеке —
#     слои в порядке helm: умолчание подчарта → values.yaml зонта → цепочка -f
#     (наложение картами, скаляры замещаются)

# (4) боевой профиль объявляет координаты у владельца
grep -n -A2 '^pg-iam:' deploy/helm/umbrella/values.prod.yaml

# (5) чем удержано: таблица гейта посадки и его отказ на нуле соединений
grep -n 'kaname|iam|' deploy/scripts/assert-production-posture.sh
grep -n 'НЕТ НИ ОДНОГО TCP-соединения' deploy/scripts/assert-production-posture.sh
```

## Связанное

- `trivy.yaml` — там же записано снятие четырёх заглушек сканирования по этой же
  причине: их предметом был отказ рендера СТАНДАЛОН-чарта, а у оставшегося в
  дереве подчарта такого отказа «не было ни секунды». Эта запись объясняет,
  почему его и не должно быть.
- `deploy/db_footprint_declaration_test.go` — соседний класс и ДРУГОЙ вывод: там
  от боевого профиля требуется объявить посадку базы (потолок памяти и трату),
  потому что умолчание чужого чарта никто под этот стенд не выбирал. Различие в
  том, ЧЕЙ объект называет величина: посадку не объявил никто, а адрес узла
  объявляет сам зонт.
