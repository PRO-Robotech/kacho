# Аутентификация

Эта страница описывает, как гейтвей устанавливает **кто** шлёт запрос (AuthN), прежде чем решать
**что** ему разрешено ([Авторизация](/architecture/authz)). Аутентификация выполняется на каждом
запросе обоих транспортов (REST и gRPC); результат — доверенный `principal`, проброшенный в
backend. Ключи конфигурации — [Конфигурация](/install/configuration).

## Принцип

AuthN — первый гейт периметра. Гейтвей принимает несколько типов удостоверений, но правило одно:
удостоверение либо валидно (и даёт конкретного principal), либо запрос отклоняется. **Невалидный
токен никогда не понижается до anonymous** — это `401`. В `production-strict` анонимный доступ
запрещён полностью.

## Базовый токен доступа — полоса выбирается ПО МАРКЕ

Базовый токен доступа — однострочный секрет вида `kacho_<id удостоверения>_<32 знака>`,
предъявляемый **как есть**: `Authorization: Bearer kacho_…`. Ни библиотеки JOSE, ни сборки
`client_assertion`, ни второго обращения. Выпускает его kaname
(`SAKeyService.Issue` / `UserTokenService.Issue`, вид `CREDENTIAL_KIND_SECRET`).

Порядок проверок на этой полосе:

1. **Марка** — полоса выбирается по префиксу `kacho_`, и только по нему. Строка с маркой
   остаётся на этой полосе, даже будучи негодной: вердикт по ней выносит она, а не следующая.
   Обратного правила («не разобралось как JWT — попробуем как секрет») нет: запасной путь по
   неудаче разбора превратил бы всякую негодную строку во вход второй полосы.
2. **Контрольная сумма** — встроена в саму строку и сверяется **без** обращения к kaname:
   обрезанный и опечатанный ввод отвергается на крае.
3. **Состояние** — идентификатор, срок, отзыв и активность владельца устанавливает kaname
   на своём cluster-internal слушателе. Ответ кэшируется на **5 секунд**; это же значение —
   объявленная граница отзыва **для ЗАПРОСА**: отозванное удостоверение перестаёт приниматься
   не позже 5 секунд после того, как отзыв закоммичен.

   :::note Та же граница действует и на ОТКРЫТОМ потоке
   Для запроса она держится тем, что каждый запрос спрашивает состояние заново. Длинное
   соединение (проекция потока подписки, `/subscription/v1/events`) запросов больше **не
   делает**: удостоверение проверено один раз, при открытии. Поэтому открытый поток
   **перепрашивает состояние своего удостоверения сам**, с тем же периодом — величина
   выводится из этих же 5 секунд, а не объявляется второй ручкой (kacho#1410).

   Полос у вопроса **три**, и они те же, что на пути запроса: удостоверение с
   идентификатором спрашивается по нему, браузерная сессия — по паре (человек, момент
   аутентификации), базовый секрет — по идентификатору строки удостоверения (kacho#1450).
   Недоступность нашего авторитета дольше объявленного срока закрывает **все** потоки
   реплики: неполученный ответ не есть «не отозван».

   Третья полоса появилась позже двух первых. До неё поток, открытый базовым секретом,
   был **неспрашиваемым**: вопрос о таком удостоверении требовал предъявленной строки, а
   держать её живой весь срок соединения значило бы завести хранилище секретов ради
   контроля. Вопрос по идентификатору снял эту цену; окно этой полосы — те же 5 секунд, и
   край **отказывается стартовать**, если объявленный срок кэша сделал бы его шире.

   Отзыв **ПРАВ** — другой предмет и другая полоса, и он до открытого потока доезжает своим
   путём (kacho#1022, перепрос изменений субъекта закрывает потоки названного субъекта).

   Чего перепрос на потоке **не** спрашивает, сказано прямо: отзывов внешнего провайдера
   (для них нужно предъявленное удостоверение целиком, а край его не хранит) и истечения
   срока самого удостоверения — истечение не отзыв, у него своя величина.
   :::
4. **Уровень аутентификации** — `1`. Следствие названо прямо: держатель базового токена
   **не может ни выпустить, ни отозвать удостоверение** — эти RPC несут floor `acr=2`, и
   церемонии, поднимающей уровень, у этой полосы нет. Долгоживущий предъявительский секрет
   не чеканит себе смену.

**Отказ на этой полосе один и неразличимый.** Неизвестный идентификатор, неверный секрет,
истёкший срок, отозванное удостоверение, заблокированный владелец, недостаточный уровень —
один и тот же `401` с одним и тем же текстом: различимый исход был бы оракулом о чужих
удостоверениях. Отдельным исходом остаётся только **недоступность** kaname: это не отказ
удостоверению, а неспособность установить его состояние, и он приходит `503`
(`UNAVAILABLE` на нативной поверхности) — повторить, а не переаутентифицироваться.

Где взять первый такой токен — «Первое удостоверение» в документации kaname.

## Проверка JWT: издатель — множество, у каждого свой набор ключей

Платформа чеканит свои токены сама, а прежний издатель на переходе остаётся,
поэтому принимаемых издателей **несколько**, и у каждого — **своя объявленная
запись** источника проверочных ключей: свой адрес, свой снимок, свой срок
годности.

Объединить наборы в один было бы дешевле и уничтожило бы ровно ту защиту, ради
которой развязка делается: ключ одного издателя проверял бы токен, объявляющий
другого. Адрес записи **объявляется** перечнем (`_TOKEN_ISSUER_KEYSETS`) и
никогда не выводится из издателя — издатель приходит от предъявителя, то есть
это недоверенный вход, а производный адрес получался бы у **всякого** издателя,
и состояние «записи нет» не наступало бы никогда.

Порядок проверок:

1. **Извлечение** токена из `Authorization: Bearer <jwt>`.
2. **Алгоритм** — только из закрытого словаря платформы (RS256 / ES256 / EdDSA);
   `alg: none` и симметричные подделки отвергаются **до** разрешения ключа.
3. **Идентификатор ключа** — форма ограничивается **до** обращения к источнику:
   значение приходит от предъявителя.
4. **Издатель** выбирает запись. Издатель, записи не имеющий, даёт **отказ** —
   никогда перебор записей подряд.
5. **Тип токена** сверяется с закрытым набором **этой** полосы. На нашей полосе
   тип обязателен: производитель типа — мы сами.
6. **Ключ** берётся из набора **выбранной** записи; алгоритм, закреплённый за
   ключом, сверяется с заголовком — заголовок алгоритм не выбирает.

   **Набор не добыт и ключ не найден — РАЗНЫЕ исходы.** Источник набора не
   ответил либо ответил не набором — неисправность **этой посадки**: `503`
   (`UNAVAILABLE` на нативной поверхности), клиенту следует повторить. Набор
   получен, а подписант назвал ключ, которого мы не публикуем, — негодное
   **удостоверение**: `401`. Граница проходит по тому, ответил ли источник, а не
   по тому, нашёлся ли ключ: иначе подделка с произвольным `kid` получала бы
   «повтори позже», а арендатор с исправным токеном — «войди заново» всякий раз,
   когда у нас лежит соседняя служба.
7. **Claims**: `iss`, `aud`, `exp` (**обязателен**), `nbf`, `iat` с объявленным
   допуском на расхождение часов.
8. **Отзыв на предъявлении.** Для токенов **нашего** издателя вопрос идёт
   **нашему** авторитету (`_PLATFORM_TOKEN_REVOCATION_URL`): прежний провайдер о
   наших токенах не знает by construction. На этой полосе недоступность
   авторитета даёт **отказ**; на полосе прежнего издателя сохраняется прежний
   мягкий проход, потому что его авторитет — третья сторона.

   **Отозванное удостоверение и молчащий авторитет отвечают РАЗНЫМИ кодами, и
   это не косметика.** Отозванный токен — отказ **удостоверению**: `401`, и
   клиенту следует пройти вход заново. Молчащий либо неверно настроенный
   авторитет — неисправность **этой посадки**, а не удостоверения: `503`
   (`UNAVAILABLE` на нативной поверхности), и клиенту следует повторить, а не
   переаутентифицироваться. Ответить `401` на нашу собственную неисправность
   значило бы послать арендатора чинить то, что у него исправно.

   **Исключение объявлено, а не умолчано:** на REST-поверхности вопрос об отзыве
   не задаётся на **предварительно разрешённых** путях — проверки живости, вход и
   выход. Ни один из них не действует властью удостоверения (выход как раз его и
   сдаёт), и требовать там живого токена значило бы запереть браузер с сессией,
   которую он не может отдать. На нативной gRPC-поверхности таких путей нет, и
   исключения тоже нет.

### Отзыв читается на ОБЕИХ полосах, и это сверяется сравнением

Полос личности человека здесь две — сессия развёрнутого провайдера (cookie) и
подписанный предъявитель. Свойство «наш отзыв действует на предъявлении» обязано
держаться на обеих, и проверяется оно **сравнением полос**, а не по каждой
отдельно: проба по каждой требует знать, каким свойство должно быть, — а
сравнение спрашивает другое, «решал ли кто-нибудь, что они различаются».

| полоса | чем удостоверяется | что спрашивается про отзыв |
|---|---|---|
| предъявитель | подпись издателя | по идентификатору удостоверения — у авторитета той полосы, чья запись выбрана |
| cookie | сессия провайдера | по паре (субъект, момент аутентификации) — у нашего авторитета |

У браузерной сессии нет ни идентификатора удостоверения, ни подписи, которую край
мог бы прочитать, поэтому вопрос к ней ставится единственным возможным способом —
по субъекту и моменту. Отсечка действует **вперёд**: вошедший заново работает.

**Отказ заканчивает носитель.** Порознь отказ даёт стоящее состояние: сессия
жива, её момент прежний, и повторной аутентификации ничто не запросит. Прежде
обратимость покупалась вызовом к административному API поставщика; теперь её
делает край своим действием — гасит cookie, и следующее обращение приходит без
сессии.

**Два неопределённых исхода различаются:** «отозван» — носитель заканчиваем;
«наш авторитет не ответил» — отказ **без** окончания носителя, потому что
заминка своего же соседа не повод выкидывать тех, кого никто не отзывал.

```mermaid
flowchart LR
  req["Bearer JWT"] --> ext["извлечь токен"]
  ext --> alg["алгоритм из словаря<br/>+ форма kid"]
  alg --> rec["выбрать ЗАПИСЬ<br/>по издателю"]
  rec -->|"записи нет"| deny["401"]
  rec --> typ["тип этой полосы"]
  typ --> jwks["набор ЭТОЙ записи<br/>(kid → ключ)"]
  jwks -->|"источник набора<br/>не ответил"| unavail["503 / UNAVAILABLE"]
  jwks -->|"набор есть,<br/>ключа в нём нет"| deny
  jwks --> sig["подпись + алгоритм ключа"]
  sig --> cl["claims<br/>iss/aud/exp/nbf"]
  cl --> rev["отзыв на предъявлении<br/>(полоса по издателю)"]
  rev -->|"ok"| pr["principal + acr"]
  rev -->|"отозван"| deny
  rev -->|"наш авторитет молчит<br/>или отвечает не то"| unavail
  cl -->|"fail"| deny
```

Пока `_TOKEN_ISSUERS` не объявлен, край строит **одну** запись из прежних
`KACHO_HYDRA_ISSUER` / `KACHO_HYDRA_JWKS_URL` — ровно прежнее поведение.
Объявить оба способа сразу нельзя: это два места об одном предмете, и край
**отказывается стартовать**, называя обе настройки.

## DPoP — sender-constrained токены

DPoP (RFC 9449) привязывает токен к ключу клиента: помимо `Authorization: Bearer` клиент шлёт
заголовок `DPoP` с подписанным proof. Гейтвей проверяет:

- **`jkt`-thumbprint** proof-ключа совпадает с `cnf.jkt` в токене (владение ключом);
- **`htm` / `htu`** в proof — HTTP-метод и URL текущего запроса;
- **`iat`-freshness** — proof выпущен в допустимом окне (`KACHO_DPOP_IAT_FRESHNESS_SECONDS`,
  дефолт 60 с);
- **anti-replay** — `jti` proof не встречался ранее. Где живёт эта запись и какие ручки ей
  управляют — зависит от вида хранилища однократности: полос **две**, и совпадают у них не
  все величины (см. ниже).

mTLS-bound вариант привязывает токен к клиентскому сертификату через `cnf.x5t#S256`. DPoP
включается флагом `KACHO_API_GATEWAY_AUTHN_ENABLE_DPOP`.

:::note Парсер proof — под fuzzing
Разбор DPoP-proof и REST-роутинг покрыты continuous-fuzzing (ночной CI) — это парсеры на границе
доверия, поэтому устойчивость к некорректному вводу проверяется отдельно.
:::

### Однократность предъявления — полос две

Запись о предъявленном `jti` живёт либо **в памяти процесса**, либо в **общей таблице флота**.
Выбирает полосу та же ручка, что и хранилище `Idempotency-Key`, — `KACHO_IDEMPOTENCY_STORE`
(`memory` | `postgres`) вместе с адресом `KACHO_IDEMPOTENCY_DSN`: второго пула к той же базе ради
того же предмета не заводится.

| | в памяти процесса | общая таблица флота |
|---|---|---|
| когда действует | `KACHO_IDEMPOTENCY_STORE=memory` | `KACHO_IDEMPOTENCY_STORE=postgres` + `KACHO_IDEMPOTENCY_DSN` |
| граница обещания | верно **ровно для одной реплики**: повтор, поданный в соседний под, записи не находит | запись видна всем репликам |
| где запись | LRU с вытеснением по ёмкости | строка `kacho_gateway.dpop_replay` |
| ёмкость | `KACHO_DPOP_REPLAY_CACHE_SIZE` (по умолчанию 100000) | ёмкости у таблицы нет — записи уходят по сроку, а не вытеснением |
| срок жизни записи | `KACHO_DPOP_REPLAY_CACHE_TTL_SECONDS` (по умолчанию 120 с) | **та же** ручка → `expires_at` строки |
| допуск | атомарная вставка-если-нет | один оператор `INSERT … ON CONFLICT`; просроченная строка перезаписывается, а не запрещает |

**`KACHO_DPOP_REPLAY_CACHE_SIZE` действует только в полосе памяти.** У таблицы ёмкости нет,
поэтому в посадке с общим хранилищем — то есть ровно там, ради чего таблица и заведена, — эта
ручка не меняет ничего. А вот срок жизни записи (`KACHO_DPOP_REPLAY_CACHE_TTL_SECONDS`,
≥ 2× окна свежести `iat`) читают **обе** полосы: в памяти это TTL записи кэша, в базе —
`expires_at` строки.

Пару «вид хранилища ↔ объявленное число реплик» (`KACHO_GATEWAY_FLEET_SIZE`) край сверяет при
старте и **отказывается стартовать**, если однократность остаётся в памяти процесса при флоте
больше одной реплики: обещание, верное лишь для одного пода, не должно тихо сужаться до него.

## Проброс identity — anti-spoofing

После валидной аутентификации гейтвей выставляет заголовки `x-kacho-principal-*` и прокидывает их
в backend (REST → gRPC-metadata). **Любые клиентские** `x-kacho-principal-*` / `x-kacho-token-*`
на входе **стрипаются** до аутентификации — клиент не может подделать identity, подставив
заголовок. Backend доверяет только тем `x-kacho-*`, что выставил гейтвей.

```mermaid
flowchart LR
  cli["клиент<br/>(может слать x-kacho-*)"] --> strip["strip входящих<br/>x-kacho-principal-* / x-kacho-token-*"]
  strip --> authn["AuthN: валидировать токен"]
  authn --> set["выставить x-kacho-principal-*<br/>(доверенный principal)"]
  set --> be["backend<br/>(доверяет только gateway-set)"]
```
